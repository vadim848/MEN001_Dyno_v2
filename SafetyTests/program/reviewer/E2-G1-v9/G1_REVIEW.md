## 3. Существенные замечания

### N20 — K-2 p−200: стимул не подаётся (ложный RED, убийца M-E2d-32 недоступен)

`current-e2d-fbk-window-abort.test.js:242–244`:
```
const R0=safeRef();const x=L.cached('Safe');x.step(OFF,100);...const fs0=fOf(R0);...
for(let n=x.t+1;n<=end;n++){...if(n===fs0)o.in_LV_Faulty_FBK=true;...}
```
Цикл начинается с `x.t+1` = `R0.p` (тот же путь `cached('Safe')` + `step(OFF,100)`, что в `safeRef`). При fs0 = p−200 условие
`n===fs0` не выполняется никогда — `in_LV_Faulty_FBK` остаётся FALSE на всей трассе.

Факт (мой прогон `k2.v75.tap` и `cand-E2d-v7.5.summary.jsonl` тестировщика): на v7.5, который при Faulty TRUE до жеста
Safe→R&D **не начинает** (аналитик v8-r §4.2), строки p−200 дают C1 ON ровно в u без Faulty; падают только на
«no R&D while LV Faulty TRUE» / «rollback … {"C1":true,"st":["STS_RND"]}». Это значит: Faulty не подан.

Последствия:
- на правильной реализации (v7.6) обе строки p−200 тоже FAIL (R&D достигается штатно, а тест считает Faulty TRUE) — ложный RED;
- именно строка p−200 — `killingScenario` M-E2d-32 в MUTATION_PLAN_E2d; как убийца она непригодна;
- атрибуция «8 K-2 RED на F1» в HANDOFF_v9 для двух строк p−200 неверна (на F1 Faulty тоже не подан).

Исправление (тестировщик): начинать цикл не позже p−200 (или выставлять Faulty до цикла) и добавить stand-precondition по
записанным входам «Faulty TRUE в p−200…p». Перепрогнать на v7.5 (ожидаемо: «C1 ON never … K-2 RED»).

Блокирует: включение K-2 в kill-базу M-E2d-32 (основной убийца по плану); G3 E2d по MOD-001 / WDG-02 (часть принятия).

### N21 — DOOR06: позитив «PLC (1,1) даёт HV» не заменён (F-76 не закрыт)

`current-door-interlock.test.js:55–60` («DOOR06 existing emergency/connector guards still prevent new HV …»):
```
for(const route of ["physical","existing-PLC-levels"]){ const healthyRun=runEnergy(route,true,true,true);
  assert.equal(healthyRun.hv,true,`${route}: healthy positive control …`); }
```
Для маршрута `existing-PLC-levels` (стимул `inPLC_RnD_Mode`=`inPLC_RnD_Mode_2`=TRUE) тест по-прежнему требует новый HV.
E2-Q76 §6 прямо: «позитив "healthy … gives new HV" для PLC-маршрута становится **запретом**». Тестировщик заменил только
соседний тест «DOOR06 actual HV chain».

Факт: на E2d v7.5 — `not ok 34 … existing-PLC-levels: healthy positive control with constant-FALSE False operand`
(`door.v75.tap`). На правильной реализации тест всегда FAIL. Цикл неисправностей для PLC-маршрута после вопроса 76 стал
вакуумным (HV и так FALSE) — парный позитив для него не существует.

Исправление (тестировщик): для PLC-маршрута ожидание hv = FALSE (запрет вопроса 76); парный позитив и цикл
неисправностей — только физический маршрут (либо PLC-цикл явно пометить как вакуумный после Q76). Прогнать **non-E2 файлы
на кандидате** (HANDOFF_v9 запускал на кандидатах только `current-e2*`) и поиском проверить, не осталось ли других
позитивов legacy (1,1) (поиск ревьюера: прочие non-E2 тесты используют (1,1) только в DOOR06 и (0,1) в rundown-baseline).

Блокирует: F-76; G3 non-E2 регресс на E2d (ложный RED).
