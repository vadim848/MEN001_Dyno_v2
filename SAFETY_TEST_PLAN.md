# MEN001 Dyno — план автоматизированного тестирования Safety Logic

> Обновление объёма 2026-10-18: действуют AGENTS.md и WORK_STATUS_AND_PLAN.md.
> Текущее задание — только программная логика; аппаратура принята как исходное
> условие. Прежние аппаратные согласования ниже сохраняются как история и не
> являются блокирующими условиями. Единый запуск: `npm run check:software`
> из SafetyTests; результаты SOFTWARE_CHECK_RESULTS.md / .json.

Статус: рабочий тестовый контракт до изменения TwinSAFE-кода.  
Источник требований: `SAFETY_STATE_MACHINE_SPEC.md`.  
Объект первой проверки: текущая версия `MEN001_Dyno_v2`.

> Этот стенд дополняет, но не заменяет Beckhoff Verify/Build, проверку CRC, испытания на TwinSAFE Runtime и validation на реальном оборудовании.

## 1. Цель

Создать повторяемую проверку всей согласованной логики:

- распознавание кнопок;
- состояния `Emergency`, `Safe`, `R&D`, `Run` и переходные фазы;
- переходы вверх и вниз;
- крышка и power-to-unlock замок;
- SS1, STO и потеря `Healthy`;
- discharge высокого напряжения;
- команды и feedback контакторов;
- таймауты, неисправности и рестарт;
- невозможность неоднозначных или опасных комбинаций выходов.

## 2. Предлагаемая архитектура стенда

### 2.1. Эталонная модель

Независимая исполняемая state machine, построенная по спецификации, а не скопированная из TwinSAFE. Она принимает дискретные входы и течение времени и выдаёт ожидаемые состояния, команды и faults.

### 2.2. Анализатор TwinSAFE XML

Читает `.splcproj`, `.sal`, `.sal.diagram`, `.sds` и `.sgvl` и формирует отчёт:

- найденные блоки, связи, переменные и параметры таймеров;
- неподключённые и потерянные ссылки;
- фактическое использование входов и feedback;
- потенциально конфликтующие выходы;
- соответствие структуры проверяемым требованиям.

Статический анализ подтверждает структуру, но не считается доказательством фактического выполнения логики TwinSAFE Runtime.

### 2.3. Сценарный симулятор

Сценарий задаёт последовательность вида:

```text
time | inputs changed | expected mode/phase | expected outputs | expected fault
```

Симулятор прогоняет нормальные, граничные и отказные сценарии с дискретным шагом времени.

### 2.4. Проверка инвариантов

На каждом шаге времени автоматически проверяются правила, которые не должны нарушаться ни при какой последовательности входов.

### 2.5. Отчёт

Для каждого теста: `PASS`, `FAIL`, `NOT PROVABLE FROM XML` или `HARDWARE VALIDATION REQUIRED`, с указанием требования и момента первого расхождения.

## 3. Глобальные инварианты

1. Одновременно активно ровно одно основное состояние.
2. После старта или рестарта `Run` не восстанавливается автоматически.
3. Любой переход вверх требует нового подтверждённого жеста.
4. Переход вверх запрещён без `CoverClosed` и `CoverLockedFeedback`.
5. `UnlockCover` запрещён в `Run`, `Emergency` и всех переходных фазах.
6. `UnlockCover` и команда движения вверх не могут быть активны одновременно.
7. После входа в `TwoButtonsAttempt` одиночная команда невозможна до полного цикла очистки.
8. Опасная энергия не включается одним PLC-битом без safety interlock и feedback.
9. Потеря `Healthy` во время SS1 приводит к STO без ожидания штатного окончания SS1.
10. Во время штатного SS1 источник и C2 остаются включены для регенерации.
11. Discharge начинается при ещё включённом источнике/C2.
12. C2 не отключается до подтверждения безопасного HV либо отдельно утверждённой отказной процедуры.
13. `R&D` не устанавливается до безопасного HV и `C2_FBK=OFF`.
14. Крышка остаётся заблокированной до завершения SS1/STO coast/discharge/отключения C2.
15. Неоднозначный feedback не приводит к автоматическому повышению состояния.

## 4. Наборы тестов

### A. Запуск, рестарт и Emergency

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| A01 | Power-up со всеми командами OFF | Только безопасное начальное состояние; `Run` запрещён |
| A02 | Power-up с зажатой зелёной | Команда не принимается до отпускания и полного фильтра |
| A03 | Power-up с зажатой синей | Unlock не возникает до отпускания и нового жеста |
| A04 | Power-up с двумя зажатыми | StepUp не возникает |
| A05 | E-Stop в каждом основном состоянии | Переход в аварийную последовательность, STO согласно проекту |
| A06 | E-Stop в каждой переходной фазе | Переход вверх прекращён, опасные выходы переводятся в определённое безопасное состояние |
| A07 | Восстановление E-Stop | Только `Safe`; автоматического возврата в R&D/Run нет |
| A08 | Перезапуск во время SS1/discharge | Безопасное восстановление без пропуска незавершённого снятия энергии |

### B. Распознаватель кнопок

|---|---|---|

| B02 | Аналогично для синей | `UnlockCover` только после `T_SINGLE` и только пока синяя удерживается |
| B03 | Вторая кнопка появилась в пределах `T_CHORD_WINDOW`, обе стабильны `T_BOTH` | Один `StepUp` |
| B04 | Вторая появилась точно на границе окна | Детерминированный результат согласно принятому правилу `<=` |
| B05 | Вторая появилась позже окна | Нет StepUp и нет новой одиночной команды до очистки |
| B06 | Синяя 0.5 s, отпускание, немедленно зелёная | Никакой команды |
| B07 | Короткие хаотические нажатия | Никакой команды |
| B08 | Дребезг до завершения `T_SINGLE` | Никакой команды; требуется очистка |
| B09 | В `TwoButtonsAttempt` моргает зелёная | `T_BOTH` сбрасывается; одиночная синяя не принимается |

### C. Крышка и замок

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| C01 | Синяя подтверждена в Safe | Соленоид включён только пока синяя удерживается |
| C02 | Синяя подтверждена в R&D | То же поведение, что в Safe |
| C03 | Синяя в Run | Игнорируется, соленоид OFF |
| C04 | Синяя во время любой transition phase | Соленоид OFF |
| C05 | Синяя отпущена, крышка остаётся открытой | Соленоид OFF; timeout/fault отсутствует |
| C06 | Попытка StepUp при открытой/незапертой крышке | Игнорируется без fault и без изменения режима |
| C07 | Крышка закрыта, но locked feedback отсутствует | StepUp запрещён |

| C09 | Locked feedback потерян при опасной энергии | Аварийная реакция; обычный переход не продолжается |
| C10 | Команда unlock и feedback locked противоречат ожидаемой последовательности | Диагностика; опасный переход запрещён |

### E. R&D -> Run

| ID | Сценарий | Ожидаемый результат |
|---|---|---|

| G03 | До окончания coast wait | Unlock OFF; R&D не устанавливается |

| G06 | Подтверждение discharge не появилось | C2 не отключается штатным путём; timeout/fault |

| ID | Сценарий | Ожидаемый результат |
|---|---|---|

### I. Feedback, timeout и противоречия

Для каждого управляемого элемента должны автоматически генерироваться варианты:

- feedback не включился;
- feedback не выключился;
- feedback появился до команды;
- feedback пропал после успешного включения;
- краткий импульс feedback;
- оба взаимоисключающих feedback активны;
- сигнал `Unknown/NotMapped`, если это обнаруживается структурным анализом.

Во всех вариантах проверяется запрет ложного повышения состояния и определённая безопасная реакция.

### J. Автоматически генерируемые последовательности

- перебор граничных времён `T-1 tick`, `T`, `T+1 tick`;
- случайный button bounce;
- случайная потеря каждого feedback в каждой фазе;
- комбинации E-Stop/Healthy/CoverLocked на границах таймеров;
- stuck-at-0 и stuck-at-1 для каждого дискретного входа;
- длительное удержание команд;
- рестарт модели в каждом внутреннем состоянии;
- проверка всех достижимых состояний на глобальные инварианты.

## 5. Трассируемость требований

Каждое правило из `SAFETY_STATE_MACHINE_SPEC.md` должно получить уникальный requirement ID. Каждый тест обязан ссылаться минимум на один requirement ID, а каждое обязательное требование — минимум на один положительный и один отрицательный тест.

Итоговая матрица:

```text
Requirement -> Tests -> Model result -> XML evidence -> TwinSAFE runtime result -> Hardware validation
```

## 6. Последовательность работ

1. Согласовать этот тестовый контракт и открытые физические параметры.
2. Добавить requirement ID в основную спецификацию.
3. Реализовать эталонную модель без изменения TwinSAFE.
4. Реализовать сценарный runner и отчёт.
5. Реализовать безопасный read-only анализатор XML.
6. Прогнать текущую `v2` и определить, какие проверки реально доказуемы автоматически.
7. Сверить несколько тестов вручную и намеренно внести дефекты только в копию/тестовый fixture, чтобы доказать чувствительность тестов.
8. После отдельного разрешения создать рабочую ветку и менять TwinSAFE.
9. После каждой правки повторять полный regression suite.
10. Завершить Beckhoff Verify/Build, CRC и аппаратную validation отдельно от стороннего стенда.

## 7. Открытые вопросы до исполняемой реализации

- точные имена и безопасная полярность всех физических входов/выходов;
- окончательные времена SS1, coast, discharge и feedback timeout;
- доступный сигнал `DischargeComplete/HV_Safe`;
- точное значение и семантика AX5805 safety feedback;
- утверждённая последовательность `R&D -> Safe`;
- аварийная discharge-процедура при E-Stop;
- возможность экспортировать/наблюдать TwinSAFE Online Values для сравнения с моделью;
- допустимая политика при дребезге `Healthy` и safety feedback.
