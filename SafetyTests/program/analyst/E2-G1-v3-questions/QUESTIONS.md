## Q-T3-2 — UNL-04 при Door FALSE: ОТВЕЧЕНО по источникам, Вадиму вопрос не нужен

### 1. Что делает in_Door_Monitor в Unlock

**Reference 4495a1f (Network2).** Есть только Safe (b_Step1):
- `FBAnd7` = b_Step1 (через FBDecouple3.DecOut1) ∧ `in_Relase_Door_PB` → `FBRs1.Set`;
- `FBAnd8` = **NOT** `in_Door_Monitor` (AndIn1, Make Contact = инверсия) ∧ b_Step1 → `FBRs1.Reset`;
- `FBRs1.RsOut` → `out_Door_Unlock_Solonoeid`.
- `in_InterLock_NC_1/2` в цепь Unlock **не входят**. Их потребители — только Network2/FBAnd1 (подъём) и Network6/FBAnd9.
- Второй потребитель Door — `FBAnd6.AndIn1` (прямой контакт): это energy guard, его заменил D-DOOR-INTERLOCK.
- Следствие: в Safe при Door FALSE одновременно активны Set и Reset. Приоритет у сброса, поэтому Unlock FALSE.
  Unlock возможен только при Door TRUE. Door, упавший при выданном Unlock, сбрасывает его. FBAnd8 (order 100)
  исполняется после FBRs1 (order 96), поэтому в reference сброс виден на скане d+1.

**Canonical F1.** Потребители Door: `Network2/FBAnd8/AndIn1`, `Network12/FBAnd11/AndIn1`, `Network12/FBAnd17/AndIn1`.
- Safe: `N2/FBAnd7` = b_Step1 ∧ recRndC_BA → `b_Set_Door_Unlock`. `N2/FBAnd8` = NOT Door ∧ b_Step1 → `b_Reset_Door_Unlock`.
  Оба идут в `N1/FBOr3`/`FBOr4` → `FBRs6` (reset-dominant) → `FBAndUnlockHold` → `out_Door_Unlock_Solonoeid`.
  Роль Door в Safe та же, что в reference: сброс при Door FALSE.
- R&D: `N12/FBAnd2` = b_Step_RnD ∧ recRndC_BA ∧ NOT green ∧ Door (через FBAnd11) → `b_Set_Door_Unlock_1`.
  Door TRUE — условие выдачи (grant). `N12/FBAnd3` = b_Step_RnD ∧ Door ∧ NOT blue → `b_Reset_Door_Unlock_1`.
- Запрет Unlock при открытой крышке, который снимают Q-ARCH-04/10, находится не в Door-цепи. Это вход
  `in_InterLock_NC_1/2` в `RndPhysicalCompact/GATE_001`, через который проходит квалификация синей (GATE_005 → GATE_010
  → BLUE TON). Таблица PLAN.v1 архитектора к Q-ARCH-04 тоже указывала InterLock-guard, а не Door.

### 2. Совместимость «крышка открыта (NC FALSE)» и «Door FALSE»
- Логически совместимы. Это независимые входы программы, все четыре комбинации допустимы. Решение 2026-10-18 требует
  проверять значения входов без выяснения их физического происхождения.
- По смыслу программы оба сигнала говорят «не закрыто». Door TRUE был разрешением подъёма в reference (FBAnd6),
  а Door FALSE сбрасывает Unlock. Поэтому NC FALSE вместе с Door FALSE — согласованное «открыто», а не противоречие.
- Физическую корреляцию аналитик не исследует (hardware вне объёма). Если физически открытая крышка всегда даёт
  Door FALSE, то Unlock при уже открытой крышке практически не наблюдается. Это следствие сохранённой роли Door, а не
  новой политики. См. примечание ниже.

### 3. Что решают Q-ARCH-04 и Q-ARCH-10
- Q-ARCH-04: «А — как в reference … независимо от того, открыта ли уже крышка **(InterLock NC FALSE)**. Запрет из F1
  снимается». Q-ARCH-10: «как в Safe (Q-ARCH-04) … (InterLock NC FALSE). Запрет F1 снимается».
- Оба решения касаются только NC1/NC2, то есть guard F1 в GATE_001. Door в них не упомянут.
- «Как в reference» дополнительно подтверждает сохранение Door-сброса: в reference Unlock при Door FALSE невозможен.
- Роль Door в Unlock прямо сохранена: D-DOOR-INTERLOCK («DoorMonitor сохраняет только existing unlock grant/reset
  роль»), SPEC §5 «Роли DoorMonitor в существующем unlock grant/reset не менять» и п.9, CVR-004 «Door сохраняет unlock
  role», CVR-006, AGENTS.md («его существующую DoorMonitor роль сохранить»).
- Более поздних решений, которые меняли бы Door в Unlock, нет.

### Вывод
Противоречия нет. Строка UNL-04 в CRITERIA_DELTA_v4 «Door TRUE/FALSE» в исходном состоянии — ошибка аналитика:
обобщение без источника. Исправлено в CRITERIA.md этой папки (UNL-04 только при Door TRUE + новый UNL-05: Door FALSE →
Unlock FALSE в Safe и R&D при любом состоянии NC). Одобренный current-unlock-hold.test.js стр. 54 этим не нарушается.

Примечание для ведущего (необязательно, не блокирует): если Вадим под Q-ARCH-04 имел в виду и физически открытую
крышку с Door FALSE, это было бы новое решение, отменяющее Door-роль из D-DOOR-INTERLOCK. Задать такой вопрос
можно только как подтверждение. Без нового ответа действует критерий UNL-05.

### Q-T3-2b (низкий, не блокирует UNL-04/UNL-05) — изменение Door во время удержания синей
Reference задаёт только Safe: Door FALSE при выданном Unlock → сброс; Door снова TRUE при удерживаемой синей → Set
(reference без квалификации 500 мс) → Unlock снова TRUE.

Чего не хватает:
1. **Safe, повторная выдача.** Исходно устойчивый Safe, Door TRUE, синяя квалифицирована, Unlock TRUE. События: Door
   FALSE в d (Unlock снят), затем Door TRUE в d+300, синяя всё время удерживается. Выдать Unlock снова сразу (как
   reference: квалификация уже пройдена) или только после отпускания обеих кнопок и новой квалификации 500 мс?
2. **R&D, Door падает во время удержания.** Исходно устойчивый R&D, Door TRUE, Unlock TRUE (синяя удерживается).
   Событие: Door FALSE в d. На canonical Door в R&D участвует только в выдаче (FBAnd2) и в сбросе при отпущенной
   синей (FBAnd3), поэтому Unlock остаётся TRUE до отпускания. В reference R&D-Unlock нет. Снимать ли Unlock как в
   Safe (Q-ARCH-10 «как в Safe»)?

До ответа: в Safe Door FALSE в d → Unlock FALSE не позже d+1 (нормативно, по reference). Повторная выдача в Safe и
R&D-случай — BLOCKED, на тестах только наблюдение.

## Q-T3-1 — in_Estop_PLC во время Run→R&D: L2 против нормальной остановки. ВОПРОС ВАДИМУ (+ временный критерий)

### Разбор
- **Откуда L2.** L2 ввёл аналитик (CRITERIA_DELTA_v4 §0.1; E2-G1-v2-questions Т3 (б)). Основание — Q-ARCH-01 и
  Q-E2Q-01 «одна цепь для всех случаев Q-ARCH-01», то есть устойчивый R&D, R&D→Safe и Safe→R&D: состояния LV ON /
  HV OFF, где нормального расписания снятия этих выходов нет. Распространение L2 на фазы Run→R&D, abort
  StartingRun, откаты и защитный спуск сделал тоже аналитик. Прямого решения Вадима о моментах аварийной цепи
  на фоне уже идущего снижения энергии нет.
- **Конфликт.** Нормальная остановка (уточнение Вадима, STP-A): STO в t_a+2000, Discharge в t_s+5000, C2 OFF в
  t_d+T_DIS. Аварийная цепь от e (L3, reference): STO +7006, HV discharge +7008, C2 OFF +8009. При любом
  e ≥ t_a нормальные моменты наступают раньше аварийных. Буквальный L2 потребовал бы отложить STO, Discharge и
  C2 OFF на величину вплоть до (e − t_a) + ≈7 с. Например, e = t_a+1999 → STO в ≈ t_a+9005 вместо t_a+2000.
  Это задержка уже запланированного безопасного действия.
- **Что говорят источники (только косвенно).**
  - SPEC §13: Emergency — высший приоритет. Это приоритет реакции, а не правило выбора более позднего момента.
  - EMG-008/009 (§9): при отказе в SS1 STO наступает немедленно, а восстановление не возвращает SS1 и не сокращает
    выбег. Направление то же: не отменять и не откладывать снижение энергии.
  - EMGREF(2): после e запрещено снятие STO. Отложенный STO формально не является «снятием», значит, EMGREF(2)
    этот случай не решает.
  - Q-ARCH-01 для «идущего R&D→Safe» буквально говорит «C1 OFF через 2 с». Если нормальный R&D→Safe (MOD5-01)
    размыкает C1 раньше e+2 с, возникает тот же вопрос.
  - Цитаты «не отменять начатое снятие энергии» в SPEC/решениях нет. Есть EMG-005 (восстановление входа не отменяет
    аварию) и D-LATE-SECOND «не отменять/не прерывать», но последнее относится только к поздней второй кнопке.
- Однозначного ответа источники не дают. Вариант «сдвигать» физически сомнителен, но запрещён ли он, не сказано.

### Оценка A11 тестировщика — ДА, ослабляет oracle
Ослабление двойное:
1. При relax (e2-rule-l.js стр. 40–42) утверждается только верхняя граница τ ≤ τ_Run+1. Нет нижней границы и нет
   границы «не позже нормального момента». Проходит реализация, которая отменяет нормальную остановку и выдаёт STO
   в любом скане из (t_a+2001, e+τ_Run). Это неверно при **любом** из двух возможных ответов: и «сохранить ранний»,
   и «сдвинуть в окно Run».
2. N — это **наблюдаемая** no-event трасса реализации (`noEvent(phase)`, e2-emergency.js:70). Нормальная остановка на
   canonical дефектна: SCENARIO_DECISIONS «Факт canonical F1» — STO, Discharge и сброс C2 одновременно, без SS1 и
   выбега. Поэтому relax включается от моментов реализации, и ожидание выводится из кода. Нормальные моменты должны
   браться из STP-A/B (нормативные t_a+2000, t_s+5000, t_d+T_DIS), а не из трассы.

Замена (CRITERIA.md, EMG-RD-L): нормативная дизъюнкция, верная при обоих ответах, с отдельной диагностикой выпавшей
ветки. Это строже A11 и не предрешает ответа. Блокируется только выбор ветки.

### Вопрос Вадиму — Q-T3-1 (средний; EMG-001/EMG-011, STP-A/B; E3)
Исходно: устойчивый Run, принята нормальная остановка Run→R&D (зелёная или PLC) в t_a. Идёт SS1 (до t_a+2000) или
уже выбег / выдержка разряда. Событие: авария в e (EStop, PLC-авария, Mentee, connector и т.п.).

Аварийная цепь из устойчивого Run (как в reference) даёт C1 OFF через ≈2 с, STO через ≈7 с, HV discharge через
≈7 с, C2 OFF через ≈8 с от e. Нормальная остановка сделала бы STO в t_a+2 с, Discharge через 5 с после STO,
C2 OFF после выдержки разряда, то есть раньше.

Чего не хватает:
- **(А)** уже запланированные нормальной остановкой шаги (STO, Discharge, C2 OFF) выполняются не позже своих
  нормальных моментов. Авария добавляет свои действия (Emergency, C3/BMS OFF и LV discharge сразу, C1 OFF через
  2 с) и может только ускорить шаг, но не отложить его;
- **(Б)** авария запускает общую цепь с её моментами от e. Нормальный STO/Discharge/C2 OFF откладываются до
  моментов цепи (STO ≈ e+7 с, даже если SS1 закончился бы раньше). Уже выполненный STO при этом не снимается;
- **(В)** иначе, например, немедленный STO при аварии во время SS1.

Тот же вопрос для прочих уже идущих спусков: abort StartingRun, откат WDG-03, защитный спуск STP-G/H, откат Config,
а также для R&D→Safe (момент C1 OFF: нормальный или «через 2 с» по Q-ARCH-01).

Рекомендация аналитика — (А). Безопасное действие не откладывается из-за аварии, по аналогии с EMG-008/009 и
приоритетом §13. Таймеры цепи при этом не меняются.
Ответ нужен до G3 E3 (STOP v2). Для G1 E2 действует дизъюнкция EMG-RD-L.
