## 1. Вопрос 1 — L2 −1 скан вне SU (G3Q-1, ослабление oracle)

**Ответ.** В TD-10 этот случай не входит: TD-10 действует только в StartingRun и прямо требует отдельного
решения для прочих состояний. Поэтому это **новое ослабление**, записано явно как G3Q-1.

**Рекомендация: расширить окно TD-10 / TD-12 на состояния общей цепи Q-ARCH-01. Обоснование:**
- та же природа, что у TD-10: путь с другой латентностью, таймер не меняется;
- выдержка C1 2 с соблюдена (2004 ≥ 2000; Q-ARCH-01 «А», Q-E2Q-01 «А»);
- норма +2005 заставила бы реализацию задерживать снятие LV (против принципа 1).

**Критерий L2-RD (READY-D, REC-ACCEPTED G3Q-1):**
- **Исходно:**
  - (a) устойчивый R&D (R0);
  - (b) R&D→Safe принят, C1 ещё ON;
  - (c) Safe→R&D принят (A1 по TD-08), R&D не подтверждён.
- **Событие:** `in_Estop_PLC` TRUE в e (удерживается) или причина L1 в e. Эталон d_Run — `in_Estop_PLC`
  в устойчивом Run, та же база.

| Выход | Норма |
|---|---|
| `out_LV_C1` OFF, R = `in_Estop_PLC` в S | d_Run−1 ≤ τ_R−e ≤ d_Run+1 и τ_R−e ≥ 2000 |
| `out_LV_C1` OFF, причина L1 X | τ_R−1 ≤ τ_X ≤ τ_R; τ_X−e ≥ d_Run−2; τ_X−e ≥ 2000 |
| STO, `out_HV_C2` OFF, `out_HV_Discharge_Request` (уже в цели до e) | в цели в каждом скане ≥ e |
| Imm (статус, C3/BMS OFF, LV discharge, Unlock FALSE) | L2 Imm / L1 Imm без изменений |
| Защёлка, Restart → только Safe | без изменений (EMG6-01) |

- (c) Safe→R&D при e < u1 (C1 ещё не ON): C1 не включается ни в одном скане ≥ e. Это инвариант L
  (Q-ARCH-01: «подъём LV прекращается немедленно»), окно здесь не применяется.
- **Самотест:**
  - −2 для R → FAIL; −1 → PASS; +2 → FAIL;
  - для X: −3 → FAIL, −2 → PASS;
  - C1 на 1999 → FAIL.
- **Факт E2b…E2d:** +2004 при Run +2005 — PASS по G3Q-1.
- **ID:** EMG-001, EMG-004, EMG-011, MOD-001, MOD-005.

## 2. Вопрос 2 — L3 +2 скана против reference (G3Q-2, без ослабления)

**Рекомендация: недопустимо. Discharge +7010 при эталоне reference +7008 — FAIL L3. Окно [ref, ref+1]
не расширяется. Обоснование:**
- это **опоздание** снятия энергии, а не опережение. Принцип 1 тут не помогает;
- Q-T3-1 «А»: авария шаг не задерживает;
- Q-ARCH-01: существующие тайминги аварийной цепи не менять;
- canonical F1 укладывался в окно (+7009), так что сдвиг — регрессия кандидатов, а не латентность,
  неизбежная для v2;
- переупорядочение R1/E2b само по себе источником нормы не является. Исправлять порядком исполнения
  (архитектор/редактор), а не oracle.

**Критерий (без изменений, L3):**
- устойчивый Run, `in_Estop_PLC` TRUE в e;
- для каждого Del-выхода (C1 OFF, STO, HV Discharge, C2 OFF): τ−e ∈ [ref, ref+1], где ref — reference
  4495a1f, измеренный тем же helper'ом;
- Imm ≤ ref+1.

Атрибуция FAIL — кандидатам E2b…E2d (появился после F1). Записано как G3Q-2 (REC-ACCEPTED, норма сохранена).
**ID:** EMG-001, EMG-011.

## 3. Вопрос 3 — E2-02 с восстановлением LV на h+1 / h+3 (G3Q-3)

**Рекомендация: да, HLT-01 действует. Обоснование:**
- Q-RC-16 «А» — прямой ответ Вадима: если спуск затронут потерей LV Healthy, по приходу в R&D всё равно
  выполняется цепной R&D→Safe, даже если LV вернулась; ответ прямо называет гонку E2-Q1;
- открытым остаётся только вопрос, считается ли потерей короткий импульс Faulty TRUE (1 скан при h+1).
  Фильтр не задан, reference реагирует на уровень, принцип 1 → **считается**. Записано как G3Q-3.

**Критерий E2-02-R (READY по Q-RC-16; длительность импульса — REC-ACCEPTED G3Q-3):**
- **Исходно:** Run; принят down (зелёная или фронт CMD — CMD только в E4); последовательность ждёт
  C2_FBK OFF после команды C2 OFF.
- **Событие:** `in_LV_Faulty_FBK` TRUE в h, FALSE с h+r, где r ∈ {1, 3, 100}; C2_FBK OFF впервые в h+d,
  d ∈ {1..5}. Вариант: восстановление после R&D.
- **Ожидается:**
  - E2-01 в каждом скане;
  - итог R&D (единственный исход);
  - затем без команды цепной R&D→Safe: C1 OFF не раньше R&D, C3/BMS OFF, C1_FBK OFF → Safe;
  - SafetyFault HealthyLost TRUE не позже Safe (Q-E2Q-02; до символа — NV, A8).
- **Запрещено:**
  - устойчивый R&D, оставшийся после восстановления LV;
  - Emergency, Step4∧Step12, возврат в Run;
  - C1 OFF до C2_FBK OFF.
- **Границы:**
  - Faulty TRUE в первом скане устойчивого R&D (после прихода) — HLT-01 (E2-Q2a), тот же итог;
  - Faulty TRUE до принятия down — STP-G (свои нормы).
- **Область G3Q-3 («1 скан считается»):** только спуски с памятью Q-RC-16 — STP-A/B (Q-RC-09/E2-Q1),
  STP-G/H, abort StartingRun (Q-ARCH-03). Конвенция STP-G «1-скан провал в устойчивом Run — наблюдение»
  не меняется.
- **Факт E2c/E2d:** R&D сохраняется — FAIL. Атрибуция архитектору, возможная связь с HLT_LV (K-2).
- **ID:** STP-004, HLT-001, EMG-012, MOD-005.

## 4. Неатрибутированные наблюдения G3

### 4.1 Выход из Emergency по Restart при C1_FBK / C2_FBK ON (старт из Safe) — норма есть, READY

**Источники:**
- **SPEC §12 п.4:** «Feedback контакторов соответствует выключенному состоянию» — условие выхода.
- **V14-Q6 «А»:** условия SPEC §12 сохраняются.
- **Reference 4495a1f Network2:** цепь выхода FBAnd1 → FBTon1 → FBAnd2 (∧ `in_LV_C1_FBK` NO ∧ `in_HV_C2_FBK` NO)
  → FBTon2 → FBAnd3 (STO FBK) → FBAnd4 (∧ FBTon3 по `in_Reset_PB`). Restart действует только при выключенных FBK,
  по уровню удержания.

**Критерий EMG6-FBK (READY):**
- **Исходно:** Safe, C1_FBK или C2_FBK ON без команды (FBK-10 / Q-V4-02); `in_Estop_PLC` TRUE в e, затем FALSE;
  энергия снята.
- **Событие:** Restart (зелёная ≥ квалификации reference) в g, при FBK ON.

| Случай | Ожидается |
|---|---|
| FBK ON во всём [g, конец нажатия] | Emergency в каждом скане до конца наблюдения; Safe нет |
| нажатие отпущено, затем FBK OFF | Emergency сохраняется; выхода без нового нажатия нет — нажатие при FBK ON не исполняется отложенно (reference — уровень, D-TEAM п.1) |
| нажатие удерживается через FBK OFF (в f) | выход в Safe допустим только при FBK OFF, по цепи reference (выдержки FBTon1/2/3 от выполнения условий). Ни одного скана Safe ≤ f |
| после выхода | только Safe (EMG6-01) |

- **Запрещено:** Safe (выход из Emergency) в любом скане с C1_FBK или C2_FBK ON; R&D/Run после Restart.
- **Факт:** выход на +100 при FBK ON на E2b…E2d — **FAIL SPEC §12 / EMG-006**. Атрибуция архитектору (выживший
  M-E2b-19, G10_EXIT.AndIn5 — не доказано).
- **ID:** EMG-006, MOD-008.
- Отсчёт выдержек выхода — по reference, без новых чисел. Точные значения FBTon1/2/3 тестировщик берёт
  из reference SAL тем же helper'ом.

### 4.2 FBK10-PLC-REG (1): R&D на u1+599 — норма есть (RND-CONF-T), FAIL

**Источники:**
- **RND-CONF-T** (E2-plan-v5-questions §2, вопрос 68 «Б», TD-02): подтверждение R&D не раньше конца окна
  500 мс от команды C1 ON. При FBK и норме с ≤ u1+499: R&D нет ≤ u1+599, u1+600 — наблюдение, R&D есть на u1+601.
- Здесь u1 — первый наблюдаемый `out_LV_C1` TRUE, независимо от того, кто запустил переход: кнопки или legacy (1,0).

**Вывод:**
- R&D на u1+599 — **FAIL** (на 2 скана раньше нормы: преждевременное подтверждение).
- Ослаблять не рекомендую: раннее подтверждение R&D открывает R&D-действия (Unlock, R&D→Run) раньше
  окна watchdog.
- Причина, вероятно, в том, что окно на пути (1,0) отсчитывается от команды, а не от выхода (ср. R5-2). Не доказано.
- Путь (1,0) удаляется в E4 (вопрос 77). Отнести FAIL к «known до E4» может только ведущий, если архитектор
  покажет, что причина в legacy-декодере. Для кнопочного Safe→R&D норма действует без оговорок.
- **ID:** MOD-001, WDG-002.
