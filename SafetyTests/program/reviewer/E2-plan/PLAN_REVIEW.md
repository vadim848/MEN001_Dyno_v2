## (b) R1 — «мёртвая» логика

- Строгость: «выходы Network4 = FALSE» — вывод «иначе reference не работал бы» (при TRUE b_Step1_Reset/b_Step3_Reset
  запрещают Safe/Run и в reference). Аргумент сильный, но DERIVED: DEC-3 для этих входов в проекте записан как
  **NV** (UNSUPPORTED_UNBOUND_PROGRAM_INPUT). Удаление N4 устраняет NV, но доказательство мёртвости N5/Step2 условно.
- Конфликт с AGENTS.md: в reference (dumpref) **Network5 — исходная power-on последовательность** Safe→Step2→Run:
  b_Step2_Set = Network2/FBTon3 (зелёная 2 с) ∧ ReadyForStep2; C1+C2 ON → FBK → **TON 5 с** → Healthy (сырое FALSE) →
  сброс запросов разряда → TON 200 мс → снятие STO → TON 200 мс ∧ **STO FBK** → Step3. В v2 её вход
  перепривязан на Network4 ранее (не в этом плане). План называет её «мёртвой логикой» и не трассирует,
  какие исходные действия сохранены в N11/N12 (например, подтверждение STO FBK перед Run, 5-секундная
  выдержка), а какие сняты согласованными решениями (D-STO-LAUNCH сохраняет «дальнейшие подтверждения Run»).
  Q-MU06-02 разрешает удалить только N5/FBAnd7, N9/FBAnd1, N12/FBAnd14 (и их входные N12/FBAnd12/13), не всю Network5.
  N1/FBAnd3/9/11 и N6/FBAnd10 — дубликаты проверены (та же функция, та же межцикловая позиция) — замечаний нет.
- Требуется: трасса «действие reference Network5 → место в v2 / решение, которым снято»; вопрос Q-ARCH-06 адресовать
  Вадиму (удаление исходной последовательности и таймеров 5 с/200 мс/200 мс/100 мс), с объявленной дельтой
  −27 FB/−244 портов/−19 Symbols для G2 (прежнее правило «CRC после потери символов не принимать»).
- Альтернатива без R1 для E2: отсоединить кольцо от N4/Step2 только деактивацией портов из списка R1
  (+ N3/FBDecouple2.DecIn2 := in_False), блоки не удалять — 242+5+1+2+1 = **251 ≤ 255** (прототип архитектора и был
  без R1, 252). R1/R2 нужны только с E3 (251+17 = 268).
