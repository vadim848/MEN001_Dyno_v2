# E4-v14 — критерии проверки PLC-интерфейса (подготовительные)

Срез / роль / дата: E4-v14 / v2-analyst / 2026-10-21.
Источник: SAL 34b5b8504e0c… SGVL 517fdadd9130… diagram 7b5eb7943901… (сверено).
Трассировка документа: TRACE.md. Вопросы: QUESTIONS.md.

Статусы критериев:
- **READY** — oracle из утверждённых требований (SPEC §§17,19–20, SCOPE, решения
  Вадима), не зависит от подтверждения v1.4. Тесты можно писать сейчас; реализация
  E4 заморожена, поэтому на canonical ожидаем честный RED там, где указано
  «ожидание на canonical: структурно FAIL».
- **OBSERVE** — фиксация текущего поведения canonical как наблюдения (решение
  Вадима E4: «текущие тесты PLC-поведения остаются как наблюдение»), не oracle.
- **PENDING-V14** — oracle только из v1.4; станет READY после подтверждения
  Вадимом статуса документа по этому пункту (вопрос 1 ведущего).
- **BLOCKED** — нужен ответ (номер вопроса указан).

Общие условия (для всех, если не сказано иное):
- R0 = «здоровые» сырые входы стенда как в `test/helpers/rnd-down-source.js` (`raw`):
  in_ES_NC_1/2=TRUE, in_InterLock_NC_1/2=TRUE, in_LV/HV_Connector_Interlock=TRUE,
  in_Mentee_EStop=FALSE, in_Estop_PLC=FALSE, in_False_SI2_CH8=FALSE, обе кнопки
  FALSE, in_Door_Monitor=TRUE, inPLC_RnD_Mode/_2=FALSE (код 00),
  inPLC_BypassC1C2=FALSE, STO/Healthy FBK по модели, контакторные FBK следуют
  командам по существующей feedback-модели стенда. Скан 1 мс. Отличия указаны.
- «Устойчивый Safe/R&D/Run» = достигнут реальными producers физическим жестом
  при коде 00 (D-…/BTN: release 2 с, BOTH 1 с от второй ≤250 мс, green 0,5 с),
  после чего обе кнопки отпущены ≥ 2000 мс. Не инъекция внутренних Set.
- Код «XY» = (inPLC_RnD_Mode, inPLC_RnD_Mode_2).
- Числового параметра для PLC-запросов не утверждено → границы q−1/q/q+1 по
  времени неприменимы; используются скан-границы (тот же скан N, N−1, N+1) для
  приоритетов и окно наблюдения 2500 мс (как в current-rnd-down-no-reenergy)
  для «отсутствия реакции». Окно — длительность наблюдения, не требование.
- «Повышение» наблюдается на реальных точках: b_Step12_Set, b_Set_HV_C2_1,
  b_Set_Transition_3, Set-входы FBRs1/FBRs2, out_LV_C1, out_HV_C2, STO-выходы
  (снятие STO), out_Step12/outPLC_RnD/out_Step3/out_Safety_Armed.

## READY

### C01 — удерживаемый код 10 не повторяет Safe→R&D (MOD-003; BOOT-002 смежно)
- Исходно: устойчивый R&D (достигнут физически при коде 00), C2 OFF.
- t0: код 00→10, держится до конца. t0+500: зелёная ON; t0+1100: OFF
  (≥0,5 с → R&D→Safe по D-LV-OFF-COMPLETE до in_LV_C1_FBK=FALSE).
- Ожидание: после установления Safe (Step1) в течение 2500 мс — нет b_Step12_Set,
  out_LV_C1 остаётся FALSE, Step12/R&D не устанавливаются, Unlock FALSE.
- Запрещено: любое повышение из неизменного кода 10.
- Источник: SPEC §20 MOD-003 «каждый шаг вверх требует нового события, а не
  удерживаемого PLC уровня»; SCENARIO_DECISIONS «Дополнение no-up oracle»;
  QP «удерживаемый mode-code не является повторяющимся новым событием» (QP на
  пересмотре, MOD-003 — действующий норматив).
- Ожидание на canonical: структурно FAIL (N2/FBAnd91 — уровень 10 ∧ Step1).
- Аварийное сочетание: тот же сценарий с in_Estop_PLC TRUE на 100 мс в окне
  наблюдения и Restart зелёной — после Restart повышения нет (см. C06).

### C02 — удерживаемый код 11 не повторяет R&D→Run (MOD-003, MOD-002)
- Исходно: устойчивый Run (физически, код 00).
- t0: код 00→11, держится. (Реакция в Run на 11 — см. C12 OBSERVE.)
- Затем любой завершённый возврат в R&D (физическая зелёная 0,5 с → полная
  текущая последовательность до in_HV_C2_FBK=FALSE и R&D).
- Ожидание: после установления R&D 2500 мс — нет b_Set_HV_C2_1, out_HV_C2 FALSE,
  STO не снимается, Step3 не устанавливается.
- Источник: MOD-003, SPEC §15 (одна команда на попытку), решение Вадима №4.
- Ожидание на canonical: структурно FAIL (N12/FBAnd10 — уровень).

### C03 — код при старте не создаёт повышения (MOD-003, BOOT-001)
- Исходно: первый скан группы; код 10 (вариант A) / 11 (вариант B) / 01 (C)
  уже установлен; остальное R0.
- Ожидание за 2500 мс после установления Safe: нет повышения (A,B,C); Run не
  восстанавливается (B — BOOT-001).
- Источник: MOD-003; BOOT-001; SPEC §17 «После рестарта система не
  восстанавливает Run автоматически».
- Предел: ограничения адаптера BOOT (UNSUPPORTED_GROUP_LIFECYCLE) — допустим NV
  с явной причиной, не PASS.

### C04 — PLC UP из Safe отклоняется при неполной паре InterLock (CVR-004, MOD-007, EMG-003)
- Исходно: устойчивый Safe, код 00. Варианты: (a) NC1 FALSE, NC2 TRUE;
  (b) NC1 TRUE, NC2 FALSE; (c) оба FALSE; каждый при Door TRUE и Door FALSE;
  (d) LV connector FALSE; (e) HV connector FALSE (оба NC TRUE).
- t0−100: нарушение установлено. t0: код 00→10, держится.
- Ожидание за 2500 мс: Step1 сохраняется, Step12/R&D не устанавливаются,
  b_Step12_Set FALSE, out_LV_C1 FALSE, Unlock FALSE. Для (d),(e): fault не
  фиксируется (EMG-003 «без fault»). Для (a)–(c) классификация fault/Emergency
  в Safe — вне этого критерия (см. Q-E4V14-09), проверяется только «нет повышения».
- t1 = t0+2500: нарушение снято (NC/connector TRUE), код 10 держится.
- Ожидание ещё 2500 мс: повышения нет (отклонённый запрос не исполняется позже).
- Положительный контроль (pair-control): тот же сценарий при полном R0 — см.
  C12 OBSERVE (позитив PLC Safe→R&D не oracle, E4 заморожен).
- Источник: CVR-004 closure («оба up маршрута … каждыйNCfalse negative»),
  DOOR_INTERLOCK_REQUIREMENT.md таблица, SPEC §5 пп7,11; SCENARIO_DECISIONS
  «Safe/R&D, крышка открыта, новый запрос вверх — состояние не меняется»;
  EMG-003; MOD-003 (удерживаемый уровень не новое событие).
- Ожидание на canonical: структурно — смена шага на Step12 возможна
  (N2/FBAnd91 без InterLock), энергия блокирована FBAndLvCurrentPermit;
  вторая фаза (после восстановления) — структурно FAIL (уровень).
- Скан-граница: нарушение снимается в скане N, код 10 появляется в N−1 / N / N+1 —
  во всех трёх случаях повышения нет до нового события.

### C05 — PLC UP из R&D отклоняется при неполной паре InterLock (CVR-004, MOD-002, EMG-011)
- Исходно: устойчивый R&D, код 00. Варианты (a)–(c) как C04, Door TRUE/FALSE.
- t0: нарушение; t0 (тот же скан) / t0+1 / t0−1: код 00→11.
- Ожидание: нет b_Set_HV_C2_1, out_HV_C2 FALSE, STO не снимается, Step3 нет.
  Реакция Emergency на потерю NC после выхода из Safe — по EMG-002, здесь не
  утверждается (Q-E4V14-09).
- Источник: CVR-004, SPEC §7, EMG-011 «аварийные условия имеют приоритет над
  повышением».

### C06 — авария имеет приоритет над PLC UP; после восстановления нет авто-повышения (EMG-001, EMG-011, EMG-006)
- Исходно: устойчивый Safe (A) / устойчивый R&D (B), код 00.
- Источник аварии (по отдельности): in_Estop_PLC TRUE; in_ES_NC_1 FALSE;
  in_ES_NC_2 FALSE; in_Mentee_EStop TRUE.
- Скан-границы: авария в скане N; код UP (A: 10; B: 11) в N−1, N, N+1.
- Ожидание: b_EStop_Ok FALSE с первого скана аварии; ни одного нового
  повышения/снятия STO; Unlock FALSE.
- Далее: причина снята (t+200), код UP держится; без Restart 2500 мс — авария
  сохраняется, повышения нет; затем зелёная ON 300 мс/OFF (Restart FBEstop1) —
  2500 мс после: система только в Safe, повышения нет (код неизменен).
- Источник: SPEC §13 (приоритет), §12 п6 «только Safe, никогда автоматически
  R&D/Run», EMG-001/006/011, MOD-003; решение №12 (зелёная = FBEstop1.Restart —
  как существующая роль; новый жест восстановления — Q-E4V14-01).
- Предел: процедура Emergency→Safe целиком (условия §12 пп3–4) — EMG-006, E2;
  здесь только «нет авто-повышения от PLC-кода».

### C07 — PLC не снимает Emergency (EMG-006)
- Исходно: устойчивый Safe и устойчивый R&D (две ветви), код 00.
- t0: in_Estop_PLC TRUE на 100 мс, затем FALSE. Вариант: in_Mentee_EStop.
- t0+200…t0+2700: последовательность кодов 00→10→11→01→00 по 500 мс,
  inPLC_BypassC1C2 TRUE на 500 мс, in_Door_Monitor переключения; кнопки OFF.
- Ожидание: b_EStop_Ok FALSE весь интервал, out_Estop_OK FALSE, Unlock FALSE,
  ни одного Set C1/C2/STO-release; Emergency не снимается без физического
  восстановления.
- Источник: SPEC §12 «PLC не имеет права отменять защёлкнутый Emergency»,
  EMG-006, SPEC §17 (одиночный PLC-бит), v1.4 §5/§8 #5 (совпадает).
- Ожидание на canonical: Bypass в аварии — permits содержат b_EStop_Ok →
  структурно повышения нет; проверить динамически.

### C08 — никакая комбинация PLC-сигналов не открывает крышку (CVR-001, EMG-007)
- Исходно: устойчивый Safe; устойчивый R&D; устойчивый Run; Emergency.
- Перебор 16 комбинаций (bit1, bit2, Bypass, DoorMonitor), каждая 600 мс,
  синяя и зелёная OFF.
- Ожидание: out_Door_Unlock_Solonoeid FALSE всегда.
- Источник: SPEC §5 п1 «UnlockCover только во время физического удержания
  синей»; CVR-001; SPEC §17; v1.4 §5 (совпадает).
- Ожидание на canonical: структурно PASS (FBAndUnlockHold.AndIn2 = синяя).

### C09 — одиночный PLC-бит Bypass не включает C1/C2 (MOD-007, SPEC §17)
- Исходно: устойчивый Safe, код 00, R0.
- t0: inPLC_BypassC1C2 TRUE, держится 12000 мс (дольше Ton1 10 с), затем FALSE.
- Ожидание: out_LV_C1 и out_HV_C2 FALSE всё время; Step/режим не меняется.
- Варианты: устойчивый R&D (out_HV_C2 FALSE весь интервал).
- Источник: SPEC §17 «Ни один одиночный PLC-бит не может непосредственно
  включить опасную энергию»; MOD-007; v1.4 §5 «PLC can never bypass».
- Ожидание на canonical: структурно FAIL (N1/FBAnd4→5/6→FBOr17/18→SetPermit).
- Зависимость: если Вадим сохранит Bypass как санкционированную сервисную
  функцию (Q-E4V14-07), критерий будет пересмотрен; до ответа действует SPEC §17.
- Границы Ton1 (наблюдение, не oracle): 9999/10000/10001 мс — фиксировать
  момент сброса как OBSERVE.

### C10 — PLC UP в переходной фазе не принимается и не исполняется позже (MOD-004, MOD-003)
- (a) Safe→R&D идёт (Step12 установлен, LV feedback ещё не подтверждён): код
  00→11 в этот момент и держится. Ожидание: нет b_Set_HV_C2_1/out_HV_C2, нет
  снятия STO; после установления R&D 2500 мс — по-прежнему нет (код неизменен).
- (b) Принятый R&D→Run (StartingRun, STO снят по D-STO-LAUNCH): код 10 или 11
  меняется/держится — нет второй ступени, нет повторного Set.
- (c) Идёт Run→R&D (после принятой зелёной): код 11 — нет повышения ни во время,
  ни после установления R&D.
- Источник: MOD-004, SPEC §15 «Любой Transition: новая команда вверх не
  принимается», решение №4 (одна ступень на попытку), MOD-003.
- Ожидание на canonical: (a),(c) структурно FAIL по уровню; (b) проверить.

### C11 — физическая синяя под PLC-кодом: Unlock и повышение не сосуществуют (CVR-005)
- Исходно: устойчивый R&D, R0. Синяя ON (квалифицирована 0,5 с, Unlock TRUE),
  держится. t: код 00→11.
- Ожидание: в любом скане НЕ (Unlock TRUE ∧ (b_Set_HV_C2_1 ∨ out_HV_C2 rise ∨
  снятие STO)). Какая из реакций выигрывает (игнор PLC или снятие Unlock) —
  не утверждается (Q-E4V14-04).
- Источник: CVR-005, SPEC §7 «UnlockCover = FALSE» как предусловие R&D→Run.

## OBSERVE

### C12 — таблица фактических реакций canonical на код × режим
- Для каждого устойчивого режима Safe/R&D/Run и кода 00/01/10/11 (переход из 00,
  держать 3000 мс, затем 00) записать: шаги, b_Step12_Set, b_Set_HV_C2_1,
  b_Set_Transition_3, out_TransitionStep, out_LV_C1, out_HV_C2, STO_DR1/2,
  out_SS1_DR1/2, discharge request, Unlock.
- Структурные предсказания (не oracle): Safe+10 → Safe→R&D; R&D+11 → R&D→Run;
  Run+01 → N6 down; R&D+00 → ничего (ветвь мертва); Run+{01,10,11} → out_SS1
  FALSE; Run+10 → Step3 сохраняется без N6 down; любой режим+11 →
  b_Set_Transition_3.
- Назначение: baseline для пересмотра E4 и для вопросов Q-E4V14-02/03.
