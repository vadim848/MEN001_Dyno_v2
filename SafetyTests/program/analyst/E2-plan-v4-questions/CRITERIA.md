## 1. B4-3 — legacy Bypass в Emergency (S6 после раннего Restart)

### Вывод
Требования однозначно запрещают подачу энергии по Bypass при статусе Emergency. Вопрос Вадиму не нужен.
Вывод для ведущего и архитектора: гейтировать Bypass и выход G10 уже в E2b. Откладывать до E4 нельзя:
- состояние «S6 ∧ EOk TRUE, статус EMG» и выход G10 создаёт сам механизм E2;
- E4-заморозка допускает изменение поведения PLC-входов, «вынужденное другими этапами» (SCENARIO_DECISIONS, раздел E4).
  Здесь оно вынуждено требованием однозначного статуса E2 и EMGREF(2).

Основания:
- **EMG-006 / SPEC §12 пп.3–4, EMG6-01.** Выход Emergency→Safe только при снятой энергии и FBK OFF.
- **SPEC §2, таблица.** Safe = LV выкл., HV выкл. и разряжено, STO.
- **EMG-011 и EMGREF(2).** При Emergency нет ни одного нового повышения энергии.
- **V14-Q16.** Bypass допустим только в устойчивом Safe при закрытой крышке, в любом другом состоянии игнорируется.
- **Q-RC-05 (a)(b).** Bypass, поднятый в Emergency или до рестарта, игнорируется до нового фронта в устойчивом Safe.
  Вход в Config требует «нет Emergency».
- **CFG-001, SCOPE EMG-006.** «Bypass, удерживаемый через Restart, Config не даёт».

Ни одно решение не разрешает энергию при статусе Emergency, в том числе временно до E4.
Факт модели (ревьюер, w7/w9, не oracle):
- R1+E2a и далее: Bypass в S6 при EOk TRUE даёт C1 = C2 = TRUE при статусе EMG;
- при подъёме Bypass в скане отпускания зелёной — 1 скан SAFE с C1 = C2 = TRUE;
- F1 тоже подаёт энергию по Bypass после аварии.

### B43-01 (READY-D) — Bypass при статусе Emergency не подаёт энергию
- **Исходно.** Устойчивый Run по R0, C2_FBK ON, кнопки отпущены ≥ 2000 мс.
  - Событие e: `in_ES_NC_1` FALSE на 100 мс, затем TRUE.
  - Ранний Restart: зелёная нажата на e+120…e+220, отпущена. Аварийная цепь ещё идёт: статус EMG, EOk TRUE (стадия S6).
  - Ожидание 12 000 мс: цепь завершена, C1/C2 OFF, оба FBK OFF, STO активен.
- **События (каждый вариант отдельно):**
  - (a) `inPLC_BypassC1C2` TRUE в b, держится 300 мс и непрерывно 5000 мс, кнопки не трогать;
  - (b) Bypass импульс 1 скан;
  - (c) Bypass TRUE уже до события e, держится всё время;
  - (d) как (a), но `in_ES_NC_1` удерживается FALSE (EOk FALSE);
  - (e) варианты (a)–(c) для Emergency из R&D и из Safe→R&D (любая причина Q-ARCH-01);
  - (f) варианты (a)–(c) после старта группы до первого Restart (BOOT-C).
- **Ожидается в каждом скане ≥ b до Restart:**
  - статус Emergency;
  - `out_LV_C1` = `out_HV_C2` = FALSE, C3/BMS FALSE;
  - STO активен (`STO_DR1/2` FALSE);
  - Unlock FALSE;
  - нет Config, нет Safe/R&D/Run;
  - нет fault (Bypass в Emergency игнорируется без ошибки, Q-RC-05(a)).
- **Запрещено:**
  - любой скан с C1 или C2 TRUE при статусе Emergency;
  - отложенное исполнение Bypass после Restart (см. B43-02).
- **Границы:** b относительно завершения цепи — до C2 OFF (b = момент C2 OFF − 1), b = C2 OFF, b = C2 OFF + 1.
  Энергия в любом из них запрещена; это не таймер, точки нормативны все.
- **Источники:** EMG-011, EMGREF(2), V14-Q16, Q-RC-05(a)(b), CFG-001.

### B43-02 (READY-D) — выход Restart→Safe не создаёт Safe с энергией
- **Исходно** как B43-01 после завершения цепи: S6, EOk TRUE, всё OFF.
- **Событие.** Зелёная нажата на 100 мс в g, отпущена в g_r. Bypass поднимается со смещением δ от g_r,
  δ ∈ {−100 (во время удержания), −1, 0, +1, +2}, и держится 300 мс.
  Отдельно — Bypass TRUE до нажатия зелёной и держится через выход.
- **Ожидается:**
  - ровно один переход статуса EMG→SAFE (EMG6-01);
  - в скане первого SAFE и во всех следующих сканах до принятого UP-жеста или команды:
    - `out_LV_C1` = `out_HV_C2` = FALSE;
    - `in_LV_C1_FBK` = `in_HV_C2_FBK` = FALSE (плант стенда следует командам);
    - STO активен;
  - Config не наступает (CFG-001 — только по новому фронту в устойчивом Safe; Config — E4);
  - удерживаемый через выход Bypass не исполняется и позже (Q-RC-05(a)).
- **Запрещено:**
  - скан SAFE с C1 или C2 TRUE — это и есть 1 скан в w9;
  - скан EMG с C1 или C2 TRUE;
  - SAFE→EMG→SAFE мерцание;
  - выход в R&D/Run/Config.
- **Граница по δ:** все пять точек нормативны (событийная граница, не таймер).
- **Вне критерия (E4, известный класс CFG-02):** фронт Bypass через ≥ 2000 мс после выхода в устойчивом Safe.
  Это вход в Config или legacy Bypass в Safe. В E2 — наблюдение. Справка: w10 — в устойчивом Safe импульса нет.
- **Источники:** EMG-006, SPEC §12 пп.3–4, SPEC §2 (Safe = энергия снята), E2 (однозначный статус), EMG6-01, Q-RC-05.

**Мутации (архитектору, B4-1).** M-E2b-24/25 (G10.AndIn7/8) с одиночной деактивацией не убиваются: Bypass поднимает
C1 и C2 в одном скане. После гейтирования Bypass в Emergency G10.AndIn7/8 могут стать эквивалентными в достижимом
поведении. Убийцу или equivalentBySearch определяет архитектор; B43-02 (δ = 0) — обязательный сценарий.

## 2. ES-06 — память стадии до первого Restart

### Вывод
Память стадии до первого Restart **не нормативна**. Из Q-RC-10 и E2-04 («старт в Emergency») следует требование
к статусу и выходам. Запрет внутренней памяти S1 при статусе Emergency из них не следует.

Обоснование:
1. **Что задают требования.**
   - Q-RC-10: «не активно ни одно основное → Emergency; группа стартует в Emergency».
   - E2-04: «первый скан и далее до EMG6-01 — Emergency».
   - Оба говорят о статусе, а не о составе внутренних памятей.
   - Внутренняя память (b_Step1) в v2 не публикуется в PLC. Статусного выхода Safe нет, есть только `outPLC_RnD`,
     декодер статуса — в E4.
2. **Нет двойного владения (E2).** По PLAN v4 §2.3 STS_SAFE = (S1 ∨ S12) ∧ EOk. Значит, «S1 ∧ ¬EOk» имеет статус EMG.
   Это штатное и достижимое состояние: Emergency, поднятый в устойчивом Safe (g7 не сбрасывает S1). Его выход —
   обычный EMG6-01. Мутант ES-06 при загрузке приводит систему в то же самое достижимое состояние.
3. **Reference.** «Step1 только после Restart» — внутренняя структура reference, а не наблюдаемое действие.
   Наблюдаемая последовательность reference (старт без энергии, Restart → Safe) сохраняется и у мутанта.
4. **Проба аналитика** (`PROBE_ES06.txt`, модель полного стека E2 v4) — сравнение мутанта N3/FBAnd1.AndIn2 с базой:

   | Сценарий | Отличие выходов (C1, C2, STO1/2, Unlock, EOk) и статуса |
   |---|---|
   | загрузка без Restart, ES в норме или нажат | только память S1 |
   | синяя 700 мс | нет (Unlock FALSE в обоих) |
   | Bypass 300 мс | нет |
   | PLC RnD_Mode 300 мс | нет |
   | Restart при нажатом ES | нет |
   | Restart после загрузки (ES в норме / после отпускания ES) | статус SAFE на 1 скан раньше у мутанта, в скане подъёма EOk, при снятой энергии и FBK OFF |
   | далее синяя / BOTH | одинаково |

   Нормативной верхней или нижней временной границы «Restart → статус Safe» нет (EMG6-01, SPEC §12).
   SAFE у мутанта появляется после отпускания зелёной, при EOk TRUE, без энергии. Значит, требование не нарушено.

### ES06-01 (READY-D) — старт группы до первого Restart (наблюдаемые требования)
- **Исходно.** Старт группы по R0, `in_ES_NC_1/2` TRUE. Вариант: `in_ES_NC_1` FALSE с первого скана.
- **События:** без Restart 300 мс; затем по отдельности:
  - синяя 700 мс;
  - BOTH 1100 мс (зелёная = Restart, поэтому BOTH допустим только как событие Restart, см. EMG6-01);
  - Bypass 300 мс;
  - CMD_* / `inPLC_RnD_Mode` 300 мс.
- **Ожидается до EMG6-01 в каждом скане:**
  - статус Emergency;
  - C1, C2, C3, BMS FALSE, STO активен, Unlock FALSE;
  - нет переходов и нет Config.
- **После Restart** (при ES в норме): Safe (EMG6-01), удерживаемые с загрузки Bypass/CMD не исполняются (BOOT-C).
- **Запрещено:** статус Safe/R&D/Run/Config до Restart; энергия; Unlock.
- **Не нормативно:** значение внутренних памятей стадий (b_Step1 и др.) до Restart; момент статуса Safe в пределах
  «после отпускания зелёной при снятой энергии».
- **Источники:** Q-RC-10, E2-04, BOOT-C, EMG6-01, EMGREF(2), Q-ARCH-10 (Unlock в Emergency запрещён).

**Классификация мутации ES-06 (N3/FBAnd1.AndIn2) — ответ на A4-7.** Категория (в): эквивалентна по требованиям.
Довод: мутант переводит загрузку в достижимое штатное состояние «S1 ∧ ¬EOk» (Emergency в Safe), его выход — EMG6-01.
Наблюдаемое отличие — статус SAFE на 1 скан раньше, а этот момент не нормирован.
Предложенный ревьюером убийца «b_Step1 FALSE до Restart» — oracle по внутреннему сигналу. Требованием он не является
и в тестовый пакет как нормативный не вносится. Допустим только как структурная проверка, явно помеченная.
Решение «equivalentBySearch (DERIVED)» оформляет архитектор, со ссылкой на этот раздел и PROBE_ES06.

**Побочное наблюдение (вне 4 вопросов, не oracle).** `PROBE_BOOT_FBK.txt`: после загрузки с удерживаемым
`in_LV_C1_FBK` или `in_HV_C2_FBK` TRUE Restart даёт S1/SAFE. Это так и на F1, и на модели E2 v4.
- EMG6-01 (CRITERIA v2): «Restart при … FBK ON → Emergency».
- Q-V4-02 «В» (новое): FBK ON без команды в устойчивом Safe → SafetyFault + запрет подъёма, не Emergency.
Это E5/E6 (FBK-*, Q-V4-02), не E2. Ведущему — проверить, покрыто ли это FBK-критериями v7. Если нет — отдельный вопрос
о старте с FBK ON. Его не задаю: он не входит в поручение, а v7 ведёт Q-V4-01/02.

## 3. RC-6 — нормативность верхней границы момента Run

### Вывод
Верхняя граница **нормативна** (READY-D), по общему правилу §0: q+1 обязателен, q — наблюдение. Основания:
- **Q-RC-RUNCONF-01 «В».** Run «подтверждается после 0,1 с непрерывно» — подтверждение наступает при выполнении условия.
  Произвольная задержка не допускается. Допуск в 1 скан — семантика TON (§0).
- **Вопрос 68 «Б»** добавляет нижнюю границу («не раньше команда + 500 + 100») и не ослабляет момент подтверждения.

Правило §0 применяется одинаково ко всем таймерам: T_SINGLE, T_BOTH, T_DIS, окно FBK. Для Run оно не особое.
Вопрос Вадиму не нужен: «на 1 скан позже допуска» не меняет поведение безопасности, а правило §0 уже действует
во всех критериях.

### RC-UB (READY-D; принцип для v7, одна формулировка)
- Для каждого порога в цепочке подтверждения Run (и R&D) нормативны q−1 (нет Run / R&D) и q+1 (Run / R&D есть);
  q — наблюдение.
- Цепочка после вопроса 68 состоит из двух порогов: окно 500 мс от команды C2 ON (C1 ON) и 100 мс непрерывно после окна.
  - Если ограничивает только порог 100 мс (условие «норма» пришло после окна), верхняя граница — q+1 этого порога.
  - Если ограничивает окно, допуск складывается по одному скану на каждый порог: Run не позже q_total + 2.
    Здесь q_total = (команда + 500) + 100. Это не новый oracle, а прямое применение §0 к двум последовательным порогам.
    Точную формулу (момент начала 100 мс относительно окна, обозначения c, W, k*) задаёт v7 (`E2-G1-v4`).
- **Согласование с v7.** Если v7 уже задал формулу с иным допуском, действует формула v7. Ведущему — свести в одну
  строку RUN-CONF. Принцип «q+1 нормативен, задержка сверх допуска §0 — FAIL» общий.
- **M-E2a-21** (FBAnd6 после FBTon3, сдвиг на +1 скан, w14) убивается сценарием, где ограничивает только порог 100 мс.
  Пример — RC-5 (iv) из v6: C2_FBK ON с c+1, `in_HV_Faulty_FBK` TRUE до c+2999, FALSE с c+3000.
  - Окно истекло, k = c+3000. По §0 Run обязателен на k+101; у мутанта — k+102 → FAIL.
  - То же даёт RC-6 «граница до Run» и провал HV после окна.
  - Сценарии с ограничивающим окном (FBK и норма с c+1) использовать для нижней границы (мутации окна), а не для M-E2a-21.
- **Источники:** Q-RC-RUNCONF-01 «В», вопрос 68 «Б», Q-V4-01 «Б», CRITERIA v2 §0, CRITERIA_DELTA v6 §1 (RC-5/RC-6).

## 4. REL-01(e) — эпизод потери разрешения, закончившийся до квалификации BOTH

### Вывод
Поведение «отказ без перехода, без fault» критериями задано. Это READY-D: §5.1 / EMG-003 + IL-02 + BTN-001/002, без нового
поведения. Требует уточнения только формулировка REL-01(e): «перекрывающий квалификацию» прочитано ревьюером как
«перекрывающий момент квалификации».
- **SPEC §5.1 / EMG-003:** «в Safe отсутствие connector только блокирует переход вверх без fault; **после восстановления
  требуется новый жест**». Жест, начатый до эпизода и удерживаемый через восстановление, — не новый жест после
  восстановления.
- **IL-02 (CRITERIA v2):** «после восстановления NC … **продолжающееся удержание не исполняется**» (R&D, крышка).
- **Q-REL-AFTER-PERMIT «А»** касается паузы при отпущенных кнопках: эпизод не сбрасывает отсчёт 2 с. «Разрешение в
  момент принятия» — необходимое, но не достаточное условие. Противоречия нет.
- **SPEC §3.1 п.9, п.11** (одна кнопка удержана; 11→10→11) задают только поведение кнопок, эпизодов разрешения
  не касаются.
- **BTN-001/002, §3.1 п.10.** Новая попытка — только после отпускания обеих и полного фильтра 2000 мс.

### REL01-e2 (READY-D) — эпизод во время удержания BOTH
- **Исходно.** Устойчивый Safe по R0, кнопки отпущены > 2000 мс, нет SafetyFault.
  Для варианта R&D — устойчивый R&D, NC1/NC2 TRUE.
- **Событие.** Первая кнопка в f, вторая в p (p − f ≤ 250), обе удерживаются 1100 мс; Q = p + 1000 — порог T_BOTH.
  Эпизод разрешения [s, r): r — первый скан восстановления.
  - Safe: `in_LV_Connector_Interlock`, `in_HV_Connector_Interlock` или оба FALSE.
  - R&D (R&D→Run): NC1, NC2 или оба FALSE.

| Эпизод | Ожидается |
|---|---|
| [p+500, p+999) (вопрос ревьюера), [p+1, p+2), [p+500, p+501) (1 скан), [f, p+300), [f−300, f+10) | отказ: нет Safe→R&D (R&D→Run), C1 (C2) не включается, STO не снимается, нет fault и нет Emergency |
| s ≤ Q−1 и r > Q (покрывает порог) | отказ (REL-01(e) в исходном виде) |
| восстановление до первого нажатия: r ≤ f−1 | принято при прочих разрешениях (REL-01(a)/(b)/(c), Q-REL-AFTER-PERMIT) |
| r = f | наблюдение |
