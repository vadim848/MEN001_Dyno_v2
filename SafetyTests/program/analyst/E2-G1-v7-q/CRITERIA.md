## 1. Норма: «новая квалифицированная зелёная» для abort (READY, прямо из решений Вадима)

### Ответ
Зелёная, нажатая через 11…500 мс после отпускания BOTH, **не является** новой квалифицированной зелёной. Abort StartingRun (V14-Q12) и abort Safe→R&D (V14-Q13) кнопкой выполняет только **новая попытка**:
1. обе кнопки непрерывно FALSE полный T_RELEASE 2000 мс, считая от rb;
2. затем одна зелёная непрерывно T_SINGLE 500 мс.

Это не решение команды и не вопрос Вадиму: норма однозначно следует из решений Вадима.

### Источники
| Источник | Что говорит |
|---|---|
| D-STARTINGRUN-GREEN-DOWN (Вадим 2026-10-20) | «новая попытка green500 **после полной очистки** прерывает запуск»; «это новая попытка, а не late-second той же принятой команды» |
| V14-Q12 «А» | CMD_RUN_TO_R&D в StartingRun «действует **как зелёная по D-STARTINGRUN-GREEN-DOWN**» — значит, зелёная там именно в смысле D-STARTINGRUN-GREEN-DOWN |
| V14-Q13 «А» | «**новая** квалифицированная зелёная (0,5 с)»; «новый UP — только новым жестом» |
| SPEC §3.1 п.1, п.2, п.10; BTN-001, BTN-002 | после каждой команды — полное отпускание обеих и полный фильтр; нажатие до конца фильтра аннулирует очистку, удерживаемая кнопка не распознаётся |
| Подтверждение Вадима 2026-10-21 п.9 | 2 с непрерывного отпускания обеих перед новой попыткой |
| п.11 там же; SPEC §3.1 п.9, п.11; BTN-007 | недействительная попытка ничего не меняет; для новой — обе отпущены 2 с. Остаток BOTH (одна кнопка удержана, вторая отпущена) ничего не делает; 11→10→11 не создаёт одиночную |
| REQ-CONSOLIDATION STP-E(1), PLC-09(b) (READY) | «новая зелёная 500 мс после полной очистки» / «новая зелёная 500 мс» |

### Про Q-RC-07
Q-RC-07 (зелёная вниз при активной SafetyFault и квитирует, и спускает) этой нормы не меняет:
- речь там тоже о квалифицированной зелёной 0,5 с, то есть о новой попытке после полной очистки;
- в FBK-05/06 при принятом подъёме SafetyFault до истечения окна нет.

### Граница очистки (как BTN-001 / K3-ACK, E2-G1-v5-k3)
| Фронт зелёной g0 | Норма |
|---|---|
| ≤ rb+1999 | **недействительна**: abort нет ни в одном скане, при любом удержании (BTN-002). После её отпускания нужны новые полные 2 с |
| rb+2000 | наблюдение (T_RELEASE не «включительно»; §0) |
| ≥ rb+2001 | действительная новая попытка: при удержании ≥ 501 мс — abort по §3.4 |

### Запрещено
- abort, спуск или SafetyFault от зелёной, нажатой в [rb, rb+1999];
- abort от остатка BOTH: синяя отпущена, зелёная продолжает удерживаться с жеста BOTH (п.9, п.11) — при любой длительности;
- «отложенное» исполнение недействительной зелёной после конца очистки или после её отпускания;
- отсчёт 2 с от p, Q или u вместо rb.

## 2. Достижимость точек FBK-05/06 §5 кнопкой

§5 (E2-plan-v5-questions) проверяет Q-V7-03: окно 500 мс истекает, когда abort уже идёт (a_b < w). **Кнопкой это недостижимо ни при какой паузе.**

| Ограничение | Величина | Источник |
|---|---|---|
| Самое раннее отпускание BOTH | rb ≥ Q+1 | BTN-006 (раньше Q жест не квалифицирован) |
| Конец окна | w = u+500 ≤ Q+900 | TD-06 (u ≤ Q+400) |
| Самый ранний фронт действительной зелёной | g0 ≥ rb+2001 ≥ Q+2002 | §1 |
| Самый ранний abort от кнопки | g0+500 ≥ Q+2502 > w (запас ≥ 1600 мс) | BTN-003 |

- Даже без очистки зелёная с фронтом в u+a_b (a_b ≥ 1) квалифицируется в u+a_b+500 > w. Значит, и нынешние тесты v7 abort до w не создают.
- Зелёная, нажатая до u, — часть жеста BOTH (остаток, п.9) или делает жест недействительным; abort она не даёт.
- Поправка к HANDOFF_v7: «ближайшая ~u+2000» — это **фронт** зелёной. Сам abort — не раньше ≈ u+2500.

**Вывод:**
- точки a_b ∈ {u+10, u+300, u+499} и {u1+10, u1+300} кнопкой из нормы **исключаются**;
- Q-V7-03 как различающий тест возможен только с фронтом CMD_* (§3.1);
- abort другой причиной (потеря LV Healthy в StartingRun, Q-ARCH-03) Q-V7-03 не различает: там SafetyFault ставится и без окна (Q-ARCH-05, одна память по 66(a)).

## 3. FBK-05/06 §5 — новая редакция (заменяет §5 E2-plan-v5-questions)

### 3.1 FBK-05/06-CMD — Q-V7-03 при abort командой PLC — **BLOCKED-E4**

**Исходно:**
- (05) принят R&D→Run, C2 ON в u;
- (06) принят Safe→R&D, C1 ON в u1;
- обе кнопки FALSE с rb ≤ a_b−1 (иначе фронт игнорируется по V14-Q14).

**Событие:** фронт `CMD_RUN_TO_R&D` (05, PLC-09(a)) / `CMD_R&D_TO_SAFE` (06, PLC-09(b)) в a_b:
- для 05: a_b ∈ {u+10, u+300, u+499};
- для 06: a_b ∈ {u1+10, u1+300, u1+499};
- FBK так и не ON; вариант: FBK ON с u+1, FALSE с u+200.

**Ожидается:** без изменений против прежнего §5:
- SafetyFault не позже w+1 (NV до символа, A8);
- последовательность abort по сканам совпадает с тем же abort при FBK ON;
- нет Emergency.

**Почему BLOCKED:**
- E4 заморожен до новой документации Вадима (AGENTS, SCENARIO_DECISIONS «E4»);
- сигналов CMD_* в интерфейсе нет.

Вопрос Вадиму не нужен: поведение задано (Q-V7-03 «А», V14-Q12/Q13). Ждёт только этапа E4.

### 3.2 FBK-05/06-W — истечение окна при недействительной зелёной — READY (E6)

Это замена нынешних тестов `current-e2d-fbk-window-abort` (стимул сохраняется, меняется oracle).

**Исходно:** как в тестах v7:
- (05) R&D → BOTH 1000 мс от p, rb = Q+2, C2 ON в u;
- (06) Safe → BOTH, C1 ON в u1.

**Событие:**
- FBK «never» или «pulse» (ON u+1…u+199, затем FALSE);
- зелёная 600 мс с фронтом g0 = u+a_b, a_b ∈ {10, 300, 499} (по §1 недействительна).

**Ожидается:** дифференциально против трассы X0 — те же входы без зелёной:
- откат по окну:
  - (05) WDG-03 / Q-RC-12: последовательность abort StartingRun + SafetyFault;
  - (06) WDG-01: откат в Safe + SafetyFault;
- начало отката по окну: не позже w+1 (E2-G1-v4/CRITERIA_DELTA_v7 §4.0: «FBK FALSE во всех трёх сканах → откат E6-Q1 … Начало отката не позже w+1»);
- выходы STO / Discharge / C1 / C2 и статусы X совпадают с X0 по сканам в [u, w+3000 + T_DIS];
- SafetyFault TRUE не позже w+1 (NV до символа, A8), как в X0;
- нет Emergency (Q-V4-01: провал в окне — не авария);
- в pulse-варианте провал FBK в u+200 Emergency не даёт.

**Запрещено:**
- любое отличие X от X0, вызванное зелёной (более ранний abort, иной порядок, «abort» вместо отката без SafetyFault);
- отсутствие SafetyFault.

**Предел:** нарушение §1 этот тест не различает — ошибочно принятая зелёная квалифицировалась бы в ≥ u+510, уже после начала отката. Различающий тест — §3.3.

### 3.3 FBK-05/06-NEG — недействительная зелёная не прерывает удерживаемый переход — READY (различающий для §1)

> **Пометка 2026-10-22 (E2-G1-v8-r §1, ревью G1 v8 N19):** формулировки «статус StartingRun (не R&D, не Run)»
> и «статус Safe→R&D (не Safe, не R&D)» в этом разделе и в §3.2/§3.4 **заменены**. Основное состояние в StartingRun — R&D,
> в Safe→R&D — Safe (SPEC §14). Фазу наблюдать по TD-14, конец abort — R_end. Остальное содержание §3 в силе.

**Исходно:**
- (05) R&D; `in_HV_Faulty_FBK` TRUE с момента до жеста. StartingRun удерживается: Run не подтверждается без HV-нормы, в пределах 30 с (Q-RC-RUNCONF-01, WDG-03);
- (06) Safe; `in_LV_Faulty_FBK` TRUE с момента до C1 ON. Safe→R&D удерживается (WDG-02, вопрос 66(b));
- BOTH p…Q+1, rb = Q+2; FBK по модели стенда (ON).

**События** (зелёная одна, синяя FALSE):

| Вариант | Фронт g0 | Удержание | Повтор |
|---|---|---|---|
| (a) | rb+10, rb+300, rb+1999 | 600 мс | — |
| (b) | rb+1999 | до rb+3000 (через «бывший» момент rb+2000+500) | — |
| (c) | rb+300 | 600 мс | после отпускания в g0+600 новая зелёная в g0+600+1999 на 600 мс — тоже недействительна (п.1: нужны новые полные 2 с) |

**Ожидается** в каждом скане [g0, h−1]; h = max(конец последней зелёной, rb+3500) + 1000 — скан снятия Faulty:
- (05) STO снят, C2 ON, SS1 не выдан, Discharge не выдан (снят принятием, вопрос 73), статус StartingRun (не R&D, не Run);
- (06) C1 ON, `out_LV_Discharge_Request` FALSE (TD-01), статус Safe→R&D (не Safe, не R&D);
- SafetyFault FALSE, нет Emergency.

Затем Faulty FALSE с h:
- (05) Run по RUN-CONF-T: K = max(k, u+500), здесь K = h; Run нет ≤ h+99, есть на h+101;
- (06) R&D по RND-CONF-T так же.

**Запрещено:**
- abort / спуск / SafetyFault от зелёной;
- после h: R&D→Safe или Run→R&D от прежней зелёной (отложенное исполнение);
- Emergency.

**Источник:** §1; WDG-02, Q-RC-RUNCONF-01, RUN-CONF-T / RND-CONF-T (TD-02).

### 3.4 FBK-05/06-POS — действительный abort кнопкой после полной очистки — READY-D (база FBK-05/06 и STP-006)

**Исходно:** как §3.3 — переход удерживается Faulty TRUE, FBK ON, rb = Q+2.

**Событие:** зелёная одна, g0 ∈ {rb+2001 (q+1, норма), rb+2000 (наблюдение), rb+5000}:
- удержание 600 мс;
- вариант: удержание 499 мс → abort нет (BTN-003, q−1).

Обозначение: a — скан квалификации T_SINGLE; g0+500 — наблюдение (q), a ≤ g0+501.

**Ожидается** (05, STP-E / V14-Q12 / D-STARTINGRUN-NO-COAST):

| Что | Окно |
|---|---|
| Признаков abort нет | каждый скан [g0, g0+499] |
| STO активен | не позже a+1 ⇒ не позже g0+502 |
| Discharge | не позже a+2 ⇒ не позже g0+503; держится уровнем до следующего принятого подъёма (Q-V7-01 «Г») |
| SS1 и выбег 5 с | нет |
| C2 OFF | не раньше t_d + T_DIS |
| R&D | после C2_FBK OFF |
| LV C1 | остаётся ON, R&D→Safe нет (E2-01) |

После R&D снять HV Faulty (FALSE):
- Run нет, C2 повторно не ON, STO не снимается — в течение ≥ 3000 мс («не возобновляется»).

**Ожидается** (06, V14-Q13 / PLC-09(b) / D-LV-OFF-COMPLETE):
- признаков abort нет в [g0, g0+499];
- C1 OFF после a (точный скан — наблюдение; PLC-09(b) не задаёт скан);
- далее C1_FBK OFF → Safe;
- LV Discharge — по TD-01 (если входит в порядок спуска);
- после Safe снять LV Faulty: R&D нет, C1 повторно не ON ≥ 3000 мс.

**Оба случая:**
- нет Emergency;
- SafetyFault от самого abort не требуется и не запрещается — наблюдение (PLC-09(b) «не задано»; Q-RC-RUNCONF-01 — HV до Run не потеря).

**Аварийные сочетания (FBK-05/06 v4, без изменений; окно давно истекло):**
- (05) C2_FBK FALSE после a, до команды C2 OFF → Emergency (Q-RC-19, EMGREF-RUN). В скане команды OFF и после — ожидаемый OFF, не авария;
- (06) C1_FBK FALSE после a, до команды C1 OFF → Emergency. Промежуток может быть 0–1 скан — тогда наблюдение (FBK-06 v4);
- NC1/NC2 FALSE во время abort StartingRun → Emergency (IL-05d(1));
- EStop / in_Estop_PLC → Emergency (V14-Q9).
