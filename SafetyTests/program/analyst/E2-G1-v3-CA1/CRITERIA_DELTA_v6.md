## 2. Статус Emergency в Safe (EMG-001, EMG-006; EMG6-01) — граница момента

Разбор:
- §0.1 v4 L2 перечисляет состояния, «где задана общая цепь». Safe не перечислен намеренно: в Safe энергии нет
  (C1/C2/C3/BMS OFF, STO и SS1 активны). Ни одного Del-выхода цепи и Imm-выхода энергии менять нечего (все n/a).
- Буквальный L2 в Safe невыполним не только из-за недостижимой базы. Reference и canonical в Safe не выдают
  LV/HV discharge (профиль null), а L2 Imm/Del потребовал бы их «как в Run» (+3 / +7008). Значит, L2 к Safe
  неприменим по существу.
- Safe — сохраняемое поведение reference: ни одно решение не меняет реакцию Safe на аварийные входы, кроме Unlock
  (см. ниже). Поэтому якорь — reference в том же состоянии, по образцу L3.

**L3-Safe (новое, READY-D; EMG6-01, решение №12, SPEC §12–13, правило L v4 §0.1 L3/L4).**
- Исходно: устойчивый Safe по реальному lifecycle (старт → Emergency → Restart → Safe), кнопки отпущены ≥ 2000 мс,
  R0, нет SafetyFault.
- Событие: `in_Estop_PLC` TRUE в e, удерживается (timeline тестировщика).
- Ожидается:
  - статус Emergency не позже **ref_Safe + 1**, где ref_Safe — смещение первого скана Emergency на reference 4495a1f
    в Safe, измеренное тем же helper'ом (число и SHA закрепить в тесте; проба аналитика: ref_Safe = +1, т.е.
    граница +2). STS_SAFE допустим только в сканах e … e+τ−1;
  - защёлка до Restart, EMGREF(2) в каждом скане ≥ e, Restart → только Safe (без изменений);
  - энергетические выходы остаются в цели (п.4 v5: n/a — «остаются в цели в каждом скане ≥ e»);
  - L4 выполняется тривиально (изменяющихся выходов цепи нет).
- Не применяется в Safe: L2 (ни для статуса, ни для выходов). LV/HV discharge в Safe — наблюдение
  (не требуется и не запрещено; reference не выдаёт).
- Прочие причины в Safe (ES_NC_1/2, Mentee): L1 против `in_Estop_PLC` в Safe (без изменений). Connector в Safe —
  EMG-003 (не авария).
- Unlock в Safe при удерживаемой синей (вариант, если тестируется): reference 4495a1f держит Unlock TRUE в Emergency
  (FBRs1 зависит только от b_Step1, проба `PROBE_UNLOCK.txt`). Это намеренно изменено решением Вадима
  Q-ARCH-10 («в Run, Config и Emergency Unlock запрещён») и EMGREF(2). Нормативно: Unlock FALSE в каждом скане со
  статусом Emergency и не позже τ_R по L1 для причин ≠ `in_Estop_PLC`. Якорь reference для Unlock не применяется.
- Запрещено: статус позже ref_Safe+1; любое повышение энергии, Unlock в Emergency; выход из защёлки кроме Restart.
- Справка (не oracle): canonical F1 в Safe тоже даёт статус +1 (`PROBE_RESULTS.json`), `out_EStop_Status` +0,
  `b_EStop_Ok` +1. Тест «EMG6-01 EMGREF in_Estop_PLC TRUE in Safe» после перевода на L3-Safe исполним на canonical.
  Его прежний RED был RED покрытия (база L2), а не дефектом.

## 3. SS1 при Emergency (m-1; EMG-001, EMG-011, EMG-006)

Разбор:
- CRITERIA v2 EMGREF-RUN: «порядок и моменты — как у `in_Estop_PLC` в устойчивом Run». Q-ARCH-01: «существующие
  тайминги аварийной цепи не менять». v4 §0.1 не включил `out_SS1_DR1/2` в списки Imm/Del — это пропуск аналитика.
- Reference 4495a1f, `in_Estop_PLC` в устойчивом Run (проба, тот же helper): `out_SS1_DR1/2` TRUE → FALSE на **+3**
  (SS1 запрошен), остаются FALSE до конца защёлки; STO на +7006. Полярность: TRUE в Run, FALSE в Safe, то есть
  FALSE = SS1 запрошен (как STO: TRUE = снят).
- IL-03 (CRITERIA v2): «ожидание SS1 2 с как условие защёлки» запрещено. Статус не ждёт SS1 — это уже покрыто L4/L3.

**SS1-EMG (новое, READY-D).**
- `out_SS1_DR1`, `out_SS1_DR2` — **Imm-выходы** правила L с целью FALSE (SS1 запрошен):
  - L3 (`in_Estop_PLC` в устойчивом Run): ≤ ref+1 (ref = +3 → ≤ +4, число закрепить в тесте вместе с REF_RUN_PLC);
  - L1 (прочие причины): ≤ τ_R в той же фазе;
  - L2 (`in_Estop_PLC` в StartingRun и прочих фазах, где SS1 до e снят): ≤ τ_Run+1;
  - EMG-RD-L п.3/п.4: где SS1 уже запрошен до e (Run→R&D после t_a, Safe, R&D) — «n/a», остаётся FALSE в каждом
    скане ≥ e.
- Инвариант (к EMGREF(2)): нет снятия SS1 (FALSE→TRUE) ни в одном скане ≥ e до Restart. Основание — EMGREF(2)
  «нет снятия STO» и сохраняемая reference-цепь (SS1 держится до конца защёлки). READY-D.
- L4: статус Emergency не позже первого изменения SS1 (SS1 входит в «аварийные выходы» L4).
- Запрещено: SS1 позже ref+1 в Run; повторное снятие SS1 после e; ожидание SS1 2 с как условие статуса/защёлки.
- Не нормируется: `outPLC_STO_*` и `b_EStop_Ok` — остаются diagnostic (статус для PLC — E4/E5).
- Пределы: в Q-T3-1 «А» SS1 не упомянут. Для фаз, где SS1 до e снят и нормальная последовательность его не
  трогает, действует правило L без сужения.

## 4. N=u ветка (ii) дизъюнкции IL-02/IL-05a — граница STO/C2 (EMG-002, CVR-006, EMG-006)

Разбор:
- Эталон «`in_Estop_PLC` в u» вырожден: `in_Estop_PLC` сам запрещает UP (F1 GATE_001, reference FBAnd1), в эталоне
  нет снятия STO. Профиль от u−1 даёт n/a для STO/C2, и момент их возврата ничем не ограничен (N4 ревью).
- Ветка (ii) по определению — принятый запуск, за которым следует потеря крышки в StartingRun (Q-RC-03(a) «Б»).
  Крышка в (ii) потеряна не позже, чем в IL-05a с c = a+1, где a — первый скан снятия. Поэтому реакция в (ii)
  должна быть не медленнее IL-05a c = a+1. Цепь не может стартовать раньше события u (тайминги цепи не
  сокращаются, Q-ARCH-01; L1 — опережение не более 1 скана).

**N=u (ii) — граница (READY-D; Q-RC-03(a), Q-ARCH-01, IL-05a, правило L1).**
- Обозначения в трассе X (NC FALSE с u):
  - a — первый скан ≥ u, где снят STO любого привода или C2 ON;
  - R — эталонная трасса с той же базой R&D и тем же жестом BOTH, NC TRUE. В R a_R — первый скан снятия
    STO/C2 ON; `in_Estop_PLC` TRUE с c_R = a_R+1 (StartingRun уже установлен, эталон не вырожден, как IL-05a c=u+1);
  - d_R(o) = τ_R(o) − c_R — смещение выхода o в R.
- Ожидается для Del-выходов o ∈ {STO_DR1/2 активен, `out_HV_C2` OFF, `out_HV_Discharge_Request`, `out_LV_C1` OFF},
  в абсолютных сканах X:
  - **u + d_R(o) − 1 ≤ τ_X(o) ≤ a + 1 + d_R(o)**;
  - верхняя граница — не медленнее IL-05a c = a+1, нижняя — не раньше цепи от события u с допуском L1;
  - STO и C2 мерить как первый скан ≥ a, где выход вернулся в аварийную цель (STO активен, C2 OFF), а не от u−1.
- Imm-выходы (статус Emergency, C3/BMS OFF, LV discharge, SS1, Unlock FALSE): τ_X(o) ≤ a + 1 + d_R(o) (без нижней
  границы); L4.
- Повышения энергии в (ii) допустимы только как действия самого принятия: в сканах a и a+1 (STO/C2 одного
  принятия). В скане ≥ a+2 любое новое повышение (повторное снятие STO после возврата, повторный C2 ON, C1/C3/BMS ON,
  снятие SS1) — FAIL (EMGREF(2)).
- Без изменений: Run ни в одном скане ≥ u, защёлка, EMGREF(2) после a+1, HV discharge выполнен, Restart → только
  Safe; исход (i) — как v4 §C.
- Запрещено: STO снят или C2 ON дольше a + 1 + d_R(o); возврат STO раньше u + d_R − 1 (укороченная цепь,
  как L1 «опережение ≥ 2 FAIL»); смешанный исход (STO снят без Emergency).
- Справка: на reference ветка неисполнима (нет R&D). На canonical (raw-false) R&D недостижим, поэтому до
  кандидата это RED покрытия.

## 5. Момент смены статуса Run → Emergency (N3; EMG-001, EMG-011, MOD-006)

Подтверждение аналитика. Решения Вадима не задают скан, норматив — правило L (v4 §0.1). Абсолютного «≤ e+1»
и «тот же скан» нет (v4 Т3).
- **Устойчивый Run, `in_Estop_PLC`:** L3. Первый скан статуса Emergency τ ≤ ref+1. Reference 4495a1f (проба
  ревьюера и аналитика): STS_RUN в скане e (смещение 0), STS_EMG с +1 (REF_RUN_PLC.status = 1) → граница **+2**.
- **Прочие причины в Run:** L1, τ_X(status) ≤ τ_R(status) той же трассы-эталона.
- **Run→R&D, abort, откаты, защитные спуски:** статус — Imm, нормальная последовательность его не задаёт
  (v5 п.3) → L1/L2 без сужения; Q-T3-1 «А» статус не меняет.
- **Правило для STS_RUN:**
  - если в скане e−1 статус Run — STS_RUN допустим только в сканах e … τ−1, где τ ограничен L1–L4. С первого
    скана Emergency и до Restart STS_RUN нет ни в одном скане (EMGREF(1), E2-01);
  - если в скане e−1 статус не Run (StartingRun, откаты, abort) — STS_RUN нет ни в одном скане ≥ e
    (IL-05a, FBK-03, RC-7: «Run не подтверждается»). Граница e = r (скан подтверждения Run) — наблюдение.
- Память стадий (`b_Step3` и т.п.) — не oracle момента. Проверяется только статус и E2-01 на точках наблюдения
  кандидата. На reference в Run b_Step3 держится до +2 (b_Step3∧b_Step4 на +2), поэтому строка e2-emergency.js:118
  ложна на reference по обеим частям.
- **Тестировщику (N3):** заменить проверку строки 118 правилом выше и подтвердить, что reference 4495a1f проходит
  (L3 и правило STS_RUN).

## 6. EMG-RD-L сужение по Q-T3-1 «А» (к v5 §2; EMG-001/002/004/011, STP-A/B, MOD-002)

Новый прямой ответ Вадима (SCENARIO_DECISIONS Q-T3-1 «А», 89d561c7…): во время принятого спуска (Run→R&D
SS1/выбег/разряд; abort StartingRun; откат WDG-03; STP-G/H; откат Config; R&D→Safe) запланированные шаги
выполняются не позже нормальных моментов; «момент = min(нормальный момент спуска, момент общей аварийной цепи
от события)»; авария только ускоряет.

- R&D→Safe: C1 OFF = min(нормальный момент MOD5-01, e + смещение C1 цепи); окно [m, m+1].
- q_N — только нормативно (STP-A/B), не из no-event трассы (v5, N6 ревью).
- BLOCKED Q-T3-1 снят. Статус EMG-RD-L: READY.
