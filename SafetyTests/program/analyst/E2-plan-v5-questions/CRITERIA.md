## 1. DIS-HOLD — удержание и снятие запросов разряда (R5-1, N1(d))

### Факты reference и F1 (справка)
- **Reference 4495a1f.** `out_HV_Discharge_Request` = N1/FBRs7, `out_LV_Discharge_Request` = N1/FBRs5.
  - Оба сбрасываются только в Network5/FBDecouple2: DecOut1 → `b_Reset_HV_Discharg_Req`, DecOut3 → `b_Reset_LV_Discharge_Req`.
  - Порядок в reference: Step2 ∧ EOk → C1 и C2 ON → TON 0,1 с → TON 5 с → FBAnd3 (Healthy) → сброс обоих запросов → через 0,2 с снятие STO → через 0,2 с Run.
  - Значит, в reference запрос снимается при подъёме, после включения контакторов, но **до** снятия STO. Иных сбросов нет.
- **F1.** Сброс HV — от N12/FBAnd6 (≈ u+101), сброс LV — от N11/FBAnd4 (≈ u1+100).
- **v5.** Оба сброса перенесены на выход окна (≈ u+600 / u1+600).
- В v2 STO снимается при принятии (D-STO-LAUNCH). Поэтому любой сброс после принятия даёт перекрытие «STO снят ∧ запрос».

### DIS-HOLD-HV (READY)
Источники: Q-V7-01 «Г», вопрос 73 «А», SPEC §7 («discharge request снят» среди предусловий), §10, D-STO-LAUNCH.

**Обозначения:**
- d — первый скан `out_HV_Discharge_Request` TRUE, выданного спуском;
- a — скан принятия R&D→Run: первый скан, в котором выполнено любое из трёх — STATE_SU установлен, `out_HV_C2` TRUE, STO снят;
- u — первый скан `out_HV_C2` TRUE (a ≤ u).

**Исходные состояния.** Каждый вариант отдельно; запрос выдан одной из последовательностей:
- (1) штатная Run→R&D (STP-A);
- (2) защитный спуск из Run (Q-RC-02, Q-RC-15; STP-G/H);
- (3) abort StartingRun (STP-006);
- (4) откат WDG-03 (Q-RC-12);
- (5) аварийная цепь из Run / StartingRun;
- (6) выход из Config (E4; до E4 — не исполняется).

Далее система приходит в R&D (или, после аварии и Restart, в Safe).

**Норма удержания (READY).** Запрос TRUE в каждом скане [d, a−1] при любых событиях до принятия:
- устойчивый R&D, синяя / Unlock в R&D;
- R&D→Safe, устойчивый Safe;
- Safe→R&D, в том числе его abort и откат WDG-01/02;
- Emergency по любой причине, Restart → Safe;
- отклонённые попытки подъёма. Каждая отдельно:
  - BOTH при открытой крышке;
  - BOTH при эпизоде разрешения REL01-e2;
  - BOTH при connector FALSE;
  - BOTH при SafetyFault / FBK-10;
  - BOTH до истечения паузы 2 с;
  - поздняя вторая кнопка > 250 мс;
  - CMD_R&D_TO_RUN при ошибке PLC-команд;
  - удерживаемый фронт CMD (не новый).
- Вход в Config (E4) — это подъём. Снятие при его принятии — по аналогии ведущего (запись 73).

**Норма снятия (READY, вопрос 73 «А»):**
- запрос FALSE в скане u+1 и в каждом следующем скане до новой выдачи спуском;
- запрос TRUE в скане a−1;
- сканы [a, u] — наблюдение: снятие допускается от скана принятия.
- Подтверждение Run не требуется: снятие не зависит от FBK, HV Healthy и окна 500 мс.

**После снятия, если Run не подтверждён** (abort, откат, авария в StartingRun): запрос выдаётся снова в момент, который
задаёт порядок этого спуска. Для abort/отката — STP-006, Q-RC-12 «STO → сразу Discharge» (E3/E6). Для аварии — общая цепь,
Q-T3-1. До этой выдачи FALSE не является дефектом.

**Аварийные сочетания:**
- авария e ≤ a−1 (принятия нет) → запрос TRUE без перерыва (норма удержания);
- e ∈ {a, a+1} → наблюдение. Допустимо: запрос остаётся TRUE, либо снят и выдан снова цепью не позже её момента (Q-T3-1);
- e ≥ a+2 → снят по норме снятия; повторная выдача — по цепи (EMG-RD-L / EMGREF).

**Запрещено:**
- любой скан FALSE в [d, a−1] — FAIL «запрос снят до подъёма HV». Ветка done-left (импульс) больше не допускается;
- запрос TRUE в скане ≥ u+1 после принятия, если повторной выдачи спуском не было. FAIL «запрос держится при включённом C2 и снятом STO». Это и есть R5-1 v5: u+600 — FAIL;
- снятие запроса отклонённой попыткой, Restart, входом в Safe или Safe→R&D.

**Границы:**
- a−1 (TRUE) и u+1 (FALSE) нормативны;
- [a, u] — наблюдение;
- для отклонённой попытки точки Q−1/Q/Q+1 порога T_BOTH: TRUE во всех.

**Мутации (архитектору):**
- деактивация нового входа сброса → убийца «TRUE в u+1»;
- сброс от квалификации BOTH вместо принятия → убийца «отклонённая попытка снимает запрос»;
- сброс от окна или подтверждения Run (как v5) → убийца «TRUE в u+1».

**Тестировщику (N1 G1 v5):** done-left → FAIL, не NV/todo. Ledger веток DIS_DONE / EXP_ABORT / свипа C2_FBK — только p.4.
Самотест anchor инвертировать.

## 3. EMG6-01-BOOT — Restart при FBK ON после старта группы (B5-2) — READY-D

Вывод: однозначно, вопрос Вадиму не нужен.
- Старт группы — это Emergency (Q-RC-10, E2-04).
- Выход Emergency→Safe возможен только при снятой энергии и FBK контакторов в выключенном состоянии, затем ручное квитирование. Основания: SPEC §12 пп.3–5, EMG-006, EMG6-01 («Restart при … FBK ON → Emergency»).
- Q-V4-02 «В» (SafetyFault, не Emergency) относится к устойчивым Safe/R&D, а не к выходу из Emergency.
- Путь g1 (N3/FBAnd1) — только реализация. Требование к выходу из Emergency от пути не зависит.

**Исходно.** Старт группы по R0: `in_ES_NC_1/2` TRUE, причин аварии нет, кнопки отпущены, все команды OFF. Варианты FBK
с первого скана:
- (a) `in_LV_C1_FBK` TRUE;
- (b) `in_HV_C2_FBK` TRUE;
- (c) оба TRUE.

**События:**
1. Restart: зелёная нажата в p_r, отпущена в r (100 мс), не раньше 300 мс после старта. FBK удерживается TRUE до g.
2. Варианты момента g (первый скан FBK FALSE):
   - g ≤ p_r−1;
   - g ∈ [p_r, r];
   - g = r+1;
   - g = r+2000;
   - FBK не снимается вовсе.
3. После g без нового Restart ждать 3000 мс. Затем новый Restart (p_r2 ≥ g+300) → ожидание.

**Ожидается:**

| Случай | Ожидание |
|---|---|
| FBK TRUE в каждом скане [p_r, r] | статус Emergency в каждом скане до нового Restart после g; Safe/R&D/Run/Config нет ни в одном скане |
| g ≥ r+1 | после g без нового Restart Emergency сохраняется (нет отложенного исполнения Restart) |
| новый Restart после g (FBK OFF) | Safe (EMG6-01); момент — как у базового EMG6-01 |
| g ≤ p_r−1 | Restart → Safe (контроль: ограничение не шире требования) |
| g ∈ [p_r, r] | наблюдение: допустимо Safe по этому Restart или Emergency до нового Restart. Запрещён Safe с FBK TRUE в том же скане |

- Во всех сканах до Safe: C1, C2, C3, BMS FALSE, STO активен, Unlock FALSE, переходов нет.
- SafetyFault из-за FBK ON в Emergency — наблюдение (v7 §4.5 «вне FBK-10»).

**Запрещено:**
- статус Safe в любом скане при `in_LV_C1_FBK` или `in_HV_C2_FBK` TRUE;
- Safe без нового Restart после g;
- SAFE→EMG мерцание;
- энергия или Unlock.

**Сопутствующие варианты той же нормой:**
- Emergency из Run (in_Estop_PLC), цепь завершена, C2_FBK удерживается TRUE (залипание) → Restart → Emergency (базовый EMG6-01, путь G10);
- старт с FBK TRUE и `in_ES_NC_1` FALSE → Restart → Emergency по обеим причинам.

**Мутация (архитектору):** деактивация нового FBK-условия пути g1 → убийца — вариант (a)/(b) «FBK TRUE в [p_r, r]».

ID: EMG-006, EMG-012/MOD-006 (однозначный статус), BOOT-001, MOD-008.

## 4. B5-1 — legacy Bypass после варианта (А)

### Вне Safe (READY, не новое поведение)
Инертность legacy Bypass вне устойчивого Safe соответствует требованиям:
- V14-Q16: Bypass допустим только в устойчивом Safe при закрытой крышке, в любом другом состоянии игнорируется;
- Q-RC-05(a): поднятый вне Safe и удерживаемый Bypass игнорируется до нового фронта в устойчивом Safe;
- EMG-011: нет повышения энергии в Emergency.

Поведение F1 «Bypass в R&D даёт C2 ON» (x2: 2998 сканов) противоречит V14-Q16. Его снятие — **намеренное изменение по решению
Вадима**, а не решение команды. Плану записать так (ревьюер B5-1).

**B51-01 (READY).** Исходно — каждое отдельно:
- R&D;
- StartingRun;
- Run;
- SS1 / выбег / разряд (Run→R&D);
- Safe→R&D;
- R&D→Safe;
- Emergency (в том числе S6);
- Safe с открытой крышкой (NC1 или NC2 FALSE).

Событие: `inPLC_BypassC1C2` TRUE 300 мс, отдельно 1 скан, отдельно удерживается 5000 мс.

Ожидается:
- выходы C1/C2/STO/Discharge/Unlock и статус совпадают по скану с той же трассой без Bypass (дифференциально);
- нет fault.

### В Safe до E4 (SAFE-NOENERGY, READY)
- Требование: SPEC §2 (Safe — LV и HV выключены), E2 (однозначный статус: Safe с энергией не является Safe; по V14-Q16 это отдельное состояние Config). Значит, в каждом скане со статусом Safe `out_LV_C1` = `out_HV_C2` = FALSE.
- Факт модели (ревьюер x2, не oracle): в устойчивом Safe legacy Bypass 3000 мс даёт C1 = 0 сканов и в базе, и в (А) («reset dominates»). Противоречия в модели нет. Утверждение «legacy Bypass в Safe поднимает C1/C2» прогоном не подтверждено.
- До E4 legacy Bypass полностью инертен. Это следствие V14-Q16 (Config ещё не реализован), а не отключение функции командой. Config — CFG-001…006, E4.
- **Критерий SAFE-NOENERGY:** в каждом скане со статусом Safe C1 и C2 OFF.
  - Варианты: устойчивый Safe + Bypass 300 мс / 1 скан / удержание 5000 мс; B43-02 δ ∈ {−100, −1, 0, +1, +2}.
  - Если кандидат даёт энергию при статусе Safe — FAIL (SPEC §2, MOD-006), не known FAIL E4.
- Вопрос Вадиму не нужен.

ID: CFG-001 (игнорирование Bypass вне Safe), EMG-011, MOD-006/EMG-012.
