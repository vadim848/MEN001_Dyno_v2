# REQ-CONSOLIDATION — вопросы Вадиму (через ведущего, по одному), 2026-10-21

Формат: исходное состояние → события → какой реакции не хватает. Порядок —
по приоритету (что блокирует ближайшие этапы E2/E3). В скобках — блокируемые
критерии CRITERIA.md. Варианты — для удобства выбора, не oracle.

## Высокий приоритет

**Q-RC-01 (E3/E2; IL-03b, CVR-006, EMG-002) — потеря крышки в Run: «как сейчас» ≠ код.**
Исходно: устойчивый Run, всё исправно. Событие: in_InterLock_NC_1 или _2 → FALSE.
Ответ V14-Q21(b): «защитный спуск в R&D, как сейчас (SS1 → STO → выбег →
Discharge → выдержка → C2 OFF)». Сейчас программа делает иначе: общая защитная
цепь Step4 (как при EStop): снимает LV (C1) через 2 с, сбрасывает battery/BMS,
STO через 7 с, далее разряд и C2 OFF; в R&D не приходит. Чего не хватает:
подтвердить цель — (А) спуск ровно как нормальный Run→R&D (SS1 2 с → STO →
5 с → Discharge → выдержка → C2 OFF → R&D), LV/battery/BMS остаются включены;
(Б) оставить нынешнюю цепь Step4 (LV тоже снимается, итог не R&D).

**Q-RC-02 (E3; STP-G) — потеря Healthy в устойчивом Run.**
Исходно: устойчивый Run, down не запрошен. Событие: LV Healthy (PS1) или HV
Healthy (PS2) пропадает. Решения покрывают только SS1 (немедленный STO),
R&D (E2-Q2) и конец нормальной остановки (E2-Q1). Сейчас программа запускает
ту же цепь Step4, что при EStop (LV снимается). Чего не хватает: (А) защитный
спуск в R&D, как для крышки по Q-RC-01(А), но с немедленным STO (как потеря
Healthy в SS1); (Б) Emergency; (В) как сейчас (Step4). Отдельно для LV и HV,
если различаются.

**Q-RC-03 (E3; IL-05) — потеря крышки во время StartingRun.**
Исходно: R&D, принят R&D→Run, STO уже снят, C2 включается, Run ещё не
подтверждён. Событие: InterLock NC1 или NC2 → FALSE. Чего не хватает: (А) как
прерванный запуск — STO → сразу Discharge → выдержка → C2 OFF → R&D;
(Б) Emergency; (В) дождаться Run и затем защитный спуск. Попутно (низкий риск,
можно одним ответом): в остальных переходах — нормальный спуск Run→R&D,
Safe→R&D (крышка и так может быть открыта), R&D→Safe — потеря крышки ничего
не меняет, переход продолжается? И при выходе из Config (Bypass уже снят,
идёт разряд) потеря крышки — Emergency, как в Config?

**Q-RC-04 (E4; PLC-05) — что считается «одновременными» командами PLC.**
Исходно: Safe, крышка закрыта. События: PLC поднимает CMD_SAFE_TO_R&D →
переход выполнен, система в R&D, PLC команду ещё держит; затем поднимает
CMD_R&D_TO_RUN (обе TRUE, но фронты в разных циклах). Чего не хватает:
(А) ошибка — любые две команды перехода TRUE одновременно, независимо от
моментов фронтов (тогда R&D→Run не выполнится, пока первая не сброшена);
(Б) ошибка только при фронтах в одном цикле (или в окне N мс — назвать N);
вторая с собственным фронтом в исходном состоянии исполняется. И: ошибка
ставится, если две команды TRUE в Config или во время перехода (когда они
всё равно игнорируются)?

## Средний приоритет

**Q-RC-05 (E4; CFG-03, EMG6-01, BOOT) — условия входа в Config.**
Исходно: Bypass TRUE выставлен, когда система была в R&D (проигнорирован);
затем зелёной переход в Safe; Bypass всё ещё TRUE; крышка закрыта. Чего не
хватает: (А) войти в Config сразу по уровню; (Б) только по новому фронту
Bypass (как для команд перехода, MOD-003). То же при закрытии крышки с уже
поднятым Bypass, после Emergency→Safe и после рестарта. Попутно подтвердить:
вход в Config требует тех же прочих разрешений, что подъём (connectors, нет
SafetyFault/ошибки PLC), и Bypass игнорируется при нажатой кнопке
(как V14-Q14)?

**Q-RC-06 (E6/E4; CFG-08) — контактор не включился при входе в Config.**
Исходно: устойчивый Safe, крышка закрыта, Bypass TRUE → Config, команды C1/C2 ON.
Событие: C1_FBK или C2_FBK не ON за 500 мс. Чего не хватает: (А) откат как
при неудачном подъёме — снять C1/C2 (через Discharge), Safe, SafetyFault;
(Б) Emergency. Healthy в Config игнорируется, поэтому 30 с здесь не применяю.

**Q-RC-07 (E5/E6; WDG-07) — команды при активной SafetyFault, кроме UP.**
Исходно: неудачный R&D→Run откатился в R&D, SafetyFault активна, кнопки
отпущены. Событие: фронт CMD_R&D_TO_SAFE от PLC. Чего не хватает: исполнить
(шаг вниз разрешён) или игнорировать до квитирования кнопкой? Аналогично в
Safe: Bypass (вход в Config) при активной SafetyFault.

**Q-RC-08 (E3/E4; PLC-10) — команды вниз в прочих переходах.**
Определены: зелёная/CMD_RUN_TO_R&D в StartingRun (abort), зелёная/
CMD_R&D_TO_SAFE в Safe→R&D (abort). Не определены: зелёная 500 мс или фронт
CMD_R&D_TO_SAFE во время нормального спуска Run→R&D (SS1/выбег/разряд);
фронт CMD_R&D_TO_SAFE во время StartingRun; любые команды во время R&D→Safe
и выхода из Config. Предложение: по общему правилу V14-Q11 — игнорировать,
без ошибки, без отложенного исполнения. Подтвердить или указать иное.

**Q-RC-09 (E3; STP-F) — потеря Healthy после STO при нормальной остановке.**
Исходно: Run→R&D, SS1 завершён, STO активен, идёт выбег 5 с или выдержка
разряда. Событие: пропадает HV или LV Healthy. E2-Q1 определяет только фазу
ожидания C2_FBK OFF. Чего не хватает: остановка просто продолжается до R&D
(и потом правила R&D), или иначе (например, fault/Emergency)?

## Низкий приоритет

**Q-RC-10 (E2; E2-04) — ни одного основного состояния.** Исходно: любое
устойчивое состояние. Событие: (гипотетически) не активно ни одно из
Emergency/Safe/R&D/Run/Config вне перехода. E2 назвал Emergency для двух
одновременно. То же Emergency и для «ни одного»?

**Q-RC-11 (E2/E5; HLT-03) — статус при потере LV Healthy в R&D.** Исходно:
устойчивый R&D. Событие: LV Healthy пропал → шаг в Safe (E2-Q2a). Выставлять
ли ошибку для PLC и нужно ли квитирование кнопкой перед следующим UP (как
SafetyFault) или Safe без ошибки?

**Q-RC-12 (E6; WDG-03) — подтверждение отката R&D→Run.** Исходно: R&D→Run
принят, STO снят, C2_FBK не ON за 500 мс (или нет HV Healthy 30 с). Предлагаю
считать откатом согласованную последовательность прерывания запуска:
STO → Discharge → выдержка → C2 OFF → C2_FBK OFF → R&D + SafetyFault.
Подтвердить (в т.ч. когда C2_FBK вообще не включался).

**Q-RC-13 (E4/E5; интерфейс) — один или два статуса ошибки для PLC.**
Ошибка одновременных команд (V14-Q8) и SafetyFault (E6-Q1) — разные биты для
PLC или один общий Fault (ваш будущий вариант п.15)? На oracle состояний не
влияет; нужно для интерфейса E4.

## Не вопросы (делегировано / уже отвечено)

- Heartbeat при старте до первого импульса — Вадим поручил архитектору (V14-Q20);
  после проекта аналитик проверит поведенческие последствия (HB-04).
- Вариант выхода из Config (последовательно или C1+C2 вместе) — выбор архитектора (V14-Q18).
- Окно «одновременности» для фронтов в одном скане и снятие ошибки — отвечены (V14-Q8/Q10).
