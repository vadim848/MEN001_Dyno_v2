Это **уточнение моего критерия** DIS-HOLD-LV (E2-plan-v5-questions §1). Новое решение команды
(TD) не нужно, вопроса Вадиму нет: норма выводится однозначно из вопроса 74 «А» («как для HV»)
и READY-определения точки `a` в DIS-HOLD-HV. Причина расхождения — ошибка в моей таблице замен.

## 1. Что было неоднозначно

DIS-HOLD-HV (READY, вопрос 73 «А») определяет:
- `a` — первый скан, в котором есть **любой** признак принятия R&D→Run: STATE_SU установлен,
  `out_HV_C2` TRUE, STO снят;
- `u` — первый скан `out_HV_C2` TRUE, a ≤ u. Норма: TRUE в [d, a−1], наблюдение [a, u], FALSE с u+1.

Для LV я записал замену «a, u → a1, u1 = первый скан `out_LV_C1` TRUE». Запись не говорила,
что у a1 своё определение. Тестировщик прочитал a1 = u1. Это сдвинуло нормативную точку TRUE
с a1−1 на u1−1 и потеряло аналог STATE_SU.

## 2. Норма LV-A1 (READY: вопрос 74 «А» + DIS-HOLD-HV, вопрос 73 «А»)

Аналог STATE_SU для Safe→R&D — переходная стадия `b_Step12`. Её устанавливает грант
принятого подъёма g2. Стадия входит в обязательно наблюдаемые (`STAGES_REQUIRED` стенда),
так что точка наблюдаема без внутренних имён.

**Обозначения** (p — первое нажатие принятого жеста, d — первый скан запроса, выданного спуском):
- **a1** — первый скан ≥ p, в котором `b_Step12` TRUE **или** `out_LV_C1` TRUE (берётся меньший);
- **u1** — первый скан ≥ p с `out_LV_C1` TRUE; a1 ≤ u1.

| Скан | `out_LV_Discharge_Request` | Статус |
|---|---|---|
| каждый в [d, a1−1] | TRUE | нормативно: вопрос 74 «А», удержание до принятия (Q-V7-01 «Г» через аналогию 74) |
| [a1, u1] | любое значение, записать в diagnostic | наблюдение (как [a, u] у HV) |
| u1+1 и каждый следующий до новой выдачи спуском | FALSE | нормативно: вопрос 74 «А», снятие при принятии, не при подтверждении R&D |

**Ответ на вопрос ведущего п.1:**
- **«Скан команды C1 ON или скан гранта g2?»** Вопрос 73 «А» описывает принятие как одно
  событие: грант, выдача команды контактора, снятие STO. Порядок внутри этой цепочки по сканам
  он не задаёт. Цепочка g2 → `b_Step12` → `out_LV_C1` занимает 2 скана. Поэтому весь отрезок
  от первого наблюдаемого признака принятия (a1) до u1 — наблюдение. Обе прочтения допустимы,
  если снятие наблюдается в [a1, u1].
- **«Допустимо ли окно [g2, u1+1]?»** Нет, если g2 < a1. Скан g2, в котором ни `b_Step12`,
  ни `out_LV_C1` ещё не видны, лежит в [d, a1−1]. Там запрос должен быть TRUE. Три причины:
  - у HV точка a−1 нормативна (TRUE);
  - g2 — внутренний сигнал, не выход. Чёрный ящик не отличит «грант в этом скане» от
    «запрос снят без принятия»;
  - D-TEAM п.1: держать запрос на скан дольше — ограничительный вариант.
  Если архитектура когда-нибудь будет снимать запрос в скане самого гранта до видимой стадии,
  этот случай вернуть аналитику. На кандидате E2a-RC и по плану v7.2 его нет: g2+1 = a1.
- **Факт кандидата E2a-RC** (repro ниже): g2 = Q = u1−2, `b_Step12` с u1−1 = a1, запрос FALSE
  с u1−1 = a1, `out_LV_C1` с u1. По норме LV-A1 это **PASS**: FALSE в [a1, u1], TRUE в a1−1,
  FALSE с u1+1. План v7.2 («LV at a+1 (≤ u1+1)», a = g2) с нормой совпадает.

**Проверка безопасности: снятие на 1–2 скана раньше C1 ON.** В сканах [a1, u1−1] запрос FALSE,
а C1 ещё OFF. Энергию это не добавляет:
- LV-домен получает энергию только через C1, а C1 включается в u1 по уже принятому подъёму;
- снятие запроса разряда ничего не подключает к источнику;
- шина LV к этому моменту разряжена: запрос держался весь Safe.
Защита не снимается раньше принятия: до a1 запрос TRUE. Отклонённые попытки запрос не снимают
(нормы удержания DIS-HOLD-LV без изменений). Если принятый подъём прерван, запрос снова
выдаётся по порядку спуска или аварийной цепи (Q-V7-01 «Г», вопрос 73 «А»). Тот же сдвиг
«запрос FALSE до выхода контактора» уже есть у HV: FBAnd4 срабатывает в u−1, запрос FALSE в u.
Reference 4495a1f снимает запрос **после** включения контакторов (Network5/FBDecouple2). v2 по
решению 74 снимает его при принятии. Это сознательное отличие от reference, не дефект.

## 3. Границы и запрещённые реакции

- **q−1/q/q+1 вокруг a1:** a1−1 TRUE (норма); a1 — наблюдение; u1+1 FALSE (норма).
  Отдельной точки «a1+1» нет: она внутри [a1, u1], пока u1 ≥ a1+1.
- **Порог жеста** (TD-06): выхода подъёма нет в [p, Q−1], первый выход в [Q, Q+400].
  На кандидате: g2 = Q, a1 = Q+1, u1 = Q+2.
- **Запрещено:**
  - любой скан FALSE в [d, a1−1], в том числе в скане g2 до видимой стадии;
  - TRUE в скане ≥ u1+1 без новой выдачи спуском (в частности, сброс по окну/подтверждению ≈ u1+600 — FAIL);
  - снятие запроса отклонённой попыткой, Restart, Emergency, R&D→Run (без изменений, §1 v5).

## 4. Аварийные сочетания (EStop в скане e; кандидат: g2 = p+1000)

| e | Норма (по аналогии с DIS-HOLD-HV) | Факт кандидата E2a-RC | Статус |
|---|---|---|---|
| e ≤ a1−1 (в т.ч. e = g2) | принятия нет: запрос TRUE без перерыва, C1 OFF | g2 не наступает, TRUE, C1 OFF (e = g2−3…g2) | норма, PASS на кандидате |
| e ∈ {a1, a1+1} | наблюдение; допустимо одно из двух: (i) запрос TRUE, (ii) снят и выдан снова аварийной цепью не позже её момента (Q-ARCH-01: LV discharge сразу; Q-T3-1) | e = g2+1 (= a1), e = g2+2: запрос FALSE ≥ 8 с, стадия `b_Step12` остаётся в Emergency, C1 не включается | вне допустимого набора; **known FAIL семейства E2b** (Emergency вне Run, LV-выдача цепью не реализована) |
| e ≥ a1+2 | снят по норме; повторная выдача — по аварийной цепи (EMG-RD-L / EMGREF) | e = g2+3, +10, +700: запрос не выдаётся снова ≥ 7 с | **known FAIL E2b**, тот же корень |

Строки e ≥ a1 — не предмет D-RC-2 и не BLOCKED вопросом: требование есть (Q-ARCH-01,
Q-V7-01 «Г»). Это known FAIL до E2b, тесту судить на стеке E2a-RC+E2b. Поведение E2a-core
в этих сочетаниях я не прогонял — NV.

## 5. Что меняется

**Тестировщику** (`test/current-e2a-dis-hold.test.js`):
- `liftRnD`: `a` = первый скан ≥ p, где `s.stages` содержит `b_Step12` или `s.out.out_LV_C1`.
  Сейчас a = u1;
- заголовок, строки 8–9: «a1 = u1 = first scan out_LV_C1» заменить на определение LV-A1
  со ссылкой на этот файл;
- прочие проверки `judge` не менять: TRUE [d, a1−1], FALSE с u1+1, diagnostic [a1, u1];
- желательно добавить диагностику: если Symbol `b_Step12_Set` есть, записать g2 − a1. Только
  diagnostic, не oracle;
- ожидание на кандидате E2a-RC: строка «DIS-HOLD-LV R&D→Safe … no event» — PASS
  (a1 = u1−1, FALSE с a1). Остальные 11 строк LV по-прежнему не доходят до предусловия (E2b/E3);
- источник в тесте: «READY: вопрос 74 "А" + DIS-HOLD-HV (вопрос 73 "А"); a1 — E2-RC-D2 LV-A1».
  Это не TEAM-DEFAULT.

**Архитектору:** ничего. План v7.2 §4.2 (FBOr1.OrIn2 := `b_Step12_Set`) норме соответствует.
M-E2a-31 (запрос LV TRUE на u1+1) убивается по-прежнему. Аварийные строки §4 — во вход E2b
(LV discharge цепью в Safe→R&D/R&D), это уже известная цель E2b.

**Мутации (справка):** сброс от квалификации BOTH вместо гранта убивают сценарии с
отклонёнными попытками (connector episode, открытая крышка) — запрос FALSE при отказе.
Ослабление a1−1 на них не влияет; a1−1 оставлен нормативным.
