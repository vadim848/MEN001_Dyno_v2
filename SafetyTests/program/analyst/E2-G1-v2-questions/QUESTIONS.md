## Т1 (A10) + N2 ревью — опережение реакции относительно in_Estop_PLC; распространяется ли допуск на NC

### Установлено по коду (без изменений файлов, скрипт аналитика в scratchpad)

- Reference 4495a1f и canonical F1 одинаково: `in_ES_NC_1` → `//Network1/FBEstop1/EStopIn1` напрямую,
  `in_Estop_PLC` → `//Network1/FBAnd1/AndIn1` → `FBAnd1.AndOut` → `FBEstop1.EStopIn3`.
- orderOfExecution: reference FBEstop1 = 18, FBAnd1 = 92; F1 FBEstop1 = 24, FBAnd1 = 90. FBAnd1 исполняется
  **после** FBEstop1, поэтому FBEstop1 читает выход FBAnd1 предыдущего цикла. Путь `in_Estop_PLC` длиннее на 1 цикл —
  это свойство сохраняемой исходной последовательности, а не артефакт F1. Mentee в F1 тоже входит в FBEstop1
  (EStopIn4) напрямую.
- Ни одно решение Вадима не задаёт задержку реакции в сканах. «Emergency как в любом состоянии / как в Run»
  (V14-Q19, Q-RC-01, Q-RC-14, Q-ARCH-01) задаёт **вид** реакции и цепь. «Мгновенно» по AGENTS (решение StartingRun)
  означает программную обработку, не физическое нулевое время.

### Ответ (READY-D, вопрос Вадиму не нужен)

1. Формулировка CRITERIA v2 «в том же состоянии и скане» означает, что событие подаётся в том же состоянии
   и в том же скане e. Она не требует совпадения выходов в один скан. Аналитик уточняет её как **правило L**
   (CRITERIA_DELTA_v4 §0.1).
2. **Одно правило для всех причин ≠ `in_Estop_PLC`/`CMD_TRIGGER_EMERGENCY`.** Это ES_NC_1/2, Mentee, connector,
   InterLock NC (IL-03, IL-05a, IL-05d, IL-04, IL-05c), heartbeat, потеря FBK (Q-RC-19), WDG-05.
   Для каждого выхода аварийной реакции допускается опережение эталона `in_Estop_PLC` (то же состояние/фаза,
   тот же e) на 0 или 1 скан. Отставание запрещено. **Ответ на N2: да, допуск распространяется на NC**.
   Строгое «тот же скан» для NC предписало бы архитектору искусственную задержку NC на 1 цикл или проводку через
   FBAnd1. Это ограничение реализации, требованиями оно не задано.
3. Опережение больше чем на 1 скан:
   - для немедленных выходов (статус Emergency, C3/BMS OFF, LV discharge, Unlock FALSE, запрет повышения)
     разрешено — более быстрая реакция требованиям не противоречит;
   - для выходов с выдержкой (C1 OFF через 2 с, STO, HV discharge, C2 OFF аварийной цепи) — **FAIL**.
     Тайминги цепи не меняются (Q-ARCH-01, Q-E2Q-01). Опережение на 1 скан выше объясняется только
     разницей пути. Для выходов с выдержкой опережение ≥ 2 сканов означает укороченный таймер или
     другую цепь.
4. Поправка тестов: IL-03, IL-05a и IL-05d перевести на правило L, вместо точного совпадения. Это смягчение
   относительно G1 v1, обоснованное reference. Отставание по-прежнему убивает тест.

Предел: «на 1 скан раньше» на стенде получено при глобальном orderOfExecution (`SAL_CLOCK_CONTRACT`
observed-fixed-scan-v1). Native/target-тайминг не утверждается.

## Т2 — граница IL-02 N=u против IL-05a c=u

Исходно устойчивый R&D. BOTH квалифицируется так, что на no-event fork R&D→Run принимается в скане u.
NC FALSE с скана N = u, удерживается.

В CRITERIA v2 противоречие допустил аналитик. IL-02 относит N к «отклонён», а это противоречит §0 (совпадающий
скан — наблюдение, если требование не «включительно») и IL-05a (c=u — наблюдение).
Оба исхода прямо заданы Вадимом: отказ подъёма (V14-Q21(a), CVR-004) и Emergency при потере крышки в StartingRun
(Q-RC-03(a)). Какой из них случится в скане совпадения, зависит от реализации.

**Ответ (READY-D): N=u — нормативная дизъюнкция**, одинаково в IL-02 и IL-05a (один тест, не два):
- исход (i) — IL-02: ни в одном скане ≥ u нет снятия STO (любого привода) и нет C2 ON; R&D, нет Emergency
  и fault; восстановление NC не исполняет удержание;
- исход (ii) — IL-05a: если в каком-либо скане ≥ u снят STO или C2 ON, то Emergency защёлкнут по правилу L
  (эталон — `in_Estop_PLC` в StartingRun в скане u) с полной EMGREF-RUN и Restart → Safe.
- Запрещено при любом исходе: Run; снятый STO или C2 ON без защёлки Emergency; «отклонено», но STO был снят хотя бы
  1 скан без последующего Emergency.
- N=u−1 → (i) нормативно; N=u+1 → (ii) нормативно (без изменений).
Тестировщику: какой исход выпал — `t.diagnostic`, но проверка самой дизъюнкции нормативна (FAIL, если ни (i), ни (ii)).

## Т3 — EMGREF-LV(2): абсолютное «LV discharge ≤ e+1» или равенство с цепью Run

Ошибку допустил аналитик в E2-G1-questions/CRITERIA_DELTA. «≤ e+1» противоречит самой сохраняемой цепи: в Run
`in_Estop_PLC` даёт LV discharge на +4 (наблюдение стенда). Требование Вадима (Q-ARCH-01: «сразу … существующие
тайминги аварийной цепи не менять»; Q-E2Q-01: «одна цепь для всех случаев, C3/BMS OFF и LV discharge — сразу»)
задаёт **равенство с цепью Run**, абсолютный скан оно не задаёт.

**Ответ (READY-D):**
- абсолютные «≤ e+1» (EMGREF-LV(1)(2), IL-05a «≤ c+1», статус Emergency «≤ e+1») **сняты**;
- нормативно правило L (§0.1 дельты):
  - (а) межпричинно — опережение ≤ 1, отставание 0;
  - (б) межсостояние: та же причина в R&D, R&D→Safe и Safe→R&D против устойчивого Run — немедленные выходы
    не позже момента в Run + 1 скан, выходы с выдержкой в окне [q_Run, q_Run+1] (q−1 ещё нет, q+1 есть);
  - (в) якорь Run: `in_Estop_PLC` в устойчивом Run на кандидате против reference 4495a1f, измеренного на стенде
    тем же helper'ом (числа закрепить с SHA) — немедленные не позже ref+1, выходы с выдержкой в [ref, ref+1];
- статус Emergency — не позже первого аварийного выхода той же трассы (E2-01: аварийная цепь не исполняется
  под другим статусом) и по правилу L против эталона.
Нынешняя проверка тестировщика «≤ Run+1» совместима с (б). Якорь (в) нужно добавить, когда reference измерен.
Без якоря дифференциальная схема пропускает равномерное замедление всех причин.

## Т4 — Q-RC-19 «В» по фазам

Разложение — CRITERIA_DELTA_v4 §FBK (критерии FBK-01…FBK-09). Кратко:
- **«Подтверждён»** = скан t_f — первый скан с FBK ON при сохраняющейся команде ON того же контактора в пределах
  watchdog (t_f ≤ t_on+500). Основание — определение E6 Вадима: 500 мс — ожидание FBK; 30 с «запускается после
  корректного поступления feedback». Значит, ожидание заканчивается в t_f, а не в t_on+500.
- До t_f — только WDG (откат + SafetyFault, не Emergency). После t_f FBK FALSE (≥ 1 скан, фильтр не задан)
  при команде ON → Emergency (READY-D, буквально). Это относится и к окну (t_f, t_on+500].
- FBK, пришедший после истечения 500 мс (в уже начатом откате), не подтверждён; его пропадание Emergency
  не даёт (READY-D: «не путать с … откат»; CFG-08).
- Ожидаемый FBK OFF после команды OFF — не Q-RC-19 (WDG-05 при залипании).
- Скан между принятием спуска и командой OFF — наблюдение.
Необязательное подтверждение Вадиму — Q-V4-01 ниже: буквальное прочтение даёт Emergency на любой однократный
провал FBK, включая дребезг при замыкании.

## N1 ревью — какие разрешения Safe→R&D остаются после E2 (для варианта REL-PERMIT)

F1 `//RndPhysicalCompact/GATE_001` = `in_Estop_PLC`(инверсно) ∧ `in_False_SI2_CH8`(константа) ∧ `b_EStop_Ok` ∧
`linkSafeMode` ∧ `in_InterLock_NC_1` ∧ `in_InterLock_NC_2` ∧ `linkSafeConnectorScope`
(`//SafeResumption/CONNECTORS` = LV ∧ HV connector). После E2 NC1/NC2 из Safe→R&D убираются (V14-Q7, IL-01).

| Разрешение Safe→R&D (кнопки/BOTH) | Источник | Годится для эпизода 300 мс в REL-PERMIT? |
|---|---|---|
| `in_LV_Connector_Interlock` TRUE, `in_HV_Connector_Interlock` TRUE | EMG-003, Q-RC-14 («в Safe — без изменений: запрет подъёма без fault»), F1 GATE_001.AndIn7 | **Да — основной вариант.** Отдельно LV, HV, оба; 300 мс в Safe при отпущенных кнопках → без fault, без Emergency; BOTH через 1700 мс → принимается (Q-REL «А», READY-D обобщение «например»). Граница по кнопкам 1999/2001 без изменений |
| Нет Emergency: ES_NC_1/2 TRUE, `in_Estop_PLC`/TRIGGER FALSE, Mentee FALSE, heartbeat (E4) | EMG-001, V14-Q9, V14-Q20, F1 AndIn1/AndIn3 | **Нет.** Любая потеря — защёлка Emergency (EMG6-01), выход только Restart зелёной — нажатие кнопки само перезапускает отсчёт по кнопкам |
| Нет SafetyFault | E6-Q2, WDG-06 | **Нет.** Сам не пропадает. Квитирование — нажатие кнопки, оно перезапускает отсчёт (WDG-06(b)) |
| Нет ошибки PLC-команд | Q-RC-18(b) | **Нет для кнопок:** ошибка PLC кнопки не блокирует. Для фронта CMD_SAFE_TO_R&D — разрешение (V14-Q8), но это E4 |
| Устойчивый Safe (не переход, не Config) | MOD-004, V14-Q16 | Нет — не временное разрешение |
| FBK C1/C2 OFF в Safe (без команды) | MOD-008 «противоречивый feedback запрещает повышение» | Условно: запрет UP READY-D; прочая реакция на FBK ON без команды не задана (Q-V4-02). До ответа в REL-PERMIT не использовать |
| LV/HV Healthy | WDG-02 (Faulty TRUE до C1 ON допустим), HLT-02 | Нет — не условие принятия Safe→R&D |
| `in_Door_Monitor` | D-DOOR-INTERLOCK | Нет — не guard |
| InterLock NC1/NC2 | V14-Q7, IL-01 | Нет — после E2 не разрешение (эпизод крышки в Safe = контроль: принимается и без Q-REL) |

Для R&D→Run разрешение крышкой остаётся (CVR-004, IL-02). Вариант REL-PERMIT для R&D→Run: устойчивый R&D,
кнопки отпущены > 2 с, NC1/NC2/оба FALSE 300 мс, затем BOTH через 1700 мс → R&D→Run принят (READY-D по
Q-REL «А» «например»). Connector в R&D для этого не годится: его потеря там — Emergency (Q-RC-14).

## Новые вопросы Вадиму (ведущему решить, отправлять ли; ни один не блокирует E2)

### Q-V4-01 (низкий; Q-RC-19, FBK-01…09) — подтверждение буквального прочтения
Исходно Safe→R&D: C1 включён командой в t_on, C1_FBK ON в t_f (например, t_on+20). Событие: C1_FBK FALSE на 1–5 мс
(дребезг) в t_f+2, затем снова ON; команда ON сохраняется.
По Q-RC-19 и E6 сейчас принято: FBK «подтверждён» с первого скана ON, любой провал ≥ 1 скана → Emergency,
в том числе внутри 500 мс от команды. Чего не хватает:
(А) подтвердить — Emergency;
(Б) до истечения 500 мс от команды FBK ведёт только watchdog (провал и возврат до t_on+500 — норма), Emergency —
после t_on+500;
(В) подтверждение — только после FBK ON непрерывно N мс (укажите N); провал внутри N — продолжение ожидания.
До ответа тесты исполняют (А). Ответ (Б)/(В) меняет только окно (t_f, t_on+500] / фильтр.

### Q-V4-02 (низкий; MOD-008) — FBK ON без команды ON
Исходно устойчивый Safe (C1, C2 OFF) или R&D (C2 OFF). Событие: C1_FBK (в Safe) или C2_FBK становится TRUE без
команды ON и держится. Известно: MOD-008 — подъём запрещён; SPEC §12 — Restart требует FBK OFF. Чего не хватает:
(А) только запрет подъёма, без fault; (Б) SafetyFault; (В) Emergency.

### Q-V4-03 (низкий; Q-ARCH-04, CVR-001) — Unlock в R&D при уже открытой крышке
Q-ARCH-04 «А» сформулирован для Safe. Исходно устойчивый R&D, NC1 или NC2 FALSE. Событие: синяя ≥ 500 мс.
Чего не хватает: (А) как в Safe — Unlock выдаётся независимо от крышки; (Б) оставить поведение F1.
До ответа UNL-04(R&D) — BLOCKED, наблюдение F1.
