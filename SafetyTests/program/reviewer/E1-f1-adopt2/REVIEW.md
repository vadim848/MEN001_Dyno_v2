## 2. Соседи 499/501: вывод из требований

**501, green-first.**
- По D-Q500 на 500 мс single «уже квалифицирована». Значит, blue на first+501 приходит строго после acceptance.
- D-LATE-SECOND для «после acceptance» требует: down не отменяется, второй команды нет, up/Unlock нет.
- Oracle идентичен случаям 500/600. Вывод корректен.

**499, green-first.**
- Delta больше 250 мс (D-CHORD250) и меньше 500 мс, то есть до квалификации single.
- Источники:
  - D-LATE-SECOND «до acceptance» и строки t300 таблицы;
  - повторное подтверждение Вадима 2026-10-20/21, п.11: «позже 250, раньше 500 до принятия single — вся попытка недействительна… обе кнопки отпущены непрерывно 2с».
- Удержание обеих кнопок 1200 мс заодно покрывает D-RUN-BOTH-IGNORE.
- Все три проверки выведены из требований, а не из кода: нет down/rawAnd23/aggregate при удержании, нет up/unlock после отпускания, нет отложенной команды после очистки.

**Позитивный контроль 2110 мс корректен.**
- Фильтр отпускания 2 с подтверждён Вадимом: п.10, п.11, D-RUN-BOTH-IGNORE «обеOFF2000». 2110 мс превышает его с запасом.
- Затем green держится 504 мс. Это больше квалификации 500 мс, а owner захватывается на q+1.
- Контроль проверяет живучесть конуса, а не точную границу фильтра. Тестировщик это прямо оговорил.

**Blue-first 499/501.**
- Oracle «нет второй команды» верен по обе стороны границы.
- В Run Unlock запрещён (п.2 подтверждений, Armed). Поэтому эти случаи слабо различают мутанты: ни одного прогнанного мутанта они не убили. Тестировщик указал это честно.
- Для blue-first 499 не проверено условие «новая попытка только после обеOFF + фильтр». Это пробел покрытия, а не ошибка.
