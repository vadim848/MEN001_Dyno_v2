# Решения и открытые сценарии — аналитик требований

2026-10-18. Область: программное поведение v2; аппаратные источники входов,
привязки и глобальные параметры не исследуются. Документ не вводит новых
требований и не превращает предположение модели в ожидаемое поведение SAL.

## Источники и порядок сверки

Первый источник старого поведения — read-only reference MEN001_Dyno,
Prodoction, 4495a1f6049f6a58ebfd436761faa84d17c8d643. Первое чтение checkout
вернуло Permission denied; повторное разрешённое чтение SAL через escalation
успешно. Прочитан заголовок Crc197137056; это подтверждает доступ к исходнику,
но не полное сопоставление фаз. Имеющиеся сведения: REFERENCE_BEHAVIOR.md и
reference-behavior.js. R&D — устойчивая промежуточная остановка/продолжение
полной рабочей последовательности reference; отсутствие такого имени в коде
не означает отсутствия соответствующей фазы. Фазы сопоставлять по коду.

Порядок источников для конкретного сценария: последнее явное решение
пользователя → утверждённое намеренное изменение требований → reference
сохраняемой последовательности → предварительные/исторические материалы.
Последние не отменяют первые. Неустранённый конфликт требует вопроса.
Неоднозначное «как в оригинале» ранее не было утверждённым решением о STO.

## Проверка существующих oracle

### Самостоятельные PLC requests: read-only trace, 2026-10-19

`MAIN.act_LogicMap()` вызывается в v2 MAIN:49. Его CASE по `n_SafeSate`
выдаёт постоянные пары Set_RnD_Mode/Set_RnD_Mode2: Safe→R&D10,
R&D→Armed/Run11, R&D→Safe00. Для Armed→R&D комментарий задаёт01,
но реальный CASE записывает10 (строки151–153): комментарий не является
доказательством программы. В прочитанном PLC-коде отдельная процедура
request/ack или генерация нового события для этих пар не найдена; сам CASE
перезаписывает уровни. Reference MAIN не содержит act_LogicMap/этих R&D bits;
сохранение исходной полной последовательности не утверждает новый handshake.

SAL v2 Network12/FBAnd8/9/10 принимает pair11 через FBOr1 параллельно
button BOTH/Ton1; FBDecouple3 выдаёт внутренний up request. FBAnd12/13/14
подаёт PLC pair00 через FBOr2 параллельно green. В FBAnd14 есть дополнительный
вход in_False_SI2_CH8, тогда как его upstream условия используют инверсию
того же входа; поэтому номинальная таблица кодов сама по себе не доказывает
исполнение down. Фактические переходы проверять на SAL, не только PLC comment.

§14 рекомендует PLC CMD_STEP_UP/DOWN и обработку как нового события с handshake,
MOD-007 оставляет проверку permissions за TwinSAFE. Это подтверждает запрет
сырого held-level bypass, но не однозначное разрешение запуска без physical
gesture: §§6–7 описывают инициатором две кнопки, §15 — действия оператора.
Следовательно, Q-PLC-REQUEST выше требует ответа. Ни удалять самостоятельный
PLC путь, ни объявлять его безусловно разрешённым по уровню нельзя. До ответа
ограничить зависимую PLC acceptance policy; независимые B1 repair/HV guards
продолжаются. DoorMonitor basis уже утверждена и новым blocker не становится.

### Проверка исходного guard запуска, 2026-10-19

Исторический анализ ниже сохранён как доказательство потребителей. Его прежний
вывод о блокере заменён D-DOOR-CURRENT: отдельный locked contract отложен,
workflow продолжается по обычному DoorMonitor и исходным условиям.

Reference SAL прочитан напрямую без изменения файлов, parser sal-parser.js:

- `in_Door_Monitor` имеет два программных потребителя:
  `//Network2/FBAnd6/AndIn1` (прямой контакт) и
  `//Network2/FBAnd8/AndIn1` (инвертированный).
- FBAnd6 объединяет DoorMonitor и оба ES_NC, его выход идёт в
  FBAnd1/AndIn2. FBAnd1 также получает Step1, connector/external interlocks
  и разрешение PLC/Mentee через FBAnd5. Дальнейшая цепь TON/контакторные
  feedback/STO feedback и green создаёт `b_Step2_Set`; исходная полная
  последовательность продолжается Network5. Это реальный код старого guard,
  а не вывод из названия режима или физического происхождения входа.
- В reference SAL нет отдельной переменной, названной locked/solenoid
  monitor; единственное door/cover monitor имя — `in_Door_Monitor`.
  Наличие только одного такого имени не доказывает его составной смысл.
- Reference PLC MAIN присваивает `stTwinSAFE_OUT.DoorMonitor :=
  DoorMonitorFromPLC` (строка25). DUT содержит отдельное поле
  `SolenoedMonitor` (строка11), MAIN использует его в HMI-ветвлении
  (строка77). Чтение программного кода не обнаружило его передачи как
  отдельного guard указанной SAL-цепи. Из этого не выводятся аппаратные факты.
- В v2 Network12 прямой DoorMonitor поступает через FBAnd16 в FBAnd4/AndIn2;
  FBAnd4 также получает R&D через FBAnd1 и request через Decouple3.
  Эта ветвь пишет `b_Set_HV_C2_1`. Следующая цепь FBAnd6/Decouple2 объединяет
  STO set requests и Step3 confirmation; D-STO-LAUNCH требует разделения.
  Другие потребители DoorMonitor в v2 относятся к door grant/reset.

Вывод аналитика: существующий DoorMonitor guard доказан программно, но
его контракт как одновременного closedANDlocked не доказан. Согласованное
сохранение исходной последовательности не отменяет автоматически намеренное
требование §5/7 об уже подтверждённом locked. Поэтому требуется ровно
Q-LOCK-CONTRACT выше (уточнён после D-LOCK-CHECK). Технический выбор имени accepted-launch marker —
работа архитектора, не вопрос пользователю. Блокируется только зависимое
разрешение StartingRun; независимые window/HV guards продолжаются.

1. ACC-B02-G/B, ACC-B03-T, ACC-B03-FLICKER и failed-chord сценарии
   candidate-button-cover.js не всегда включают начальный полный release
   filter, но часть из них ожидает положительную команду после удержания.
   Сейчас это сокращённые component checks Network12. Перед переносом на
   полноценный recognizer необходимо явно подготовить ArmedIdle через
   согласованную последовательность отпускания. Иначе positive oracle
   противоречит BTN-002/BOOT-002. Negative assertions не ослаблять; стартовые
   удержания сохранять отдельными запрещёнными сценариями.
2. Численные ожидания 900/1100/1900/2100 мс относятся к заменённым
   предварительным 1/2 с. После явного ответа пользователя D-TIMING ниже
   oracle следует перевести на 0.5/1 с, сохранив проверки до/на/после порога,
   непрерывности и сброса. Это изменение требования по ответу пользователя,
   а не изменение SAL timer или ослабление проверки ради зелёного отчёта.
3. Прежний конфликт FULL_NORMAL_CYCLE.md и §7 о снятии STO закрыт явным
   D-STO-LAUNCH ниже. Актуальные документы разрешают снятие при принятом
   launch без ожидания C2/HV Healthy feedback, сохраняя отдельное подтверждение
   Run и аварийные/interlock запреты. Старый after-feedback oracle не применять.
4. FEEDBACK_TIMEOUTS.md задаёт 5/10 с и конкретные реакции как предварительную
   модельную политику. Не принимать эти числа/реакции как утверждённые SAL
   требования без источника. Имеющиеся времена SAL проверять без пересмотра.
5. STATE:* с инъекцией внутренних Set проверяют ownership boundary, а не
   достижимость/приём внешнего жеста. PRIORITY seeded фазы и fallback FALSE/TRUE
   дают условные контрпримеры. Это ограничения доказательства, не новые oracle.

## Согласованные решения

D-DOOR-CURRENT, последнее действующее решение пользователя 2026-10-19 через
координатора: сохранить обычный цифровой DoorMonitor через PLC и программные
условия исходного рабочего проекта; НЕ добавлять отдельное locked feedback
в launch guard до обсуждения с инженером исходной системы. Будущие изменения
только после нового ответа пользователя. Это заменяет условный D-LOCK-CHECK
как текущее указание исправлять DoorMonitor-only и снимает dependent guard hold.
Q-LOCK-CONTRACT отложен в будущий объём, ответа сейчас не требует и не является
mandatory NOT VERIFIED текущей приёмки. Trace завершён, исследование hardware
не продолжается. DoorMonitor — обычный вход, не safe proof/closedANDlocked;
исходные EStop/interlocks/прочие защитные цепи не удалять и не обходить.
Существующие условия нужно проверить реальным кодом, они не объявлены
проверенными самим решением. Структурный дефект binding repair B1 независим
и не отменён. SPEC§5/6/7, CVR-004/006 и SCOPE отражают текущую границу.

Текущий oracle: при новом правильном жесте R&D→Run проверяются существующий
DoorMonitor и исходные программные разрешения; отсутствие нового отдельного
locked feedback не является причиной отказа/блокером. При DoorMonitorFALSE
повышение не принимается без fault по существующим требованиям крышки.
Потеря других защитных разрешений сохраняет прежнюю реакцию. Детали нового
отдельного locked-loss поведения не придумываются и пока не проверяются
как обязательный текущий контракт.

D-LOCK-CHECK, 2026-10-19: последнее условное решение пользователя через
координатора: «Если в оригинале он смотрел на DoorMonitor и игнорировал
Lock Feedback Safe, то это неверно, это надо исправлять». Прежняя отменённая
реплика «как в оригинале» не разрешает DoorMonitor-only приёмку. Требование
closed+locked не отменено. Адресный readonly анализ существующих программных
объявлений/mappings выполнен в LOCK_FEEDBACK_SOFTWARE_TRACE.md; найденный по
имени solenoid status не признан safe feedback. Q-LAUNCH-BINDING заменён
конкретным Q-LOCK-CONTRACT; ответ о пригодном locked сигнале ещё отсутствует.

D-LATE-SECOND, последнее уточнение пользователя 2026-10-18 через координатора:
«Просто не начинать новое». Если вторая появляется позже250мс ДО single
accepted — игнорировать попытку без fault, ни single, ни StepUp. Если single
УЖЕ accepted — не отменять команду, не откатывать и не прерывать начатый переход;
не принимать новое до полного отпускания обеих кнопок и существующего фильтра.
Ровно500мс сохраняется D-Q500 single priority. GreenON подавляет Unlock, это
output hold, не rollback события. Новых значений release filter не задано.
Раннее «поздняя отменяет single» не является актуальным общим правилом:
его заменяет это контекстное разделение до/после acceptance. Связанные late
неоднозначности закрыты; остальные открытые вопросы выше не изменены.

Текущая матрица — обязательный oracle для новых проверок фактического SAL;
полнота исполнения этих шести сценариев ещё не подтверждена. Отдельно проверить
истечение фильтра и отсутствие acceptance раньше его окончания, не вводя нового
значения. Другие причины Emergency/interlock loss сохраняют свои приоритеты:
«не прерывать» относится именно к поздней второй кнопке, не отменяет аварии.
Трассировка: SPEC§3.1 пп10,14; BTN-001/002/003/004/005/008, CVR-001.

D-CHORD250, последнее решение пользователя 2026-10-18 через координатора:
`T_CHORD_WINDOW = 250 ms`, допустим интервал `delta <= 250 ms` симметрично
для обеих первых кнопок. После появления второй обе непрерывно удерживаются
полную1с; SINGLE0.5с сохраняется. Явно разрешено изменить именно этот
программный window параметр вопреки прежнему общему запрету изменения времён.
Аппаратные/физические параметры не меняются. Это заменяет старый chord500
oracle; D-Q500 не означает допуска chord500 и не является открытым вопросом.

и имеет приоритет, ретроспективный TwoButtonsAttempt запрещён. Симметрично
для синей/зелёной первой. StepUp из этой же принятой single attempt запрещён;
новая попытка требует прежних полного отпускания/release filter. Видимость
Unlock отдельно: зелёная TRUE запрещает выход по существующему hold gate.
Не задавать длительность импульса Unlock в совпавшем скане.

D-STO-LAUNCH, 2026-10-18: пользователь через координатора: «Разрешаю мгновенно
снятие STO, не надо ждать фидбэка». Для R&D→StartingRun снятие STO (разрешение
момента) выполняется при принятом launch без ожидания C2_FBK/HV Healthy.
Поднятие STO означает запрет момента. Это программный момент, не физически
нулевое время. Остальные EStop/interlocks/permissions сохраняются; подтверждение
Run и обработка отказа запуска не отменяются. Прежний Q-StartingRun закрыт.
Трассировка: SPEC §7, MOD-002; scenarios/FULL_NORMAL_CYCLE.md этапы4–5.

D-REFERENCE-BASE, 2026-10-18: пользователь подтвердил, что v2 сохраняет полную
исходную рабочую последовательность и добавляет устойчивую среднюю остановку
R&D с продолжением. Это не redesign; архитектор обязан сопоставить исходные
фазы по коду даже без имени R&D. Намеренные изменения отслеживаются отдельно.

Для архитектуры StartingRun после D-DOOR-CURRENT: accepted launch включает
единственный R&D, новый жест, DoorMonitor и исходные программные разрешения
крышки (без нового отдельного locked proof), UnlockFALSE, снятый discharge
request, исправный LV и отсутствие действующей аварии/critical faults;
connector/external interlocks сохраняются по §5.1. Новый user decision запрещает
использовать ожидание C2/HV Healthy feedback как задержку момента снятия STO.
Это перечень требований, не утверждение, что существующий b_Set_Transition_3
уже доказывает все разрешения. REFERENCE_PHASE_MAPPING.md показывает объединённые
STO requests и Step3 confirmation; их разделение — архитектурная задача.
Точный marker и реальные producers/consumers обязаны иметь трассировку;
ввод accepted-request в компонентном тесте не закрывает полный external-input
acceptance. Отложенный отдельный locked contract больше не блокирует guard;
существующие EStop/interlocks и остальные исходные цепи не обходить.

D-TIMING, 2026-10-18: пользователь через координатора: «Оставим как в эталоне

Решение не изменяет release filter 2 с, chord window 0.5 с, порядок распознавания,
rearm или повтор; эти вопросы нельзя считать отвеченными этой цитатой.
Трассировка: SAFETY_STATE_MACHINE_SPEC.md §§3.1,16,18,20; BTN-003/004/006.

Проверка после D-TIMING: BUTTON_COVER_DESIGN.md описывает inclusive `<=`
и переход Candidate→TwoAttempt, а BUTTON_COVER_PROTOTYPE.md включает точку
500 мс; оба подготовлены при старом single 1000 мс, когда совпадения порогов
не было. Их старое inclusive equality правило заменено D-Q500.
Старые defaults single 1000/both 2000 в прототипах — историческая модель,
не текущий timing oracle. Теперь их можно синхронизировать по D-TIMING и
D-Q500 и последующему D-CHORD250, сохранив остальные требования и тесты.
LV permission независима. Старые inclusive500 chord проверки — исторические.

ролей. Этот документ записывает анализ; он не является ответом пользователя
на открытые вопросы и не является независимым ревью реализации.
