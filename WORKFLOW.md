# Workflow программных исправлений TwinSAFE v2

Утверждён пользователем 2026-10-18: оформить и сразу выполнять, включая реальные
изменения программной логики. Границы AGENTS.md сохраняются. Это локальный цикл,
без публикации, загрузки в контроллер и изменения hardware/global parameters.

R&D добавляет устойчивую остановку/продолжение внутри исходной полной рабочей
последовательности. Сохранять её шаги, кроме явно согласованных изменений;
соответствие исходных фаз и границ R&D обосновывать кодом, не названиями.
Приоритет по конкретному сценарию: последнее согласованное решение пользователя
в его контексте → утверждённые требования намеренных изменений → reference
сохраняемого поведения. Предварительные/исторические документы не override.
Оставшийся конфликт реакции требует вопроса, не самовольного выбора.

Уточнение границ: запрещены hardware mappings, физические настройки и
аппаратные/групповые конфигурационные параметры; обычные программные переменные
и связи можно менять по плану. Заданные таймеры не менять. Техническую границу
параметра сначала изучить; если неясна — спросить, не расширяя hardware scope.

Последнее текущее решение DoorMonitor заменяет прежние HOLD/условное исправить
DoorMonitor-only: сохранить обычный цифровой DoorMonitor через PLC и программные
условия исходника; отдельное новое locked feedback guard не добавлять до
обсуждения пользователем с инженером и отдельного будущего решения. Workflow
не блокируется. Существующие EStop/interlocks сохранить, не обходить; обычный
input не называть safe, аппаратную безопасность не заявлять. Выполненная
read-only трассировка lock feedback — история/справка, не новый обязательный gate.

Действующее решение StartingRun R&D→Run: снять STO при принятом запуске,
не ожидая C2_FBK/HV Healthy. Другие разрешения/EStop и последующие
подтверждения Run сохраняются. Термины: снятие STO разрешает момент, поднятие
запрещает. Речь о программном порядке, не физическом нулевом времени.

Решения кнопок: single 0.5с / both 1с; **окно комбинации 250 мс включительно**,
симметрично для обоих порядков. BOTH отсчитывается с появления второй кнопки
при непрерывном совместном удержании. Изменение именно этого программного
окна явно разрешено пользователем; прочие заданные времена не менять.
При второй кнопке ровно на 500 мс (уже вне окна комбинации)
приоритет у уже квалифицированной одиночной, без ретроспективного StepUp из
той же попытки. Это симметрично для обоих порядков. Событие квалификации
отделять от условий выхода: зелёная ON по-прежнему снимает Unlock. Не
назначать неоговорённую длительность видимого импульса на границе скана.

Поздняя вторая (>250 мс) до single acceptance делает попытку недействительной
без ошибки: нет single/StepUp, нужна полная очистка. Если single уже принято,
поздняя вторая не отменяет/не откатывает/не прерывает начатый переход и не
создаёт новых команд до отпускания обеих+фильтра. На500 мс приоритетsingle.
Отдельное снятие удерживаемого Unlock зелёной сохраняется; это не rollback.
Число фильтра этим решением не изменено; другие abort-сценарии не определены.

1. Владелец запускает `npm run check:software` в SafetyTests. Неизменяемый
   снимок результатов сохраняется с SHA256 SAL, версией кода, требованиями,
   допущениями и исходным SAL. Историческая fixture не перезаписывается.
   Перед функциональным исполнением валидировать весь исходный SAL/SGVL:
   typed alias/global bindings, DSL wrappers, usage indices и один native
   wiredLink на новую пару портов. Не отбрасывать ошибочные связи выделением
   удобного подграфа; чтение runtime только по имени не структурная проверка.
2. Отдельный аналитик требований и сценариев изучает согласованные решения,
   требования, read-only reference и контрпримеры. Для сценария фиксирует
   исходное состояние, входы/события, ожидаемые состояния/выходы, исключения,
   конфликты и критерии проверки с трассировкой. Неполный/неоднозначный сценарий
   направляет пользователю, не придумывая oracle. Решения и открытые вопросы:
   SafetyTests/SCENARIO_DECISIONS.md. Технические решения оставляет архитектору.
3. Отдельный архитектор изучает reference, v2, требования и контрпримеры.
   Пишет конкретный пакет: блоки/связи, ожидаемое поведение, сохраняемые
   инварианты, приёмочные сценарии, разрешённые файлы и границы итерации.
   Новая функция R&D определяется требованиями v2, а не копированием reference.
   В точке готовности первичного тестового пакета перед редактором создать
   локальный checkpoint-коммит относящихся требований/правил/тестов/baseline.
   Честные FAIL сохраняются, зелёная приёмка для исходного checkpoint не нужна.
   Перед коммитом остановить запись исполнителей; исключить посторонние файлы
   и секреты. Если редактор уже начал, не переписывать историю reset/stash или
   откатом: чисто разделить при возможности, иначе явно назвать checkpoint
   текущим, включающим уже выполненные правки. Push этим не разрешён.
4. Отдельный редактор реализует пакет небольшими итерациями. После каждой —
   целевые проверки и регрессия; перед ревью — полный согласованный пакет.
   Ошибки стенда исправляются с обоснованием без ослабления требований.
5. Независимый ревьюер читает требования, план, фактический diff, тесты и
   результаты. Проверяет как новые связи, так и оставшиеся старые обходы.
   Зелёные тесты не заменяют ревью; программные тесты не доказывают hardware safety.
6. Существенные замечания возвращаются на соответствующий этап: требования
   аналитику, архитектура архитектору, код редактору. После исправлений повторяются
   относящиеся проверки, полный пакет и независимое ревью. Одинаковый неудачный
   подход не повторяется бесконечно: редактор сообщает архитектору, исследует
   причину и получает уточнённый подход.

Одновременно запись каждого файла принадлежит одному исполнителю. Владелец
ведёт статус и границы; аналитик пишет сценарии/решения; архитектор пишет план;
редактор меняет код/тесты;
ревьюер пишет только отчёт ревью. Передача файлов явно оговаривается.
При новых неоднозначностях любого этапа возвращаться к аналитику, затем при
необходимости пользователю. Полезная завершённая работа не отменяется;
приостанавливаются только зависимые изменения, остальные продолжаются.

Приёмка итерации: её требования проходят на фактическом SAL, нет новых
необъяснённых регрессий, существенные замечания закрыты. Незакрытые требования
общего проекта остаются FAIL/NOT VERIFIED и не скрываются. Финал всего задания:
все обязательные программные требования/проверки из
SafetyTests/SOFTWARE_ACCEPTANCE_SCOPE.md покрыты и пройдены, существенные
замечания закрыты, ограничения явно записаны. Зелёная модель не равна зелёному
SAL; необъяснённые FAIL и обязательное непокрытое поведение остаются открытыми.
Технические/модельные допущения имеют явные пределы; условные контрпримеры не
объявляются доказанными дефектами. Неизвестное поведение не заменяется oracle.
Native/hardware validation вне текущего объёма не является скрытым gate и не
выдаётся за выполненную. SAL CRC в XML не объявляется пересчитанным без native evidence.

Обычные подготовка, реализация, тестирование и возврат с ревью уже разрешены.
Для всех ролей: базовый вопрос ожидаемого сценария требует ответа пользователя,
если reference и утверждённые требования не дают однозначной реакции. Вопрос
содержит исходное состояние, последовательность входов/событий и недостающую
реакцию состояния/выхода/приоритета. Не вводить своё предположение как требование
или тестовый oracle; зависимый участок оставить без изменения, продолжать
независимые части. Отсутствие ответа не считать согласием.
Вопрос пользователю нужен лишь при влияющей на поведение неоднозначности после
изучения reference/требований, недоступных необходимых данных, выходе за объём
или конкретном блокере после исчерпания осмысленных вариантов. Независимые части
продолжаются. Обязательные разрешения среды не обходятся.
