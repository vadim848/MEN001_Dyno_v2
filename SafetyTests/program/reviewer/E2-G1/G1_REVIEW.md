## 3. Зависимость от плана; D2-A (п.2)

Из плана взяты только имена (STS_*, b_Step*), формула D2-A и список мутаций.
Формула D2-A **не нейтральна**. Архитектор сам называет её «нормативной для E2-01».
Она задаёт отображение: S12 → Safe, S2/S4/S5/S6 → Emergency, «ни одной стадии» →
Emergency. При D2-A тест «exactly one status» по построению слабее «stages≤1» (INV-3
следует из INV-1). Независимую нагрузку несут только проверки своевременности
(MOD1-01/MOD-002/STP-A/MOD5-01), правило «нет STS_EMG в нормальном lifecycle»
и EMGREF. Их ожидания выведены из требований, поэтому формулу можно принять как
средство наблюдения. Пределы:
(a) прохождение «exactly one status» при D2-A не является отдельным доказательством E2-01;
(b) решение «S12 = Safe в течение Safe→R&D» — выбор архитектора, а не требование;
(c) при D2-B/E4 опубликованные STS_* проверяются уже как независимый наблюдаемый
выход. Тогда G4 должен сверить отображение с требованиями.

## 4. Допущения (п.3)

- **A1 — существенное замечание (C1).** `in_Safety_Run` связан в SAL с портом группы
  `//RunStop` (SAL, строки 12341–12370; targetUsages: groupPortUsage RunStop и
  N3/FBAnd1.AndIn1). Пока логика группы исполняется, вход TRUE. Нормативный вариант
  FALSE плюс инъекция памяти b_Step1 физически недостижим и противоречит CRITERIA §0
  («Safe — через EMG6-01», «не инъекцией»). Он отключает реальный путь программы:
  резерв N3/FBAnd1 «нет стадии → Step1». Проба `repro/safety-run-probe.mjs` (split):
  - при TRUE на canonical b_Step1 остаётся вместе с b_Step3 во всём Run (S1∧S3 с t=6520);
  - после in_Estop_PLC в Run и Restart при TRUE стадии S1+S5, при FALSE — застревание
    в b_Step6.

  В FALSE-варианте это видно лишь косвенно: gap → STS_EMG в lifecycle-тесте.
  Остальные файлы вообще не проверяют TRUE. Инъекция объявлена и не выдаётся за
  достижимость. Нарушение G1 «нет инъекций, выдаваемых за достижимость» формально
  не допущено, но нормативный режим выбран неверно.
- **A2 — модель объекта** (FBK = команда + 1 скан; удержание через hold). Маскировки
  нет: удержания ограничены окнами < 500 мс и явно указаны.
- **A3 — split.** Разделение корректно: split не попадает в нормативные цифры.
  Ограничение: тест останавливается на первой упавшей проверке. В split поэтому
  не видны последующие утверждения: конечное состояние и Unlock в IL-03, цепь L
  в E2-02, C3/BMS в HLT-01. Диагностика показывает дефекты за RED полярности, но
  не доказывает, что выполняются остальные утверждения. Это станет видно только
  на кандидате (G3).
- **A5 — скан 1 мс и наблюдение после скана.** Приемлемо и объявлено.
- **A6 — D2-A.** См. §3.

## 5. RED на canonical (п.4)

118 тестов падают на предусловии «R&D after BOTH» (N11/FBAnd4.AndIn3, D-ARCH-POL).
Это правильная причина: MOD1-01 прямо ожидает RED по полярности. Без split этот
RED скрыл бы все прочие утверждения. Split их частично раскрывает (§4 A3):
S1∧S12, S3∧S4, Step4∧Step12, IL-03 на скан раньше эталона, отказ спуска при
открытой крышке (GATE_001), V14-Q7. Это достаточно, чтобы убедиться, что тесты
нагружают нужные места. Этого недостаточно как доказательства, что все утверждения
выполнимы и непусты; окончательно это проверит G3.

## 7. Мутации (п.6)

- **C3 (блокирует G3 mutation run).** Во всех MUTATION_PLAN_E2a…d `testFiles` содержит
  строку-шаблон вида `"current-e2a-*.test.js (v2-tester, G1)"`. scripts/sal-mutation-check.js:60
  фильтрует testFiles через `fs.existsSync`. Такой файл не существует и молча
  отбрасывается. **Ни один E2-тест не будет запущен**, и мутации будут оцениваться
  только старыми тестами. Кроме того:
  - `behaviouralTests` по срезам (`^E2b `, `^E2c `, `^E2d `) не совпадают с убивающими
    тестами. E2b-02 убивается тестами `E2d IL-01/02`.
  - Файлов `current-e2c-*`/`current-e2d-*` нет: тесты E2c/E2d лежат в
    current-e2a-rnd-cover-healthy.test.js.

  Нужно: 4 точных имени файла и `^E2[a-d] ` в каждом плане (архитектору). В раннере
  отсутствие файла из testFiles желательно сделать ERROR, а не молчаливым пропуском
  (стенду).
- Таблица «каким тестом убиваема» в HANDOFF — утверждения тестировщика.
  Проверить их можно только на кандидате/мутантах (G3), до этого NV. E2a-08,
  E2a-12, E2a-14/15, E2a-16, E2b-01, E2c-01 убиваются падением предусловия. Это
  засчитывается как kill, только если раннер учитывает failed assertion, а не
  ERROR/load-fail (helper бросает AssertionError — допустимо).
- Не убиваются сейчас: E2b-03, E2b-04, E2b-11 (IL-05a/b), E2b-12 (Q-RC-14 — теперь
  READY), E2d-03/04 (CFG-02, E4), E2a-17 (NV). E2b-10 — «вероятно», проверить на G3.
- Эквивалентность MU11, N7/FBAnd8.AndIn5, N6/FBAnd18.AndIn4 — в эту G1 не входит;
