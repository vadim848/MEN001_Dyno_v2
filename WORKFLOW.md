# Workflow программных исправлений TwinSAFE v2

## ДЕЙСТВУЮЩИЙ ПРОЦЕСС — компактный (утверждён Вадимом 2026-10-23)

Заменяет «Команду Claude Code» (ниже — история). Причина: процесс разросся
непропорционально (≈1400 тестовых случаев, 8 версий плана E2, ~80 вопросов).

**Основа проверки — каталог сценариев** `SafetyTests/program/lead/SCENARIO_CATALOG.md`
(100 сценариев, утверждён Вадимом). Тесты пишутся только по каталогу:
полная программа, реальные входы, штатный старт Emergency→Restart→Safe, допуск
по времени ±50 мс, инвариант «одно основное состояние». Новый сценарий — только
если появилось новое решение Вадима; добавляется строкой в каталог.

**Роли (минимум):**
- ведущий — основная сессия; ведёт этапы, коммиты, общение с Вадимом через
  родительскую сессию;
- исполнитель — `v2-editor` (Sonnet): код SAL по плану этапа;
- тестировщик — `v2-tester` (Opus): тесты каталога, независимо от исполнителя;
- ревьюер — `v2-reviewer` (Opus): **одно ревью в конце этапа** (план + diff +
  результаты каталога);
- аналитик/архитектор — только по необходимости (новое решение, сложный план),
  не на каждый шаг; прогоны — `v2-runner` (Haiku).

**Этапы (крупные):**
- S1 — каталог в тесты: `SafetyTests/test/catalog/`; `check:software` прогоняет
  каталог + структурную проверку (native preflight, CRC, FB ≤ 512). Прежние тесты —
  в архив (`test/archive/`, остаются в git, в регресс не входят).
- S2 — E2: на кандидате v7.7 исправить 4 известных дефекта (L3 +2, E2-02, выход из
  Emergency при FBK ON, u1+599), прогнать сценарии E2 каталога, ревью, перенос.
- S3 — E3 (STOP v2). S4 — E4 (PLC-интерфейс, Config, heartbeat). S5 — E5/E6+E7.
- S6 — Verify/Build в TwinCAT (Вадим) и исправления по результатам.

**Gate этапа:** сценарии каталога этого этапа PASS (+ все ранее перенесённые),
native CRC/структура OK, мутации только из раздела M каталога, одно ревью ACCEPT →
перенос в canonical → локальный коммит. Без G1-ревью тестов, без скановых свипов,
без поблочных слепков, без мутационного критерия «каждая убита».

**Вопросы Вадиму:** только если по каталогу и решениям реакция не определена и нет
рекомендации агента (правило REC-ACCEPTED сохраняется). Экономия квоты (Sonnet для
исполнителя, отчёты коротко на английском, checkpoint перед исчерпанием лимита)
сохраняется. Запреты AGENTS.md (push, download, оборудование, reference) сохраняются.

## ИСТОРИЯ: прежний процесс (до 2026-10-23)


## Непрерывная ответственность ведущего

Ведущий отвечает за весь согласованный цикл, а не только за запуск специалистов.
Запуск агента, завершение его хода или обычный отчёт о прогрессе не означают
завершения задачи. Ведущий получает результаты, проверяет их и готовность пакета,
явно передаёт работу следующему исполнителю с границами записи, возвращает
замечания аналитику/архитектору/редактору и организует повторную проверку.
После завершения исполнителя ведущий продолжает координацию, а не оставляет
следующий этап ждать новой просьбы пользователя. При ожидании результатов
использует ожидание сообщений и сообщает прогресс без завершения рабочего цикла.

Перед сообщением «работа продолжается» ведущий проверяет фактические статусы:
running означает незавершённый этап и может скрывать ожидание инструмента или
разрешения; это не доказательство выполняющихся проверок. Исполнитель сразу
сообщает ведущему о таком ожидании и его точной причине. Ведущий различает
вычисление/редактирование, ожидание результата и ожидание разрешения;
необходимые разрешения не обходит и не повторяет без причины уже подтверждённые
read-only проверки идентичности reference. completed означает полученный результат,
которому нужны проверка и следующая передача. Завершённый ход ведущего сам по
себе не является фоновым процессом координации; автоматическое продолжение нельзя
обещать без действующего механизма. При отсутствии активных исполнителей ведущий
не называет работу выполняющейся.

При эскалации исполнитель не оставляет ведущего без информации на всё время
approval: если оркестратор инструмента вернул идентификатор продолжающегося
вызова, сообщает ожидание и нужное разрешение до следующего длительного wait.
Отменённые пользователем запросы не повторяет и не обходит; оценивает, какие
уже прочитанные данные достаточны и какие независимые работы доступны.

Координация продолжается до согласованного результата, явной остановки
пользователем либо реального блокера, требующего его решения. Технический HOLD
возвращается на исследование и исправление, пока доступны осмысленные действия.
Неоднозначность ожидаемого поведения блокирует только зависимый участок;
ведущий задаёт адресный вопрос и продолжает независимые работы. Непрерывность
не отменяет review gates, разграничение файлов, согласованные требования,
честные FAIL/NOT VERIFIED и обязательные разрешения среды.

Утверждён пользователем 2026-10-18: оформить и сразу выполнять, включая реальные
изменения программной логики. Границы AGENTS.md сохраняются. Это локальный цикл,
без публикации, загрузки в контроллер и изменения hardware/global parameters.

R&D добавляет устойчивую остановку/продолжение внутри исходной полной рабочей
последовательности. Сохранять её шаги, кроме явно согласованных изменений;
соответствие исходных фаз и границ R&D обосновывать кодом, не названиями.
Приоритет по конкретному сценарию: последнее согласованное решение пользователя
в его контексте → утверждённые требования намеренных изменений → reference
сохраняемого поведения. Предварительные/исторические документы не override.
Оставшийся конфликт реакции требует вопроса, не самовольного выбора.

Уточнение границ: запрещены hardware mappings, физические настройки и
аппаратные/групповые конфигурационные параметры; обычные программные переменные
и связи можно менять по плану. Заданные таймеры не менять. Техническую границу
параметра сначала изучить; если неясна — спросить, не расширяя hardware scope.

Последнее решение после разговора пользователя с инженером Нивом:
Door Monitoring (in_Door_Monitor) только для соленоида открытия крышки.
В energy advance guards заменить его проверкой обоих in_InterLock_NC_1/2,
не путать с in_ES_NC_1/2. Существующую Unlock роль сохранять; других
изменений её поведения этим решением не вводить. Прежнее сохранение
DoorMonitor energy guards отменено. EStop/прочие разрешения сохраняются,
hardware mappings не менять; аппаратная валидация не заявляется.
Read-only lock feedback trace остаётся справкой, не новым gate.

Действующее решение StartingRun R&D→Run: снять STO при принятом запуске,
не ожидая C2_FBK/HV Healthy. Другие разрешения/EStop и последующие
подтверждения Run сохраняются. Термины: снятие STO разрешает момент, поднятие
запрещает. Речь о программном порядке, не физическом нулевом времени.

Решения кнопок: single 0.5с / both 1с; **окно комбинации 250 мс включительно**,
симметрично для обоих порядков. BOTH отсчитывается с появления второй кнопки
при непрерывном совместном удержании. Изменение именно этого программного
окна явно разрешено пользователем; прочие заданные времена не менять.
При второй кнопке ровно на 500 мс (уже вне окна комбинации)
приоритет у уже квалифицированной одиночной, без ретроспективного StepUp из
той же попытки. Это симметрично для обоих порядков. Событие квалификации
отделять от условий выхода: зелёная ON по-прежнему снимает Unlock. Не
назначать неоговорённую длительность видимого импульса на границе скана.

Поздняя вторая (>250 мс) до single acceptance делает попытку недействительной
без ошибки: нет single/StepUp, нужна полная очистка. Если single уже принято,
поздняя вторая не отменяет/не откатывает/не прерывает начатый переход и не
создаёт новых команд до отпускания обеих+фильтра. На500 мс приоритетsingle.
Отдельное снятие удерживаемого Unlock зелёной сохраняется; это не rollback.
Число фильтра этим решением не изменено; другие abort-сценарии не определены.

Роли цикла: ведущий координатор → аналитик → архитектор → редактор →
независимый тестировщик → независимый ревьюер. Ведущий выполняет координацию
сам; отдельный агент-координатор не создаётся. Подготовительные чтение и
проектирование проверок могут идти параллельно при раздельном владении файлами.

1. Владелец запускает `npm run check:software` в SafetyTests. Неизменяемый
   снимок результатов сохраняется с SHA256 SAL, версией кода, требованиями,
   допущениями и исходным SAL. Историческая fixture не перезаписывается.
   Перед функциональным исполнением валидировать весь исходный SAL/SGVL:
   typed alias/global bindings, DSL wrappers, usage indices и один native
   wiredLink на новую пару портов. Не отбрасывать ошибочные связи выделением
   удобного подграфа; чтение runtime только по имени не структурная проверка.
2. Отдельный аналитик требований и сценариев изучает согласованные решения,
   требования, read-only reference и контрпримеры. Для сценария фиксирует
   исходное состояние, входы/события, ожидаемые состояния/выходы, исключения,
   конфликты и критерии проверки с трассировкой. Неполный/неоднозначный сценарий
   направляет пользователю, не придумывая oracle. Решения и открытые вопросы:
   SafetyTests/SCENARIO_DECISIONS.md. Технические решения оставляет архитектору.
3. Отдельный архитектор изучает reference, v2, требования и контрпримеры.
   Пишет конкретный пакет: блоки/связи, ожидаемое поведение, сохраняемые
   инварианты, приёмочные сценарии, разрешённые файлы и границы итерации.
   Новая функция R&D определяется требованиями v2, а не копированием reference.
   В точке готовности первичного тестового пакета перед редактором создать
   локальный checkpoint-коммит относящихся требований/правил/тестов/baseline.
   Честные FAIL сохраняются, зелёная приёмка для исходного checkpoint не нужна.
   Перед коммитом остановить запись исполнителей; исключить посторонние файлы
   и секреты. Если редактор уже начал, не переписывать историю reset/stash или
   откатом: чисто разделить при возможности, иначе явно назвать checkpoint
   текущим, включающим уже выполненные правки. Push этим не разрешён.
4. Отдельный редактор реализует пакет небольшими итерациями. После каждой —
   целевые проверки и регрессия; перед ревью — полный согласованный пакет.
   Ошибки стенда исправляются с обоснованием без ослабления требований.
5. Независимый тестировщик проектирует и выполняет проверки по утверждённым
   требованиям и reference, отдельно от редактора реализации и ревьюера.
   Проверяет разрешённые и запрещённые переходы, временные границы, исключения,
   конфликты команд, аварийные сочетания, сброс и рестарт в пределах итерации.
   Самопроверки редактора сохраняются, но не заменяют независимую проверку.
   Тестировщик получает требования, проверенный архитектурный пакет, точный
   источник/SHA256 кандидата и результаты самопроверок. Использует готовые
   проверки после оценки их ожиданий и добавляет недостающее покрытие;
   не дублирует готовую работу без причины и не выводит oracle из реализации.
   Не ослабляет требования ради PASS и не исправляет реализацию. Дефекты
   возвращает редактору/архитектору, неоднозначности — аналитику через ведущего.
   Передаёт ревьюеру воспроизводимые команды, результаты с SHA256,
   FAIL/NOT VERIFIED, допущения и пределы покрытия. После изменения кандидата
   повторяет относящиеся проверки и согласованную регрессию.
6. Независимый ревьюер читает требования, план, фактический diff, тесты и
   результаты. Проверяет как новые связи, так и оставшиеся старые обходы.
   Зелёные тесты не заменяют ревью; программные тесты не доказывают hardware safety.
7. Существенные замечания возвращаются на соответствующий этап: требования
   аналитику, архитектура архитектору, код редактору. После исправлений повторяются
   относящиеся проверки, полный пакет и независимое ревью. Одинаковый неудачный
   подход не повторяется бесконечно: редактор сообщает архитектору, исследует
   причину и получает уточнённый подход.

Одновременно запись каждого файла принадлежит одному исполнителю. Владелец
ведёт статус и границы; аналитик пишет сценарии/решения; архитектор пишет план;
редактор меняет реализацию и её самопроверки; независимый тестировщик владеет
явно назначенными файлами независимых тестов и их результатов; ревьюер пишет
только отчёт ревью. Передача файлов явно оговаривается. Общие файлы тестов
нельзя одновременно поручать редактору и тестировщику. При нехватке слотов
ведущий ставит следующую роль в очередь и активирует после завершения занятого
этапа, сохраняя полезную текущую работу и независимость проверки.
При новых неоднозначностях любого этапа возвращаться к аналитику, затем при
необходимости пользователю. Полезная завершённая работа не отменяется;
приостанавливаются только зависимые изменения, остальные продолжаются.

Приёмка итерации: её требования проходят на фактическом SAL, нет новых
необъяснённых регрессий, существенные замечания закрыты. Незакрытые требования
общего проекта остаются FAIL/NOT VERIFIED и не скрываются. Финал всего задания:
все обязательные программные требования/проверки из
SafetyTests/SOFTWARE_ACCEPTANCE_SCOPE.md покрыты и пройдены, существенные
замечания закрыты, ограничения явно записаны. Зелёная модель не равна зелёному
SAL; необъяснённые FAIL и обязательное непокрытое поведение остаются открытыми.
Технические/модельные допущения имеют явные пределы; условные контрпримеры не
объявляются доказанными дефектами. Неизвестное поведение не заменяется oracle.
Native/hardware validation вне текущего объёма не является скрытым gate и не
выдаётся за выполненную. SAL CRC в XML не объявляется пересчитанным без native evidence.

Обычные подготовка, реализация, тестирование и возврат с ревью уже разрешены.
Для всех ролей: базовый вопрос ожидаемого сценария требует ответа пользователя,
если reference и утверждённые требования не дают однозначной реакции. Вопрос
содержит исходное состояние, последовательность входов/событий и недостающую
реакцию состояния/выхода/приоритета. Не вводить своё предположение как требование
или тестовый oracle; зависимый участок оставить без изменения, продолжать
независимые части. Отсутствие ответа не считать согласием.
Вопрос пользователю нужен лишь при влияющей на поведение неоднозначности после
изучения reference/требований, недоступных необходимых данных, выходе за объём
или конкретном блокере после исчерпания осмысленных вариантов. Независимые части
продолжаются. Обязательные разрешения среды не обходятся.

## Команда Claude Code — действует с 2026-10-21 (утверждено Вадимом)

Заменяет исполнителей прежних циклов; принципы выше (ответственность ведущего,
честные FAIL/NV, вопросы через аналитика, приоритет источников) сохраняются.

**Роли** (`.claude/agents/`): ведущий — основная сессия; `v2-analyst`,
`v2-architect`, `v2-stand-engineer` (новая роль: симулятор/parser/мутации/
воспроизводимость), `v2-editor`, `v2-tester`, `v2-reviewer` — Opus;
`v2-runner` — Haiku, только прогоны. Агенты не запускают других агентов.

**Владение путями** проверяет PreToolUse-хук `.claude/hooks/path-guard.mjs`
(fail-closed: неизвестная роль или неназначенный путь — отказ; reference,
.tsproj/.xti/_Config — отказ всем; публикация в remote — отказ, срабатывает
и на упоминание команды в тексте Bash). Хук не разбирает команды Bash/PowerShell,
пишущие файлы: для них владение остаётся правилом роли.
Таблица владения: SafetyTests/program/README.md.

**Независимость:** тестировщик и ревьюер получают требования, план, SHA и diff;
материалы редактора — только после своего вердикта. Редактор работает
в изолированном worktree; перенос в canonical — по указанию ведущего после G4.

**Gates среза:**
- G0 вход: native-structure preflight, SHA canonical, нет открытых вопросов по зависимым ID.
- G1 тесты до кода: RED-baseline тестировщика; ревьюер подтверждает, что oracle из требований.
- G2 кандидат: самопроверки редактора, native CRC, сохранность Symbols/портов/блоков.
- G3 независимая проверка: тесты среза + полный регресс + мутации guard'ов
  среза (из плана архитектора) — каждая убита поведенческим тестом.
- G4 ревью ACCEPT → перенос → локальный checkpoint-коммит → обновление матрицы.
Повторная неудача одного подхода — к архитектору, не новая попытка редактора.

**Дорожная карта:** E0 укрепление стенда (семантика FB по документации
Beckhoff, незаданный вход = ошибка, мутации SAL, воспроизводимость без git) →
E1 F1 gates/перенос → E2 Safe+Armed: однозначное присвоение статусов, конфликт

**Экономия квоты (Вадим 2026-10-23, все четыре меры; лимит расходов не поднимается,
работа только в квоте Max 5x):**
1. Модели: Opus — аналитик, архитектор, независимый тестировщик, ревьюер;
   Sonnet — редактор (сборка по готовому плану) и инженер стенда; Haiku — прогонщик.
   Механические прогоны регресса/мутаций — через v2-runner или стенд, не Opus.
2. Ревью G1 — только в ключевых точках: перед G3 и перед G4/переносом, а не после
   каждой версии тестов. Промежуточные версии тестов — самопроверка тестировщика.
3. Отчёты агентов — коротко и на английском; решения Вадима и общение с ним — на русском.
4. Работа в окнах квоты: ведущий следит за 5-часовым и недельным лимитом; при
   приближении к исчерпанию (~90 %) — checkpoint: агенты сохраняют точку
   остановки, ведущий пишет заметку возобновления и делает локальный коммит
   относящихся файлов. После сброса — продолжение без повторной работы.

**Экономия контекста (Вадим, 2026-10-22).** Расход лимита определяется числом
шагов × размером накопленного контекста, а не объёмом ответа.
- *Сессии ведущего:* одна сессия — один этап (E0…E8) или один крупный срез.
  Новую сессию открывают на границе этапа или когда контекст разросся.
  Внутри этапа после каждого закрытого gate — `/compact`. Передача между сессиями
  только через файлы: `WORK_STATUS_AND_PLAN.md` (один экран: canonical SHA,
  текущий этап и gate, следующий шаг, открытые вопросы), `TRACE_MATRIX.json`,
  handoff ролей. Новая сессия начинает с них, а не с перечитывания истории.

  ведущий) в том же шаге обновляет строку дайджеста.
- *Вывод и большие файлы:* правила в каждом `.claude/agents/*.md`, раздел
  «Экономия контекста»; ведущий соблюдает их сам и указывает субагентам точные
  файлы/ID в задании.
- История статуса — `SafetyTests/program/lead/WORK_STATUS_HISTORY.md`, только чтение по необходимости.
