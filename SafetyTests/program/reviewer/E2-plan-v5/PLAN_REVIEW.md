### 1.2 Замечания

**R5-1 (существенно; уточнено §1.3 по Q-V7-01 «Г») — побочный эффект переноса Symbol на выход окна: Discharge Request держится при включённом контакторе

Symbols. Модель x3 (второй цикл, когда запрос уже выставлен предыдущим спуском):

| Переход | Перекрытие «команда ON ∧ Discharge Request» | STO |
|---|---|---|
| R&D→Run, v4/R1-подобно | [u, u+101] | снят с u |
| R&D→Run, **v5** | **[u, u+599]** | снят с u |
| Safe→R&D, v4 | [u1, u1+99] | — |
| Safe→R&D, **v5** | **[u1, u1+599]** | — |

- Reference этого места не содержит (Network11/12 — добавление v2; в reference запрос сбрасывается только в Network5), то есть
  это не сохраняемая последовательность, а момент v2, который v5 меняет **без решения**: вопрос 68 нормирует момент Run/R&D,
  а не момент снятия разряда.
- SPEC §7 (R&D→Run, предусловия) перечисляет «discharge request снят» среди предусловий. F1 уже отступает от этого на ~100 мс;
  v5 увеличивает перекрытие до 600 мс при снятом STO.
- Требуется: архитектору — либо сохранить прежний момент снятия (Symbol от отдельного условия без окна, ≈ +1…+2 FB на
  сторону), либо через аналитика получить решение о моменте снятия HV/LV Discharge Request при подъёме (исходно: R&D
  с выставленным после Run→R&D запросом; событие: BOTH, C2 ON; не хватает: в каком скане относительно u запрос должен
  быть снят — до/в u, по FBK ≈ u+100 или по подтверждению u+600). Тестировщику — после решения добавить проверку.

**R5-2 — окно стартует на u−1, а не в скане u.** x4: N12/FBAnd4 (вход WIN_C2) поднимается на скан раньше `out_HV_C2`
(выход ставится через RS и Symbol). Поэтому FBAnd6 истинно с u+499, отсчёт 0,1 с начинается за 1 скан до w, Run на u+600.
- RC-2 (нет Run ≤ u+599) и RC-3 (K+100 — наблюдение) выполняются; но запрет v7 «Run, отсчитанный от k < w (Run на k+101
  при k < u+500)» буквально нарушается в одной точке (k = u+499).
- Требуется: архитектору исправить текст §3.2 («окно начинается в скане u»); аналитику — согласовать формулировку v7
  (K+100 наблюдение против запрета k<w в точке u+600). Если аналитик сочтёт u+600 недопустимым — WIN_C2/WIN_C1 питать
  от сигнала скана u. Блокирует только эту точку оракула, не реализацию.

**R5-3 — M-E2a-21.** По решению аналитика (RC-UB) верхняя граница нормативна. x4 подтверждает: M-E2a-21 убивается RC-5 (iv)

## 1.3 Дополнение: ответы Вадима Q-V7-01 «Г», Q-V7-03 «А», Q-V7-04 «Б» (SCENARIO_DECISIONS `0fcb4f33…f2e0`)

**Q-V7-01 «Г» — запрос HV Discharge уровнем до принятого подъёма HV; «снятие запроса — только при принятом подъёме HV».**

Что сбрасывает запрос в R1/E2 (нетлист R1, v1/v2):
- `out_HV_Discharge_Request` = N1/FBRs7.RsOut; Reset ← N1/FBOr5, где в R1 активен **только** OrIn2 = `b_Reset_HV_Discharg_Req2`
  (OrIn1 = reference-сброс из Network5 деактивирован удалением Network5). Set ← N1/FBOr6 (спуски и аварийная цепь).
- Источник `b_Reset_HV_Discharg_Req2`: R1 — N12/FBAnd6 (TON 0,1 с от команды C2 ∧ C2_FBK ∧ HV норма), v5 — FBTon3.TonOut после окна.
- **Импульсным запрос не стал:** это RS-память, держится уровнем от выдачи до сброса (x3: после Run→R&D TRUE до следующего
  подъёма). Сбросов вне подъёма HV в R1/E2 нет — «не раньше» выполняется. Safe→R&D запрос не снимает (верно: это не подъём HV).
- **Но момент снятия не совпадает с принятием подъёма.** Принятие R&D→Run — грант GATE_020 → STATE_SU.Set (скан a ≈ u−1/u).
  Снятие в R1 — около a+102 (подтверждение Run), в v5 — около a+601 (x3: перекрытие «C2 ON ∧ запрос» [u, u+101] → [u, u+599],
  STO снят с u). Если подтверждение Run не наступает (нет FBK/HV, провал после окна, будущий abort E3/E6), запрос после
  принятого подъёма **не снимается вовсе**. Запрос, таким образом, привязан к подтверждению Run, а не к принятию подъёма.

Требуется (заменяет HV-часть R5-1):
- **Архитектору:** источник сброса FBRs7 перенести на сигнал принятого подъёма HV (грант R&D→Run: выход GATE_020 /
  установка STATE_SU — через Symbol, межсетевой wire не создавать). Тогда в E2a-RC Symbol `b_Reset_HV_Discharg_Req2` **не переносится
  на FBTon3.TonOut**; FBTon3.TonOut питает только DecIn1…4. В E4 добавить вторую причину сброса — вход в Config (в эскиз E4).
  Пересчитать порты (Symbol-usage меняет блок, число Symbols прежнее). Мутации: (1) deactivate нового входа сброса — убийца
  «после принятого R&D→Run запрос TRUE в a+2»; (2) сброс от квалификации BOTH вместо принятия — убийца «отклонённая попытка
  (REL01-e2, крышка открыта) снимает запрос».
- **Аналитику:** критерий DIS-HOLD — исходно R&D после Run→R&D (запрос TRUE); события: (а) принятый BOTH R&D→Run, (б) отклонённый
  BOTH (крышка/REL01-e2), (в) Safe→R&D после R&D→Safe, (г) Emergency и Restart; ожидается: запрос TRUE в каждом скане до скана
  принятия a, снят в [a, a+1] (q/q+1); при (б)–(г) TRUE без перерыва. Граница «принятие и одновременная аварийная причина» — по L1.
- **LV-часть R5-1 остаётся открытой:** Q-V7-01 касается только HV. Момент снятия `out_LV_Discharge_Request` при Safe→R&D
  (сейчас ≈ u1+100, в v5 u1+600) решением не задан — вопрос аналитику (исходно: Safe после R&D→Safe, запрос LV TRUE; событие:
  принятый Safe→R&D, C1 ON; не хватает: снимать в скане принятия, по FBK или по подтверждению R&D). По аналогии с «Г» — вероятно,
  при принятии; без ответа не закреплять.
