# S1-Q2 - discharge requests after group start (analyst finding, 2026-10-23)

Question (tester S1): boot -> Emergency -> Restart -> Safe, no previous descent. E2d has
out_LV_Discharge_Request / out_HV_Discharge_Request FALSE in Safe and R&D. Preserved, or must the
request be active whenever the contactor is off (also after boot)?

Answer: DETERMINED by reference + decisions -> option (b): FALSE after boot is preserved behaviour.
No Vadim question needed.

## (1) Reference 4495a1f (MEN001_Dyno HEAD == 4495a1f, read-only)
File MEN001_Dyno/Safety_Dyno/TwinSafeGroup1/TwinSafeGroup1.sal:
- out_LV_Discharge_Request <- //Network1/FBRs5/RsOut (safeRs, reset-dominant);
  Set = FBOr2(GVL1.b_Set_LV_Discharge_Request), Reset = FBOr1(GVL1.b_Reset_LV_Discharge_Req).
- out_HV_Discharge_Request <- //Network1/FBRs7/RsOut (safeRs);
  Set = FBOr6(GVL1.b_Set_HV_Discharge_Request), Reset = FBOr5(GVL1.b_Reset_HV_Discharg_Req).
- Only Set writers: Network7/FBDecouple1.DecOut1 gated by GVL1.b_Step4 (LV, descent step);
  Network8/FBDecouple1.DecOut3 gated by GVL1.b_Step5 (HV, descent step).
- Reset writers: Network5/FBDecouple2 DecOut1/DecOut3 (ascent sequence) - same as TD-01 trace.
- Network4 (Step reset path) resets Step3..6 and sets Step1 directly; it does not pass Step4/5
  and does not write any discharge Set.
- safeRs output is FALSE at group start (no init/set path at boot). => after boot both requests
  FALSE until the first descent (Step4 / Step5) sets them.

## (2) Canonical F1 (v2 MEN001_Dyno/Safety_Dyno/TwinSafeGroup1, last commit 0391fae)
Same latches (Network1/FBRs5, FBRs7). Additional Set inputs only from descent/abort paths:
b_Set_LV_Discharge_Request (Network7, b_Step4), b_Set_LV_Discharge_Request_2 (Network12 "RnDStep"),
b_Set_HV_Discharge_Request (Network8, b_Step5), b_Set_HV_Discharge_Request_3 (Network6 FBDecouple2,
with STO reset outputs). No boot set path. => FALSE after boot, like reference.

## (3) Decisions
- Q-V7-01 "Г" + вопрос 73 "А": HV request "однажды выданный в последовательности спуска ...
  удерживается уровнем до следующего подъёма" - held from issue, i.e. exists only after a descent.
- TD-01 / вопрос 74 "А": LV request "держится уровнем от выдачи до принятого подъёма LV";
  Emergency/Restart do not clear it (and do not create it).
- Q-ARCH-01: Emergency chain issues LV/HV discharge only for the energized cases (LV ON / HV ON).
  Emergency in Safe right after boot (energy already off) - no decision requires a discharge.
- No decision / SPEC §§19-20 / SCOPE row requires "request ON whenever contactor OFF".
- Prior criteria already use this: analyst/E2-Q76/CRITERIA.md R-RND "FALSE, если запрос с boot не
  выдавался - тогда «не меняется»".

## Test consequence
- U-02/U-03: precondition through a real descent (as the tester did) is correct.
- Boot -> Restart -> Safe/R&D without descent: oracle = request FALSE and unchanged (must not be
  set by Restart, not cleared). Asserting TRUE there would be an invented oracle.
- Not a hardware/protection claim: whether the physical circuit needs a request at power-up is
  outside software scope; if Vadim wants (a), it is a new requirement (behaviour change), not E2.
