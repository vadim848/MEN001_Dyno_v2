# FULL-NORMAL-01 — полный штатный цикл состояний

Цепочка:

```text
Safe -> StartingRnD -> R&D -> StartingRun -> Run
     -> StoppingSS1 -> HVDischarging -> HVDisconnecting
     -> R&D -> StoppingToSafe -> Safe
```

| Этап | Событие/feedback | Ожидаемое состояние | LV cmd | C2 cmd | SS1 | STO | Discharge |
|---|---|---|---:|---:|---:|---:|---:|
| 1 | Исходное состояние | Safe | 0 | 0 | 0 | 1 | 0 |
| 2 | Новый StepUp, DoorMonitor и исходные программные разрешения выполнены | StartingRnD | 1 | 0 | 0 | 1 | 0 |
| 3 | `LV_FBK=1` | R&D | 1 | 0 | 0 | 1 | 0 |
| 4 | Принят новый StepUp при остальных действующих разрешениях; C2/Healthy feedback ещё не требуется для снятия STO | StartingRun | 1 | 1 | 0 | 0 | 0 |
| 5 | `C2_FBK=1` и требуемый Healthy подтверждены | Run | 1 | 1 | 0 | 0 | 0 |
| 6 | Новый StepDown | StoppingSS1 | 1 | 1 | 1 | 0 | 0 |
| 7 | SS1 и штатная выдержка завершены | HVDischarging | 1 | 1 | 0 | 1 | 1 |
| 8 | `DischargeComplete/HV_Safe=1` | HVDisconnecting | 1 | 0 | 0 | 1 | 0 |
| 9 | `C2_FBK=0` | R&D | 1 | 0 | 0 | 1 | 0 |
| 10 | Новый StepDown | StoppingToSafe | 0 | 0 | 0 | 1 | 0 |
| 11 | `LV_FBK=0` | Safe | 0 | 0 | 0 | 1 | 0 |

Ключевые утверждения:

Раннее снятие STO в этапе4 утверждено пользователем 2026-10-18: «Разрешаю
мгновенно снятие STO, не надо ждать фидбэка» (D-STO-LAUNCH в
../SCENARIO_DECISIONS.md). Это разрешение момента при принятом launch,
не подтверждение Run и не отмена EStop/interlocks/прочих разрешений.
Отсутствие C2/HV Healthy feedback само по себе не задерживает этот момент.
Полная последовательность reference сохраняется кроме явно согласованных
изменений для устойчивого R&D; условные имена фаз не задают её redesign.

D-DOOR-CURRENT2026-10-19: обычный цифровой DoorMonitor через PLC и исходные
программные условия сохраняются. Новое отдельное locked-feedback условие
отложено до инженера/нового ответа пользователя, запуск сейчас им не блокировать.
Не обходить EStop/interlocks или другие исходные защитные цепи; не называть
DoorMonitor safe подтверждением. Таблица не доказывает их фактическую проверку.

Таблица — требуемый сценарий, не доказательство исполнения фактического SAL.
Completion/timeout oracle использовать после сопоставления существующей
последовательности reference; неизвестные детали не брать из предварительной
модели FEEDBACK_TIMEOUTS.md как утверждённые требования.

- каждое повышение требует нового жеста и пройденного release filter;
- по последнему D-CHORD250 интервал второй кнопки delta<=250мс включительно
  в обеих очередностях; затем обе непрерывно1с от второй кнопки. Поздняя
  вторая не создаёт StepUp; single остаётся0.5с, двойное принятие одной попытки
  запрещено. Старый chord500мс не является текущим oracle;
- D-LATE-SECOND: поздняя вторая доsingleaccepted игнорирует всю попытку без
  fault; послеsingleaccepted не отменяет принятую команду/начатый переход,
  не откатывает и не прерывает его. Новые команды только после обеOFF+фильтр.
  GreenON снимаетUnlock как heldoutput, а не отменяетcommand event;
- `Run` не объявляется до `C2_FBK=1`;
- во время SS1 C2 остаётся включён для регенерации;
- STO включается до разряда;
- discharge начинается при ещё включённом C2;
- C2 отключается только после подтверждения безопасного HV;
- `R&D` не объявляется до `C2_FBK=0`;
- `Safe` не объявляется до `LV_FBK=0`.
