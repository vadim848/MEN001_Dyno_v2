# Независимое ревью каталога диагностических причин — 2026-10-21

**Вердикт: каталог принят как предварительная архитектурная классификация; это не приёмка реализации Fault.** Для основной сводки использовать **17 укрупнённых кандидатов /24 детализированных обозначения**, включая две причины без привязанных входов. Утверждать «найдены все возможные ошибки» либо «уже реализованы17 ошибок» нельзя.

## Независимо проверено

Прочитаны REQUEST, ARCHITECT, ANALYST, VERIFICATION, действующие пункты1–15 SCENARIO_DECISIONS, отмена предложений Нива, SPEC и emergency requirements. Сначала просмотрен подтверждённый reference, затем текущий SAL. До разбора текущего SAL самостоятельно повторены native-serialization preflight PASS:14 Networks/254 блока/2172 порта/75 Symbols/319 wires/0 межсетевых графических wire; typed SAL/SGVL bindings PASS без ошибок. - SGVL `c31e129072e2837234e376e51038ff988a92373cbfea97b383fbf23536c7946b`.

Два текущих FB Error (`FBEstop1`, `WINDOW`) не имеют wire/global consumers; их наличие не доказывает прикладной Fault latch. Сигнал ErrorACK — команда квитирования, не вход причины ошибки. Фактические входы и success-gates подтверждают наблюдаемость отдельных условий, но не существование утверждённых timeout detectors и сохранения причин.

## Подсчёт и дедупликация

У ARCHITECT15 прикладных строк. Их детализация даёт22: +1 для каналов EStop, +1 для внешних interlock, +1 для C1 ON/OFF, +1 для C2 ON/OFF, +3 для двух STO/двух направлений. SPEC явно называет driver fault/watchdog; отсутствие отдельных входов не позволяет забыть эти требования. Поэтому общий **названный каталог =17/24**, из них2 причины пока без программного источника.

F15 допустим только как «не классифицированная иначе неудача принятого перехода». Его нельзя одновременно считать вторым корневым отказом поверх C1/C2/Healthy/STO и нельзя добавлять ещё отдельную причину просто за нахождение в SafetyFault/TransitionFault. Если будущий интерфейс использует F15 исключительно как общий статус, а не fallback-причину, получится16/23 с учётом driver/watchdog. Эта оговорка не отменяет согласованный reset после rollback.

F07/F08 — кандидаты требуемого контроля Healthy в соответствующем контексте, а не доказанные универсальные текущие детекторы. F09 отдельно обоснован явно названным HealthyLostDuringSS1 с особой реакцией/памятью. F13 и C2-OFF mismatch могут быть симптомами одного эпизода; отсутствие подтверждения и его timeout не создают две независимые причины автоматически. Для C3/BMS нет отдельных подтверждающих входов: нынешний каталог не заявляет их раздельную диагностируемость, оставляя интерфейсный пробел видимым.

Исторические/альтернативные11 аналитических umbrella-категорий нельзя складывать с15 строками архитектора. После замечания ревью заключение ANALYST исправлено и повторно прочитано: оно согласовано с ARCHITECT и VERIFICATION — **15/22 прикладных +2/2 непривязанных =17/24 всего**. Замечание о несогласованном знаменателе закрыто; в финальной сводке применять эту единую запись.

## Ёмкость и границы

- 4бита с0 дают15 ненулевых номеров: помещают только выбранную прикладную группировку15 без запаса; не весь названный каталог17 и не детализацию24.
- 5бит дают31 ненулевой номер: помещают17 либо24 при данной классификации. Это оценка ёмкости, не решение реализовать номера.
- Пять native group diagnostic категорий оставлены отдельно: их нельзя молча прибавить как пять наблюдаемых прикладных root causes. Необходимо отдельно решить доступность и перекрытие;29 — лишь условная верхняя арифметика перечисленных обозначений.
- При нескольких причинах один номер потребует политики выбора/истории. Защитный приоритет действий не задаёт приоритет диагностического номера. Битовая маска и код-перечисление имеют разную ёмкость.

Нормальные ожидания, запрет up до принятия, отсутствие connector в Safe, открытая крышка в допустимом режиме, некорректная попытка кнопок и BOTH в Armed не включаются в Fault автоматически. Код0 может означать отсутствие выбранной ошибки при заблокированной операции.

Последнее предложение об одном BOOL Fault и мигании остаётся будущим вариантом: TwinSAFE передаёт признак, PLC реализует индикацию зелёной/синей; ориентир200мс не принят как новый SAL timer. Зелёная/синяя уточнены пользователем. Reset SafetyFault после завершённого rollback, узкий HealthyLost edge-reset и FB Restart не объединены в одно новое правило. Никаких новых требований, детекторов, fault memory, transport/mapping или приоритетов этим ревью не введено.

Достаточно документов и структурной проверки: функциональный прогон неизменённой реализации не доказал бы реализованность предложенного каталога. SAL/SGVL/PLC, тесты и настройки не менялись; reviewer записал только этот REVIEW.md. Runtime completeness, полная достижимость, native/online/hardware validation не заявляются.
