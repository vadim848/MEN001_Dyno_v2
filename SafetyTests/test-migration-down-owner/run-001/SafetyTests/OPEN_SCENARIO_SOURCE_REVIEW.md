## 1. Q-TRANSITION-DOWN

Что установлено:

- SPEC§15 прямо допускает две реакции на новую зелёную во время Transition:
  «не принимается либо ... abort-down». §13 даёт down приоритет, но не задаёт
  конкретного нового действия для уже выполняемого up.
- Reference Network2 green через FBTon3/FBAnd4 создаёт Step2Set, после чего
  Network5 подключает источники и выполняет подтверждения. Network5/FBAnd7
  создаёт Step1Set3 при Step2, дополнительном инвертированном входе и
  NOT EStopOK. Это ветвь возврата при снятом EStopOK, не явно новая зелёная.
- Reference Network6/FBAnd1 квалифицирует Step3; FBAnd2 при NOT общей
  защитной цепи FBAnd9 выдаёт Step4Set через FBDecouple1. Это аварийное
  снятие, не доказательство green abort в процессе подключения.
- D-LATE-SECOND запрещает отменять уже принятую single из-за поздней второй
  кнопки. Оно явно не задаёт другие abort-сценарии и не отвечает на новый
  самостоятельный green после полноценной очистки.

Вывод: reference подтверждает сохранение аварийного пути, но не устраняет
альтернативу §15 для новой штатной команды во время нового R&D up.

Единственный неразрешённый сценарий: R&D→StartingRun уже принят, C2 feedback
ещё не подтвердился; оператор полностью отпустил обе кнопки, выдержал
существующий release filter, затем удержал только зелёную0.5с. Аварии нет,
исходные разрешения исправны. Игнорировать новую команду и завершить launch
или начать abort-down? Только если выбирается abort — требуется указать
конечный режим и условия завершения, не подставлять новую процедуру самим.

Независимо можно проверять сохранение аварийного приоритета, запрет нового
up во время перехода MOD-004 и отсутствие ложного abort от late-second.

## 2. Q-FAULT-DESTINATION

Что установлено:

- SPEC§13/EMG-012 требует StateConflict→Emergency/TransitionFault, оставляя
  альтернативу. §14 запрещает неоднозначное основное владение.
- Reference Network3 содержит шесть отдельных RS для Step1–Step6 и
  направленные reset зависимости: Step2 reset Step1, Step3 reset Step2,
  Step4 reset Step3, Step5 reset Step4, Step6 reset Step5, Step1 reset Step6.
  Это обычное владение исходной последовательностью, не полный pairwise
  conflict detector, выбирающий один из новых статусов.
- Reference Network3/FBAnd1: in_Safety_Run AND EStopOK AND NOT всех шести
  шагов → FBOr2→Step1Set. Поэтому отсутствие всех step bits в исходном
  программном старте может быть путём инициализации Safe, а не всегда fault.
  Нельзя автоматически применять новый zero-hot fault ко всем таким сканам.
- В reference нет нового отдельного TransitionFault mode, который мог бы
  однозначно задать ожидаемый destination нового R&D state conflict.

Вывод: отрицательный oracle «одновременно Safe и Run недопустимы» уже
определён, но exact destination/recovery не выбирается кодом reference
для нового программного обработчика. Это не основание оставлять конфликт.

Неразрешённый сценарий: после завершённой инициализации, вне штатного handoff,
обнаружены одновременно Safe и Run (либо ни одного допустимого основного
режима при отсутствии перехода). Какой статус должен защёлкнуться — Emergency
или TransitionFault — и применяется ли существующая ручная аварийная процедура
восстановления в Safe? Стартовый all-zero путь исключить из этого сценария.

Независимо можно проверять фактические writers/reset связей, невозможность
нового повышения при конфликте и отсутствие ошибочного присвоения normal Run.

## 3. Q-COMPLETION

Что установлено:

- SPEC§10/STP-003 однозначно задаёт discharge timeout → TransitionFault,
  UnlockFALSE, ошибка зафиксирована; автоматическое продолжение запрещено.
  Новый вопрос о самом fault/блокировке открытия не нужен.
- Reference Network8/FBDecouple1 DecOut3 пишет SetHVDischargeRequest;
  FBton1 имеет1с. Далее FBOr1→FBTon2(1с) пишет ResetHVC2_2,
  FBAnd3 совмещает TON2 с дополнительным инвертированным входом для Step6Set.
  Это существующая timed removal последовательность, не явный timeout
  ожидания отдельного DischargeComplete с новыми выходами TransitionFault.
- Среди SAL variable names reference нет отдельного DischargeComplete/HVSafe/
  Timeout/Fault входа. Это ограничение интерфейса кода, не физическое утверждение.
- FEEDBACK_TIMEOUTS.md прямо предварителен: его5/10с и конкретное удержание
  C2/discharge при fault не являются окончательным oracle. Заданные reference
  времена не пересматривать и не переименовывать hold delay в timeout.

Вывод: существующую последовательность нужно сохранять с явно согласованными
изменениями. Нельзя вводить выдуманный completion вход или ошибочно считать
текущую выдержку доказанным новым discharge timeout. Сначала архитектор
сопоставляет реальный completion/timeout predicate в используемой цепи.

Только оставшийся вопрос, если нужен новый timeout fault path: в фазе разряда
источник/C2 подключены, discharge requestTRUE; предусмотренное программное
подтверждение не получено до установленного предела. TransitionFault,
UnlockFALSE и запрет автоматического продолжения уже заданы. Какими должны
остаться команды C2 и discharge после fault и какое новое ручное действие
разрешает выход? Не спрашивать/пересматривать здесь физические времена.

## Связь с обязательными ID и следующими пакетами

| Область | Уже определено и проверяемо | Ещё не определено |
|---|---|---|
| MOD-004 / штатный down conflict | Новые up в Transition не принимаются; late-second не отменяет принятое | Новый отдельный green в незавершённом launch: ignore/abort-down |
| EMG-012 / MOD-006 | Однозначное владение; normal Safe+Run запрещено; учитывать исходный startup | Конкретный conflict destination/recovery вне startup |
| STP-003 | Timeout fault, UnlockFALSE, latch ошибки, no auto continue | C2/discharge после нового timeout и выход из fault; сначала определить реальный software predicate |
| EMG-010 / STP-002/004 | Порядок discharge→C2 OFF→feedback→R&D по согласованному требованию | Новая отказная процедура не выводится из предварительной модели |

Это подготовка backlog, не новые нормативные тесты. Не требуется задавать
пользователю все вопросы немедленно: зависимый малый пакет уточняется перед
реализацией, независимые структурные исправления/разрешения продолжаются.
Зелёные исторические воспроизведения и компонентные тесты не закрывают эти ID.
