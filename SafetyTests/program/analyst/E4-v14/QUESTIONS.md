# E4-v14 — вопросы Вадиму (через ведущего, одним списком)

2026-10-21, v2-analyst. Не дублируют 5 вопросов ведущего (статус v1.4; новые
PLC↔TwinSAFE сигналы в конфигурации группы; источник нулевых скорости/тока и SS1;
первый UP после Emergency только физически; closed+locked = InterLock NC1∧NC2).
Q-E4V14-09 — уточнение к вопросу 5 ведущего, Q-02/03 зависят от ответа на
вопрос 2 ведущего. Формат: исходное состояние → события → какой реакции не хватает.

**Q-E4V14-01 — жест снятия аварии (T09, T19, T27–T28; EMG-006; C19).**
Исходно: Emergency защёлкнут по in_Estop_PLC (или Mentee), причина уже снята,
гриб E-Stop не нажимался; энергия снята. События: вариант A — только нажатие
и отпускание зелёной; вариант B — только нажатие и отпускание гриба;
вариант C — гриб, затем зелёная. Не хватает: какой вариант переводит в Safe?
Сейчас по вашему решению №12 Restart FB EStop выполняет зелёная (A); v1.4
требует гриб (B) «даже если аварию вызвал не он». Заменяет ли v1.4 зелёную,
или нужно оба (C)? Условия SPEC §12 (снята энергия, feedback OFF, только Safe)
сохраняются в любом варианте.

**Q-E4V14-02 — кодировка, если остаются 2 бита (T23, T36–T37; §3 TRACE; C14).**
Только если на вопрос 2 ведущего ответ «новые сигналы не добавлять».
Исходно: устойчивый Run (и отдельно устойчивый R&D), кнопки отпущены.
События: PLC выполняет «Armed→RnD» — по таблице-комментарию код 01, по CASE
фактически пишет 10; PLC без запросов держит значение по умолчанию 00
(`n_SafeSate=0` = «RnD_2_Safe»). Не хватает: (a) какой код правильный для
Run→R&D — 01 (так декодирует TwinSAFE) или 10 (так пишет PLC)? (b) 00 — это
«нет запроса» или команда R&D→Safe? Сейчас в TwinSAFE 00 в R&D ничего не делает
(ветвь отключена входом False), а в Run 00 обязателен для разрешения SS1; если
сделать 00 командой R&D→Safe при постоянном 00, R&D будет сразу сбрасываться.

**Q-E4V14-03 — что считать новым PLC-запросом (C14; MOD-003).**
Исходно: устойчивый R&D, InterLock в норме, кнопки отпущены, PLC держит код
Safe→R&D (10) после уже выполненного перехода. Событие: PLC меняет код прямо на
R&D→Run (11), без промежуточного «нет запроса». Не хватает: является ли такая
смена кода новым запросом R&D→Run (переход выполняется), или запрос считается
новым только после возврата PLC в «нет запроса» (переход не выполняется)?
Удерживаемый неизменный код новым запросом не является (MOD-003) — это не
спрашивается.

**Q-E4V14-04 — PLC-запрос при нажатой кнопке (QP-уточнение на пересмотре; C11, C15).**
Исходно: устойчивый R&D. События: (a) зелёная нажата 200 мс (ещё не
квалифицирована), в это время PLC присылает запрос R&D→Run, затем зелёная
отпущена; (b) синяя квалифицирована, Unlock активен, PLC присылает R&D→Run.
Не хватает: прежнее правило «если хотя бы одна кнопка нажата — запрос PLC
игнорируется, после отпускания не исполняется» остаётся в силе для всех
PLC-команд (кроме аварийной), включая Safe→R&D и R&D→Safe? В (b): игнор PLC
при удерживаемой синей?

**Q-E4V14-05 — команда не своего режима и PLC DOWN в переходной фазе (C16; MOD-004).**
(a) Исходно: устойчивый R&D. Событие: приходит CMD_SAFE_TO_R&D (предназначен для
Safe). Не хватает: игнорировать (не трактовать как «вверх» → Run)? Аналогично
CMD_RUN_TO_R&D в R&D (не трактовать как R&D→Safe)?
(b) Исходно: принятый R&D→Run, STO уже снят (StartingRun). Событие:
CMD_RUN_TO_R&D от PLC. Не хватает: действует так же, как зелёная по решению
D-STARTINGRUN-GREEN-DOWN (прерывание и Run→R&D), или игнорируется до Run?
(c) Исходно: идёт Safe→R&D, LV ещё не подтверждён. Событие: CMD_R&D_TO_SAFE.
Не хватает: игнор или прерывание вниз в Safe?

**Q-E4V14-06 — battery/BMS в R&D (T10, T49; MOD-001/005; C21).**
Исходно: устойчивый Safe. Событие: принятый Safe→R&D. Не хватает: должна ли
TwinSAFE при входе в R&D автоматически включить battery relay (C3) и BMS relay,
как пишет v1.4 («R&D = PS1 + battery + BMS»)? Сейчас они включаются только
отдельными PLC-командами Manual On/Off в R&D/Run, а в исходной последовательности
— только в Run. При R&D→Safe и аварии они выключаются в обоих вариантах.

**Q-E4V14-07 — сигнал inPLC_BypassC1C2 (T14; MOD-007; C09, C22).**
Исходно: устойчивый Safe, всё в норме, кнопки отпущены. Событие: PLC ставит
Bypass_C1C2 = TRUE. Сейчас TwinSAFE включает оба контактора C1 (LV) и C2 (HV)
без режима и жеста и сама выключает их через 10 с; в reference этого нет, в v1.4
сигнала нет, SPEC §17 запрещает включение опасной энергии одиночным PLC-битом.
Не хватает: удалить функцию, оставить только как сервисную при каком-то условии
(каком?), или оставить как есть?

**Q-E4V14-08 — heartbeat PLC↔TwinSAFE (T32–T34; C20).**
Зависит от вопроса 2 ведущего (новый сигнал). Исходно: любой режим, PLC
перестаёт обновлять heartbeat. Не хватает: (a) нужен ли heartbeat в текущем
объёме; (b) значение таймаута (в v1.4 PLACEHOLDER). Реакция по v1.4 —
защёлкнутый Emergency с физическим восстановлением. Это не тот watchdog,
который вы определили для E6 (C1/C2 feedback 500 мс, Healthy 30 с).

**Q-E4V14-09 — уточнение к вопросу 5 ведущего: открытая крышка в R&D (C04/C05, C18; EMG-002, CVR-003).**
Исходно: устойчивый R&D (и отдельно Safe). Событие: оператор открывает крышку
синей кнопкой — если InterLock NC1∧NC2 и есть «closed + locked», то оба NC
становятся FALSE. Не хватает: это просто запрет UP без аварии (как пишут v1.4
и CVR-003 «крышка может быть открыта неограниченно в Safe/R&D без fault»), или
Emergency по §5.1/EMG-002 («потеря любого канала External Emergency Interlock —
Emergency»)? Сейчас в коде в Safe/R&D потеря NC только блокирует повышение,
в Run запускает защитный сброс.

## Информация для Вадима (без вопроса)
- v1.4 «short press SAFETY RESET» — действует ваше решение: зелёная непрерывно 0,5 с.
- v1.4 оставляет тайминг dual press открытым — у нас утверждено: окно 250 мс,
  BOTH 1 с, single 0,5 с, пауза 2 с.
- v1.4 §8 утверждает, что сейчас PLC видит только кнопки — фактически TwinSAFE
  отдаёт 11 статусов (C1/C2 FBK, E-Stop NC1/NC2, Mentee, Healthy, разъёмы, STO)
  и шаги; статуса крышки/InterLock среди них нет.
