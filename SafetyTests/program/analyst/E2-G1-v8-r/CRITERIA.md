## 1. N19 — как наблюдать StartingRun (FBK-05, STP-I)

### 1.1 Что требуется (утверждённые требования, не TEAM-DEFAULT)

- **SPEC §2:** StartingRun — переходная фаза, а не основное состояние.
- **SPEC §14 (one-hot):** в каждый момент активно ровно одно основное состояние: Emergency XOR Safe XOR R&D XOR Run.
- **SPEC §7 и MOD-002:** Run устанавливается только после подтверждений. StartingRun нельзя считать Run.
- **MOD-006:** основные режимы однозначны; фазы — отдельно от режимов.
- Вывод для StartingRun и его abort: основное состояние — **R&D**. Это единственное из четырёх, которое не
  противоречит MOD-002: не Run, не Safe, не Emergency. Фаза наблюдается отдельно.
- Вывод для Safe→R&D: по MOD-001 R&D ставится только после feedback, поэтому основное состояние — **Safe**,
  фаза — отдельно.
- **Поправка к собственному критерию.** Формулировки E2-G1-v7-q §3.3 «статус StartingRun (не R&D, не Run)» и
  «статус Safe→R&D (не Safe, не R&D)» не имели источника и противоречат SPEC §14. Они **заменены** этим пунктом.
  Ошибка была в критерии аналитика, а не в тесте; в v7-q §3.3 поставлена пометка.

Факт (E2b v7.2, E2d v7.4.1, E2d v7.5, справка):
- StartingRun: стадия `b_Step_RnD`, статус STS_RND, `recRndC_SU` TRUE, C2 ON, STO снят, `outPLC_RnD` TRUE;
- Safe→R&D: стадия `b_Step12`, статус STS_SAFE, `outPLC_RnD` FALSE.

### 1.2 Наблюдение фазы (TD-14, мера)

- **Начало StartingRun** (кнопочный путь) — A по TD-08.
- **Фаза StartingRun в скане n:**
  `SR(n) := recRndC_SU(n) ∧ основное состояние R&D(n) ∧ ¬Run(n)`.
  - Нет Symbol `recRndC_SU` → ERROR стенда, как в TD-08/TD-09. Переход на «не R&D» запрещён.
  - Если архитектор переименует или перенесёт маркер, определение следует за маркером защёлки принятого
    R&D→Run.
  - Legacy (1,1) SU не ставит. В v7.5 он отключён (вопрос 76 «Б»), поэтому здесь не рассматривается.
- **Фаза Safe→R&D:** `b_Step12 ∨ (out_LV_C1 ∧ основное Safe)`, как A Safe→R&D в TD-08.
- **Поведенческие предикаты проверяются отдельно от маркера и статуса и сами по себе:**
  - «StartingRun удерживается»: STO снят ∧ `out_HV_C2` TRUE ∧ SS1 не выдан ∧ `out_HV_Discharge_Request` FALSE
    ∧ ¬Run;
  - «Safe→R&D удерживается»: `out_LV_C1` TRUE ∧ `out_LV_Discharge_Request` FALSE ∧ не R&D.
  - Признак отката или abort — изменение этих выходов (STO активен, C2 OFF, Discharge, SS1; для 06 — C1 OFF).
    Основное состояние R&D/Safe признаком отката **не является**.

### 1.3 Конец abort StartingRun — для `pos()` (TD-14, мера)

- **R_end** — первый скан ≥ a, где одновременно `out_HV_C2` FALSE ∧ `in_HV_C2_FBK` FALSE ∧ STO активен
  (STO_DR1 и STO_DR2). Здесь a — скан квалификации зелёной (FBK-05-POS) или скан причины c (STP-I).
  Это «R&D после C2_FBK OFF» из STP-006 / Q-ARCH-03 в наблюдаемой форме.
- **`pos()` (05):** снять `in_HV_Faulty_FBK` в R_end+1. Не по стадии `b_Step_RnD` и не по STS_RND.
- **R_end не наступил к t_d + T_DIS + 3000 мс** (t_d — скан Discharge) → FAIL «abort не завершён», а не
  пропуск. Если Discharge не выдан вовсе — FAIL по таблице STP-006.
- **После `pos()`.** Если маркер SU всё ещё стоит и кандидат возобновляет запуск (C2 ON, STO снят, Run) —
  это **FAIL «не возобновляется»** (STP-006, V14-Q12), а не ошибка теста. Маркер SU после R_end —
  diagnostic; нормой служит отсутствие возобновления ≥ 3000 мс.
- **Положительный хвост (READY-D, по желанию тестировщика):** после R_end+1 и очистки кнопок ≥ 2001 мс
  новый BOTH из R&D принимается штатно (StartingRun → Run по RUN-CONF). Значит, фаза действительно
  завершилась. Источник: SPEC §15 (R&D: обе → R&D→Run), STP-006 «→ R&D».

### 1.4 Статус — отдельной проверкой

| Проверка | Норма | Статус |
|---|---|---|
| S1. Основное состояние в StartingRun и во время abort | ровно одно, R&D, в каждом скане [A, R_end]; Run ни в одном скане, если Run не подтверждён по RUN-CONF | **READY** (SPEC §2/§14, MOD-002, MOD-006) |
| S2. Основное состояние в Safe→R&D | ровно одно, Safe, до подтверждения R&D | **READY** (SPEC §14, MOD-001) |
| S3. Фаза отдельно от режима | маркер фазы (SR / `b_Step12`) TRUE в фазе и FALSE в устойчивом R&D/Safe | READY-D (MOD-006; маркер по TD-14) |
| S4. PLC-индикация `outPLC_RnD` в StartingRun, abort и Safe→R&D | ~~BLOCKED (Q-V8R-01)~~ → **READY** по вопросу 78 «А» (Вадим, 2026-10-22), границы §1.4b | READY |

- S1–S4 — отдельные проверки. Поведенческие предикаты FBK-05 (§1.2) от них не зависят.
- Падение S1/S4 не должно маскировать поведенческий PASS/FAIL, и наоборот.
- Факт: на кандидатах S1 и S2 PASS (по снимку), `outPLC_RnD` TRUE в SU и FALSE в `b_Step12`.

### 1.4b S4 — `outPLC_RnD` по сканам (READY; вопрос 78 «А», RND-CONF-T, RUN-CONF-T)

**Источник.** Вопрос 78 (Q-V8R-01), ответ Вадима «А»:
- `outPLC_RnD` TRUE в StartingRun и во время его abort (→ R&D);
- FALSE во время Safe→R&D, пока R&D не достигнут (подтверждён);
- новых сигналов нет.

Reference 4495a1f `outPLC_RnD` не имеет (добавление v2), моменты из него не выводятся.

**Мера.** `outPLC_RnD` — PLC-копия основного состояния R&D (S1/S2). Моменты отсчитываются от наблюдаемого
подтверждения R&D (RND-CONF-T) и Run (RUN-CONF-T), а не от стадий реализации. Допуск передачи в PLC — 1 скан
(конвенция L2 Imm «≤ +1»).

**(a) Safe→R&D** — исходно устойчивый Safe, `outPLC_RnD` FALSE; BOTH (или legacy (1,0)) → A1 (TD-08), u1 — C1 ON;
K1 — по RND-CONF-T (K1 = max(k1, u1+500)), τ_R — первый скан основного R&D.

| Скан | Норма |
|---|---|
| каждый скан [A1, K1+99] | FALSE (R&D не достигнут; R&D нет ≤ K1+99) |
| K1+100 | наблюдение |
| K1+101 | наблюдение, если τ_R = K1+101 (допуск передачи 1 скан) |
| ≤ τ_R+1 и далее в каждом скане устойчивого R&D | TRUE |
| ≥ K1+102 без TRUE | FAIL (τ_R ≤ K1+101 по RND-CONF-T) |
| Откат Safe→R&D (WDG-01/02, abort V14-Q13) | FALSE в каждом скане до Safe и в Safe |

**(b) StartingRun и его abort** — исходно устойчивый R&D, `outPLC_RnD` TRUE; BOTH → A (TD-08), u, R_end (TD-14 §1.3).

| Скан | Норма |
|---|---|
| каждый скан [A−1, R_end] (включая u, abort, Discharge, C2 OFF, C2_FBK OFF) | TRUE — **без единого FALSE-скана** |
| R_end, R_end+1 и далее в устойчивом R&D | TRUE (abort → R&D: основное состояние не меняется) |
| граница c = A (abort/отказ в скане принятия) | TRUE в каждом скане — исход (i) отказ или подъём не влияет на R&D |

- Импульс FALSE на любом скане внутри [A−1, R_end+3000] — FAIL S4.
- Запрещено: TRUE→FALSE→TRUE на границе R_end.

**(c) StartingRun → Run** (граница фазы, для полноты) — K по RUN-CONF-T, τ_Run — первый скан основного Run:
- TRUE в каждом скане ≤ K+99 (Run нет);
- K+100, K+101 — наблюдение;
- FALSE не позже τ_Run+1 и в устойчивом Run;
- TRUE в скане, где основное состояние Run, допускается только в τ_Run (1 скан передачи).

**Не покрыто ответом 78** — NV, отдельные вопросы при необходимости:
- `outPLC_RnD` в R&D→Safe, в нормальном Run→R&D (SS1/выбег/разряд), в откате WDG-03 после Run-подтверждения;
- `outPLC_RnD` в Emergency.

Здесь не нормируются. Аналогия «копия основного состояния» напрашивается, но по D-TEAM п.4 значение PLC-сигнала —
интерфейс. Без ответа Вадима не закреплять.

**Аварийные сочетания:**
- Emergency во время StartingRun/abort — `outPLC_RnD` в Emergency не нормирован (NV, см. выше);
- выход состояния Emergency — по EMG-критериям.

### 1.5 Затронутые тесты

- **`current-e2d-fbk-window-abort` (FBK-05):**
  - -W — признак отката (`sign`) без `isRnD`, только выходы по §1.2;
  - -NEG — «StartingRun удерживается» по §1.2 и S1 отдельно, без `!isRnD`;
  - -POS — `pos()` по R_end (§1.3).
  - FBK-06 (Safe→R&D): «не Safe» заменить на «C1 ON ∧ не R&D» по §1.2; основное Safe — проверка S2.
- **STP-I (`current-e2c-stp-i`) затронут.** `tr` = первый `b_Step_RnD ∨ STS_RND` на кандидатах — уже скан c
  (StartingRun внутри R&D). Поэтому «R&D не раньше C2_FBK OFF» и «Safe > R&D» сравнивают не то.
  - Замена: tr := R_end (§1.3).
  - Проверки «C1 OFF ≥ tc», «Safe после C1_FBK OFF», «Safe > R_end», «нет Emergency», «не возобновляется»
    не меняются. S1 в [c, R_end] — отдельно.
- **Прочие тесты,** опознающие StartingRun как «не R&D» или «ни Run, ни R&D» (тестировщику проверить поиском:
  IL-05a, IL-05d(1), STP-E, WDG-03, RUN-CONF, dis-hold), — та же замена.
- **На F1 вывод не меняется.** R&D недостижим, это покрытие. Маркера SU нет: по TD-14 это ERROR предусловия
  там, где тест доходит до StartingRun.

## 2. m-21 — REL01-e2-LATE при A = s и l = never: допустим ли отказ

Ответ: **да, допустим**. TD-13 (E2-G1-v8-q §4.2), строка «A = s» — наблюдение, допустимы (i) и (ii).

- (i) **Отказ при A = s** засчитывается, если выполнено всё сразу:
  - нет Emergency и fault;
  - подъёма нет ни в одном скане до конца наблюдения, в том числе после восстановления крышки в s+100.
    Удержанный или защёлкнутый SU не должен исполниться позже (TD-07: «не исполнять отложенно»);
  - основное состояние R&D в каждом скане;
  - после отпускания и очистки ≥ 2001 мс новый жест принимается (строка «После отказа» REL01-e2-LATE).
    Это показывает, что принятие не «повисло».
- (ii) Emergency без повышения в скане ≥ s — тоже допустима.
- Маркер SU, поставленный в s и оставшийся TRUE при исходе (i), — diagnostic. Нормой служит отсутствие
  отложенного подъёма и приём нового жеста.
- Запрещено: «принят без Emergency» (подъём есть, Emergency нет); подъём в скане ≥ s.
- Тестировщику: при a = s и l = never требовать дизъюнкцию (i) ∨ (ii), а не только Emergency.

## 3. m-22 — E2b-dev §2.3 и (ii) TD-08 при c = A (TD-15, сведение)

- **Расхождение.** TD-08 §1.3 при c = A допускает (ii) «Emergency». Когда A определено самим выходом
  (legacy: A = u, первый C2 ON или снятие STO), (ii) читалось как «C2/STO в c, затем Emergency». E2b-dev §2.3
  запрещает новый C2 ON или снятие STO в любом скане с NC FALSE, включая первый.
- **Сведение (приоритет у §2.3, норма не новая):** при c = A **нового повышения в скане c нет ни в одном исходе**.
  - (i) отказ без Emergency — повышения нет по определению;
  - (ii) Emergency — повышения нет ни в c, ни позже (инвариант правила L Imm «в каждом скане ≥ e», IL-02,
    §2.3). Выход принятия в самом c при FALSE-разрешении в c — **FAIL**, не (ii).
- То же для Safe→R&D (connector, EMG4-03-A): C1 ON в скане c = A при FALSE connector в c — FAIL.
  Признак `b_Step12` в c при этом допустим как наблюдение.
- A по-прежнему берётся по трассе без события. Если A — выход, то «выход в A на трассе с событием» как раз
  и запрещён.
- Сфера: legacy (1,1) R&D→Run отключён в v7.5 (вопрос 76 «Б», срез `E2-Q76/`). Здесь только правило; на
  строки legacy действует срез E2-Q76.
- Источник: E2b-dev §2.3 (V14-Q5, IL-02), CRITERIA_DELTA_v4 §0.1 (L Imm), TD-08. Записано как TD-15
  (уточнение формулировки, не ослабление).

## 4. m-25 — K-2: Safe→R&D при `in_LV_Faulty_FBK` TRUE до жеста

### 4.1 Норма (READY, не TEAM-DEFAULT)

- **WDG-02 (REQ-CONSOLIDATION, READY):** Safe→R&D, `in_LV_Faulty_FBK` TRUE «с момента до C1 ON».
  - C1 включается.
  - От C1_FBK ON (t_f) — ожидание LV-нормы до 30 с:
    - FALSE к t_f+29999 → R&D;
    - TRUE к t_f+30000/+30001 → откат в Safe + SafetyFault.
- **Основа — вопрос 66(b) «да» (Вадим):** «при Safe→R&D 30 с от C1_FBK ON ограничивают всё ожидание
  подтверждения R&D (LV в норме)». Ответ предполагает, что LV-нормы при включении C1 может не быть.
  Ограничения «Faulty TRUE началось после жеста» в нём нет.
- **Ограничений в решениях Вадима нет.** Ни одно решение не делает LV Healthy условием **принятия** Safe→R&D:
  - E2-Q2(a) касается устойчивого R&D;
  - Q-RC-16 и Q-E2Q-02 — спуска;
  - Q-ARCH-03 — StartingRun.
  Таблица разрешений Safe→R&D (E2-G1-v2-questions/QUESTIONS.md) прямо указывает: LV/HV Healthy — «не условие
  принятия Safe→R&D» (WDG-02, HLT-02).
- **Отказ запуска — не TEAM-DEFAULT.** D-TEAM п.1 («ограничительнее») здесь неприменим: отказ противоречит
  ответу Вадима 66(b) (D-TEAM п.4). Сделать отказ нормой можно только новым решением Вадима; вопрос не
  задаётся, потому что поведение задано.

### 4.2 Факт (модель, справка)

| Источник | LV Faulty FALSE | LV Faulty TRUE с t−200 до BOTH |
|---|---|---|
| F1 canonical | S12 +1002, C1 +1004 (R&D на F1 недостижим — известное покрытие) | S12 +1002, C1 +1004, конец — `b_Step_RnD` (полярность N11/FBAnd4 на F1, D-ARCH-POL) |
| E2d v7.4.1 | C1 +1003, R&D | **S12 нет, C1 нет**, Safe. После снятия Faulty жест не исполняется (отложенного исполнения нет — верно) |
| E2d v7.5 (2276d773) | C1 +1003, R&D | **S12 нет, C1 нет**, Safe — как v7.4.1 |

Дополнительно на v7.4.1: Faulty TRUE с p+900 (во время удержания BOTH, до принятия) → C1 не включается.

### 4.3 Вывод

- **K-2 на E2d v7.4.1 и v7.5 — содержательный FAIL WDG-02 / MOD-001.** Не наблюдение и не допустимый отказ.
  - Новое условие запуска сверх утверждённых. Кроме того, F1 запуск при LV Faulty TRUE не запрещал.
  - Атрибуция и исправление — архитектору и редактору. По плану v7.5 гейта LV Faulty на принятии Safe→R&D нет;
    вероятно, это побочный эффект. Не атрибутировано.
- **База FBK-06-NEG/POS («Faulty TRUE с момента до C1 ON») нормативно достижима.**
  - На кандидатах её недостижимость — RED, относимый к K-2.
  - Это **не** «precondition not reached / покрытие» и не ERROR стенда. Тестировщику классифицировать как
    содержательный RED (K-2 / WDG-02).
- **Границы WDG-02 для теста:**
  - Faulty TRUE: с t ≤ p−200 (до жеста), с p+900 (во время BOTH), в скане A (`b_Step12`), в A+1;
  - во всех четырёх — C1 ON по трассе без события, ожидание до t_f+30 с;
  - Faulty FALSE к t_f+29999 → R&D; удержание → откат + SafetyFault на t_f+30001 (t_f+30000 — наблюдение).
- **Запрещено:** отказ запуска из-за LV Faulty; Emergency; исполнение жеста после снятия Faulty, если жест
  не был принят (в правильной реализации принятие и так уже произошло).
- **Аварийные сочетания:** без изменений WDG-02 (EStop/connector во время ожидания → Emergency, EMGREF-LV).

## 4b. K-2b — Unlock в Safe при `in_LV_Faulty_FBK` TRUE (V76-B, ревью плана v7.6)

### 4b.1 Норма (READY; reference + решения Вадима, не TEAM-DEFAULT)

**Reference 4495a1f, Network2** (прочитано через `git show 4495a1f:MEN001_Dyno/Safety_Dyno/TwinSafeGroup1/TwinSafeGroup1.sal`, вывод sha256 `c5f0c0cea479f65e…` — без CRLF-нормализации стенда; эталон стенда `efddc60b…c334`; парсер стенда):
- `out_Door_Unlock_Solonoeid` = FBRs1;
  - Set = FBAnd7 = FBDecouple3(`b_Step1`) ∧ `in_Relase_Door_PB`;
  - Reset = FBAnd8 = ¬`in_Door_Monitor` ∧ FBDecouple3(`b_Step1`).
- LV Healthy в reference читают только Network5/FBAnd3 (исходная последовательность запуска),
  Network6/FBAnd9 (Run) и Network10 (ретрансляция в PLC). В цепь Unlock он не входит.

**Решения Вадима:**
- Q-ARCH-04 «А» («как в reference»): в Safe квалифицированная синяя ≥ 500 мс выдаёт Unlock. «Прочие условия
  Unlock (EStopOK, PLC stop, только Safe/R&D, удержание/снятие) не меняются». LV Healthy в этом перечне нет.
- Q-ARCH-10 — то же для R&D.

**Вывод:** Unlock в устойчивом Safe **не зависит** от LV Healthy.
- Отказ Unlock из-за LV Faulty — новое условие, которого нет ни в reference, ни в решениях Вадима. Это FAIL
  Q-ARCH-04 / CVR-001, а не допустимое ограничение.
- Оценка по D-TEAM: Unlock — соленоид крышки, не энергия привода. В Safe энергия снята (SPEC §2: LV и HV
  выключены, STO). Норма воспроизводит существующее поведение reference и ответ Вадима: защиту не снимает,
  энергию не добавляет. Вопрос Вадиму не нужен.
- В Safe LV Faulty TRUE ничем не обрабатывается: PS1 в Safe выключен (E2-Q2(b) — аналогичное рассуждение
  Вадима для PS2 в R&D). Fault, SafetyFault и Emergency от него в Safe не задаются.

### 4b.2 Критерий UNL-LVF (READY)

- **Исходное состояние:** устойчивый Safe, кнопки отпущены ≥ 2000 мс, нет Emergency/SafetyFault, крышка любая
  (Q-ARCH-04).
- **Контроль X0:** те же входы при `in_LV_Faulty_FBK` FALSE.
- **Стимул:** синяя одна с P, удержание 600 мс (вариант — 2000 мс), затем отпускание. Зелёная FALSE.

| Момент TRUE `in_LV_Faulty_FBK` (удерживается до конца) | Ожидается |
|---|---|
| ≤ P−200 (до нажатия) | `out_Door_Unlock_Solonoeid` по сканам = X0: FALSE в [P, P+499], TRUE к P+501 (P+500 — наблюдение, BTN-004/T_SINGLE), удерживается до отпускания синей, FALSE после отпускания — как X0 |
| P+250, P+499, P+500, P+501 (во время квалификации) | то же = X0 |
| P+700 (Unlock уже TRUE) | Unlock остаётся TRUE до отпускания, = X0 |
| импульс TRUE 100 мс в [P−100, P+600] | = X0 |

- **Во всех строках:**
  - стадия Safe, статус Safe;
  - нет Emergency, SafetyFault, fault;
  - C1/C2 не включаются, STO не снимается.
- **Запрещено:**
  - Unlock FALSE в любом скане, где X0 даёт TRUE (отказ или задержка из-за LV Faulty);
  - Unlock TRUE раньше X0;
  - Emergency, SafetyFault или переход из-за LV Faulty в Safe.
- **Аварийные сочетания (без изменений):**
  - ES_NC_1/2 или `in_Estop_PLC` → Unlock FALSE (условие EStopOK);
  - зелёная → Unlock снимается (существующий hold gate);
  - LV Faulty при этих событиях исхода не меняет.
- **Факт (справка, со слов ведущего / ревью плана v7.6):**
  - E2a-RC, E2b и план v7.6 — Unlock на P+501, PASS;
  - E2c и E2d v7.5 — Unlock не включается, **FAIL UNL-LVF**.
  - Корень, вероятно, общий с K-2 (HLT_LV без стадии), не атрибутировано. Архитектору.
- **Не покрыто этим критерием:** Unlock в R&D при LV Faulty. Там потеря LV запускает цепной R&D→Safe
  (E2-Q2(a)), а Unlock в переходе — отдельный вопрос, вне V76-B.
- **ID:** CVR-001, CVR-002 (Unlock в Safe), BTN-004 (blue 500 / held gate в Safe). Источник: reference Network2,
  Q-ARCH-04 «А», D-PHYSICAL-UNLOCK-SCOPE, SPEC §2/§5.
