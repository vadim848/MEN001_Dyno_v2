## Q1 тестировщика — in_Safety_Run: какое значение задавать

### Что установлено программно (без аппаратного исследования)

1. **Объявление и привязки (canonical = reference 4495a1f, одинаково).** SAL-переменная
   `in_Safety_Run` (Id c8e3bd3c-13cc-4008-9721-90c96ea7ed1d), источник — стандартное PLC
   alias device `IN_SAFETY_RUN.sds` (SDSID 50, StandardAliasDevice, LinkingMode Manual, BIT).
   Потребители (targetUsages) ровно два:
   - групповой порт **`//RunStop`** группы TwinSafeGroup1;
   - `//Network3/FBAnd1/AndIn1` (контакт NC, т.е. прямое значение).
   В GVL1.sgvl переменной нет (ни в canonical, ни в reference) — это не глобальный символ.
2. **Network3/FBAnd1 (canonical):** `in_Safety_Run ∧ b_EStop_Ok ∧ ¬Step2 ∧ ¬Step1 ∧ ¬Step3 ∧
   ¬Step4 ∧ ¬Step5 ∧ FBAnd2`, где FBAnd2 = `¬b_Step12 ∧ ¬in_False_SI2_CH8 ∧ ¬b_Step_RnD ∧ ¬Step6`;
   выход → FBOr2.OrIn2 → **FBRs1.Set = b_Step1 (Safe)**. Reference — та же функция для Step1…6
   (`AndIn8 = ¬Step6`; R&D/Step12 в reference не стадии Network3). То есть это исходная
   ветвь инициализации Safe: «группа работает ∧ авария снята ∧ нет ни одной стадии → Safe».
3. **Семантика `RunStop`** (документация Beckhoff, уже зафиксированная в проекте:
   SCENARIO_DECISIONS V14-Q20, историческая запись — проверка ведущего; NETWORK4_SOFTWARE_SEMANTICS.md
   §«RunStop / ErrAck»): Run = FALSE ⇒ все FB группы в STOP, выходы группы в безопасном
   состоянии; RUN — разрешение выполнения. Поскольку тот же сигнал подан на `//RunStop`,
   **в любом скане, где логика группы реально исполняется, `in_Safety_Run` = TRUE**.
   Скан «логика исполняется при in_Safety_Run = FALSE» в target недостижим; это артефакт
   стенда (`sal-runtime.js` исполняет блоки независимо от RunStop — BOOT:UNSUPPORTED_GROUP_LIFECYCLE).
   Чтение `AndIn1` в FBAnd1 внутри работающей группы — тождественно TRUE.
4. **Решения/требования.** Прямого значения в R0 (CRITERIA v2 §0) нет. Согласуются с TRUE:
   - Вадим (V14-Q20, историческая запись): «TwinSAFE не работает без PLC; при остановке PLC
     группа TwinSAFE тоже переходит в безопасное состояние»;
   - Q-RC-10: «по проекту группа стартует в Emergency» + SPEC §4 `[*] --> Emergency --> Safe`
     (физическое восстановление); V14-Q6/EMG6-01: выход из Emergency — зелёная (in_Reset_PB →
     FBEstop1.Restart) только в Safe. Путь reference к Safe после Restart — именно FBAnd1
     при in_Safety_Run TRUE;
   - BOOT-001/BOOT-C: старт/рестарт не восстанавливает Run/Config.
5. **Проверка на стенде (canonical, диагностический прогон, скрипт аналитика в scratchpad,
   helper тестировщика без изменений):**
   - TRUE: до Restart — стадий нет, статус Emergency (D2-A); Restart (in_Reset_PB 1 скан на t=11,
     отпущена t=12) → `b_Step1` с t=13 без инъекции. Safe достижим реальным producer'ом.
   - FALSE: после Restart стадий нет бессрочно (`b_EStop_Ok` TRUE, статус по D2-A — Emergency);
     Safe недостижим без записи памяти.
   - TRUE, режим `E2_LV_HEALTHY_MODE=split` (только диагностика, обход RED полярности):
     вход в Run через BOTH из R&D — скан без стадий (R&D сброшен, Step3 ещё нет), FBAnd1
     ставит Step1 ⇒ `b_Step1+b_Step3` со следующего скана и далее; через ~2 скана после
     этого C1 и C2 OFF, затем STO активируется (+~100 мс). Т.е. при реальном значении
     TRUE canonical имеет **двойное владение и снятие энергии в Run через ветвь
     инициализации Safe**. Это условный (split) контрпример, не доказанный дефект; он попадает
     под E2-01/E2-04 и скрыт нормативным вариантом FALSE + инъекция.

### Ответ аналитика (READY-D, вопрос Вадиму не требуется)

- Для всех функциональных тестов E2 (и далее до E7) **in_Safety_Run = TRUE постоянно**
  — дополнение к R0. Обоснование: §3 (значение определено привязкой к `//RunStop`
  и семантикой группы), §4 (решения Вадима согласуются). Это не утверждение о том, как PLC
  формирует бит (вне объёма: «входы программы заданы»), а единственное значение, при котором
  исполняется проверяемая логика.
- `in_Safety_Run = FALSE` и переходы FALSE↔TRUE — только сценарии E7 BOOT/group lifecycle,
  требующие модели жизненного цикла группы (STOP ⇒ безопасные выходы, сброс/сохранение памяти
  FB). На нынешнем стенде такие тесты не имеют oracle и не дают PASS/FAIL по BOOT-001/002.
- «Старт группы» на стенде = первый скан с in_Safety_Run TRUE и начальными памятями SAL —
  приближение, не native BOOT (см. ограничения ниже).

Необязательное подтверждение для Вадима (не блокирует, ведущий решает, задавать ли):
«Исходно PLC в RUN, обмен EtherCAT в норме. Подтвердите, что бит IN_SAFETY_RUN (SDS 50,
Run группы TwinSAFE) всё это время TRUE и что при его снятии действует только штатное
поведение группы (STOP, безопасные выходы), без отдельной программной реакции.»

## Q2 тестировщика — допустима ли объявленная инъекция начального Safe до EX/BOOT

### Рекомендация

**Как нормативный путь — нет; как объявленная диагностика — да.**

1. Инъекция больше не нужна: при in_Safety_Run TRUE Safe достигается реальным путём
   «старт группы → Emergency → Restart зелёной → Safe (FBAnd1)» — тот же путь, что в reference
   и в EMG6-01. CRITERIA v2 §0 прямо требует: устойчивые состояния — реальными producers,
   «не инъекцией Set». Инъекция b_Step1 при FALSE противоречит §0.
2. Инъекция при FALSE маскирует ровно класс рисков E2: при FALSE ветвь FBAnd1 выключена, и
   тест не видит её срабатывания в бесстадийных сканах переходов (наблюдение §5 Q1). Значит
   нормативный FAIL/PASS E2-01/E2-04 по варианту FALSE + инъекция занижает покрытие.
3. Поэтому:
   - нормативные тесты E2 (E2-01, E2-02, E2-04, IL-*, HLT-*, POL-01) — **in_Safety_Run TRUE,
     без инъекции**; lifecycle: старт → Restart → Safe → … ;
   - вариант FALSE + `declareSafe`/запись b_Step1 — сохранить только как диагностический,
     с пометкой в имени `[DIAG injected-Safe, in_Safety_Run FALSE]`, вне `behaviouralTests`
     мутационного раннера и вне подсчёта покрытия ID; его PASS не засчитывается ни одному ID,
     его FAIL — справка;
   - E2-04 «group start before Restart [in_Safety_Run false]» — переименовать в диагностику
     (в target при FALSE логика не исполняется; тест не моделирует ничего достижимого);
     нормативен вариант `[… true]`.
4. **Что не доказывают тесты E2 даже с TRUE (пределы):** native BOOT группы и её STOP/RUN
   lifecycle, ErrAck, сброс памяти FB при рестарте (BOOT-001/002 остаются E7); поведение при
   пропадании Run группы во время работы; поведение target-Restart. «Первый скан» — начальные
   значения SAL на стенде, не доказательство порядка инициализации EL69xx.
5. **Что не доказывают тесты с инъекцией (если оставлены):** достижимость Safe; выход из
   Emergency (EMG6-01); E2-04 во время работы; отсутствие ложной инициализации Safe из
   беззаповедного скана; любые утверждения «стадий ≤ 1» на участке старт → первый Safe.

Пометка для тестировщика по переходу на TRUE: в нормативном режиме (raw FALSE = исправно)
lifecycle всё равно RED на входе в R&D (N11/FBAnd4, D-ARCH-POL) — ожидаемо; в split-диагностике
появится S1∧S3 + снятие C1/C2 при входе в Run (§5 Q1) — это не причина возвращаться к FALSE.

## Новые вопросы Вадиму (адресные)

### Q-E2Q-01 (средний; EMG6-01/EMGREF-LV, вариант (2) Q-ARCH-01) — момент C1 OFF при аварии во время Safe→R&D
Исходно: устойчивый Safe, принят Safe→R&D (BOTH), C1 включён, R&D ещё не подтверждён.
Событие: in_ES_NC_1 FALSE (или in_Estop_PLC / Mentee / потеря connector).
Известно (Q-ARCH-01 «А»): общая аварийная цепь — сразу C3/BMS OFF и LV discharge, C1 OFF
через 2 с; Emergency; «во (2) подъём LV прекращается немедленно».
Не хватает: C1 в этом случае снимается (А) по общей цепи через 2 с (а «немедленно» значит
только: R&D не подтверждается и новых шагов подъёма нет), или (Б) сразу в скане события?
Зависит только проверка момента C1 OFF в варианте (2); остальное READY (CRITERIA_DELTA EMG6-01-LV).

### Q-E2Q-02 (средний; STP-F, E2-02(L), HLT-03) — SafetyFault при потере LV Healthy на нормальной остановке
Исходно: устойчивый Run, принят down (зелёная/CMD_RUN_TO_R&D); STO уже активен (выбег 5 с,
выдержка разряда или ожидание C2_FBK OFF). Событие: LV Healthy пропала (in_LV_Faulty_FBK TRUE),
не вернулась. Известно: Q-RC-09 — остановка продолжается до R&D, «не fault», далее цепной
R&D→Safe (E2-Q2a); Q-ARCH-05/Q-RC-11 «А» — SafetyFault (HealthyLost) при потере Healthy
в Run, SS1, StartingRun и в устойчивом R&D (шаг в Safe).
Не хватает: выставляется ли SafetyFault в этом случае — (А) да, когда начинается цепной
R&D→Safe (как в устойчивом R&D); (Б) нет — потеря пришлась на штатную остановку (Q-RC-09
«не fault»), спуск в Safe без ошибки. То же для гонки E2-Q1 (потеря LV в ожидании C2_FBK OFF).
Потеря HV в этих фазах — без ошибки (Q-RC-09, E2-Q2b), не спрашивается.
