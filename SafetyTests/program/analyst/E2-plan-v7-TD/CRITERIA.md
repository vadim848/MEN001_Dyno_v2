## 1. TD5-EOK — legacy (1,0) в Emergency не исполняется (TEAM-DEFAULT TD-05)

Источники: TD-05; вопрос 74 «А» (TD-01: Emergency запрос LV не снимает); D-TEAM п.1. Подкрепляет Q-RC-05(b).
ID: MOD-001, MOD-005, EMG-011. Мутант: M-E2a-35 (PLAN v7 §8).

**Исходное состояние R-T5.**
- Устойчивый Safe после R&D→Safe (MOD-005):
  - `out_Step1` TRUE, `out_Step12` FALSE;
  - `out_LV_Discharge_Request` TRUE;
  - `out_LV_C1` и `out_HV_C2` FALSE, C1_FBK и C2_FBK OFF;
  - STO установлен.
- Крышка закрыта, connectors в норме, M = (0,0), кнопки отпущены.
- Нет SafetyFault.

**Последовательность.** Сначала `in_ES_NC_1` FALSE с e (вариант: `in_ES_NC_2`; вариант: `in_Mentee_EStop`).
Затем M = (1,0) с t; удержание 3000 мс либо импульс 50 мс; дальше M = (0,0).

| Граница t | Ожидание | Статус |
|---|---|---|
| t ≥ E+1 (в т.ч. E+1, E+50, E+2000) | см. «Ожидается» | TD-05 |
| t = E | наблюдение | конвенция q |
| t = E−1 | подъём может быть принят до Emergency; дальше аварийная цепь по EMG-критериям. Здесь не нормируется | — |

**Ожидается: каждый скан [t, t+3000], пока Emergency активна.**
- `out_Step12` FALSE, стадия S1 (либо аварийная стадия по цепи Emergency, но не S12/SR);
- `out_LV_Discharge_Request` TRUE без перерыва;
- `out_LV_C1` FALSE, `out_HV_C2` FALSE, STO установлен.

**Запрещено:**
- S12 хотя бы в одном скане;
- `out_LV_Discharge_Request` FALSE хотя бы в одном скане (на E2a-RC без гейта: FALSE на +3 — модель t20 (D));
- `out_LV_C1` TRUE;
- снятие Emergency по команде PLC.

**Импульс (1,0) только внутри Emergency, затем рестарт с M = (0,0).** После рестарта подъёма нет.
Это отсутствие отложенного исполнения, D-TEAM п.1 (READY-D: уровень снят до рестарта).

**Положительный контроль (READY: TD-01 / DIS-HOLD-LV).** R-T5 без Emergency, фронт (1,0) в t.
- S12 принят;
- запрос LV FALSE не позже u1+1.

Контроль нужен, чтобы гейт не оказался постоянным FALSE.

**Не нормируется здесь.** (1,0) удерживается через рестарт: после возврата EOk исполнится по уровню.
Это known FAIL KF-3 (§3).

## 2. FBK10-PLC — запрет подъёма по legacy-пути при FBK ON без команды (READY-D)

> **Частично заменено E2-Q76 (вопрос 76 «Б», 2026-10-22)**, `program/analyst/E2-Q76/CRITERIA.md`: FBK10-PLC-B и FBK10-PLC-REG (2) заменены оракулом LEG11-OFF — Q76-N2 и Q76-N1; позитив собственного FBK — Q76-P3. FBK10-PLC-A и FBK10-PLC-REG (1) ((1,0)) действуют без изменений (Q76-P4). Текст ниже не переписан.

Решение ведущего: PLAN v7 §13, вариант (а).

Это не TD. Однозначная цепочка:
- **Q-V4-02 «В»:**
  - «в устойчивом Safe (C1_FBK или C2_FBK ON) или R&D (C2_FBK ON) без команды ON … запрет подъёма, пока FBK не станет OFF»;
  - запрет задан на состояние; источник подъёма (кнопка, PLC) не оговорён.
- **TRACE_MATRIX MOD-008:** «каждый противоречивый/неподтверждённый feedback запрещает up». Тоже без оговорки источника.
- **Q-V7-04 «Б»:** запрет держится, пока FBK ON.
- **Кнопочный путь уже так гейтирован**, тем же сырым FBK (F1/план v5 §3.6, справка о реализации, не oracle):
  - Safe→R&D — N2/FBAnd2;
  - R&D→Run — GATE_020.AndIn8.

Аналогия (D-TEAM п.2) не требуется: требование прямо покрывает любой источник.

ID: MOD-008, MOD-001, MOD-002, WDG-004 (часть «UP заблокирован»).

### FBK10-PLC-A — Safe→R&D

**Исходное состояние.**
- Как R-T5 без Emergency.
- С f один из вариантов:
  - C1_FBK ON без команды;
  - C2_FBK ON без команды;
  - оба ON.
- Safe устойчив до f; ≥ 600 мс после последней команды OFF — вне окна E6-Q1.

**Последовательность.** M = (1,0) фронтом в t ∈ {f+1, f+100, f+3000}. Удержание до t+1000, затем (0,0).
FBK ON всё это время, до t+1500.

**Ожидается: каждый скан [t, t+1500].**
- `out_Step12` FALSE;
- `out_LV_C1` FALSE;
- запрос LV TRUE (если был выдан);
- STO установлен.

**Запрещено:**
- S12;
- C1 ON;
- снятие запроса LV;
- Emergency из-за FBK-10 (Q-V4-02: «Не Emergency»).

### FBK10-PLC-B — R&D→Run

**Исходное состояние.**
- Устойчивый R&D:
  - `out_Step12` TRUE;
  - C1 ON, C1_FBK ON;
  - LV в норме.
- С f C2_FBK ON без команды C2.
- Крышка закрыта, EOk, `out_HV_Discharge_Request` TRUE.

**Последовательность.** M = (1,1) с t ∈ {f+1, f+100, f+3000}, удержание 1500 мс.

**Ожидается: каждый скан [t, t+1500].**
- стадия R&D, SR нет;
- `out_HV_C2` FALSE, `b_Set_HV_C2_1` FALSE;
- STO установлен;
- `out_HV_Discharge_Request` TRUE (DIS-HOLD-HV: снятия нет без принятого подъёма).

**Запрещено:**
- SR/Run;
- C2 ON;
- снятие STO;
- снятие запроса HV;
- Emergency из-за FBK-10.

### Границы FBK OFF (g — первый скан FBK FALSE)

| Сценарий | Ожидание | Статус |
|---|---|---|
| Импульс M 50 мс, окончившийся в g−1 | подъёма нет ни в одном скане до t+3000 | READY-D (Q-V4-02; удержанного уровня нет) |
| Импульс, окончившийся в g | наблюдение | конвенция q |
| M удерживается до g+1 и дальше, либо новый фронт после g без квитирования кнопкой | по Q-V7-04 «Б» подъёма нет (SafetyFault до квитирования). На E2 гейт ¬FBK этого не обеспечит | **known FAIL KF-1** до E5 |

### FBK10-PLC-REG — гейт не меняет нормальный legacy-подъём (READY-D)

Источники:
- решение ведущего (а) «без изменения интерфейса PLC»;
- D-TEAM п.4: отключение legacy-пути — это вариант (б) и вопрос Вадиму;
- Q-V4-02: «без команды ON»; FBK ON после собственной команды ON сюда не относится.

**Сценарии.**
- (1) R-T5 без Emergency, FBK OFF, фронт (1,0), удержание. C1_FBK ON в u1+x, x ∈ {1, 250, 499}. LV в норме.
- (2) Устойчивый R&D, C2_FBK OFF, крышка закрыта, (1,1) удерживается. C2_FBK ON в u+x, x ∈ {1, 250, 499}. HV в норме.

**Ожидается.** Выходы `out_Step*`, `out_LV_C1`, `out_HV_C2`, STO, запросы разряда — поскан равны тем же сценариям на кандидате без гейта ¬FBK (тот же срез E2a-RC/E2d).
В частности:
- R&D наступает по RND-CONF-T;
- Run — по RUN-CONF-T.

**Запрещено.** Собственный FBK ON после выданной команды:
- не снимает C1/C2;
- не возвращает стадию;
- не ставит SafetyFault/Emergency;
- не прерывает запуск.

**Подслучай: окно выключения (E6-Q1), FBK ещё ON ≤ 500 мс после команды OFF в Safe.**
- Подъём по legacy-пути в этом окне: **наблюдение**.
- Q-V4-02 его не покрывает («устойчивый Safe»). Ни одно требование не требует там подъёма.
- Кнопочный путь гейтирован тем же сырым FBK.

### KF-3-DESC — пример KF-3: удержание (1,1) во время спуска Run→R&D (READY-D, known FAIL до E4)

Источник примера — ревью плана v7.2, V2-1 (`heldThroughDescent`, модель proto v7.2; на canonical F1 — NV).
Это KF-3 (уровень исполняется повторно), не гейт FBK-10: с M-E2d-14 (гейт снят) исход тот же.

**Исходно.**
- Устойчивый Run, достигнутый legacy-путём: M = (1,1) удерживается с подъёма.
- C2 ON, C2_FBK ON, HV норма, STO снят.
- Крышка закрыта, EOk, кнопки отпущены ≥ 2000 мс.

**Последовательность.**
- Зелёная 0,5 с (одиночная, квалифицированная) → принят Run→R&D в t_a.
- M = (1,1) удерживается без перерыва до t_a+10000, затем (0,0).

**Ожидается** (V14-Q11, PLC-001 «удерживаемая … не повторяется», MOD-003, D-TEAM п.1):
- спуск Run→R&D идёт штатно: SS1/STO/Discharge/C2 OFF по STP-001/STP-004. Моменты — по их критериям, здесь не нормируются;
- после прихода в R&D, каждый скан до t_a+10000:
  - стадия R&D, SR/Run нет;
  - `out_HV_C2` FALSE после его штатного снятия;
  - STO не снимается;
  - `out_HV_Discharge_Request` TRUE (Q-V7-01 «Г»: держится до следующего **принятого** подъёма).

**Запрещено:**
- повторный вход в SR/Run;
- повторная выдача C2 ON;
- снятие STO;
- снятие запроса HV удерживаемым уровнем (1,1).

**Положительный контроль:** после (0,0) ≥ 600 мс и нового фронта (1,1) R&D→Run принимается (FBK10-PLC-REG).

До замены legacy-интерфейса в E4 — **known FAIL** (модель: R&D на +106, затем снова Run).

Попутно (справка, не oracle этого пункта): в той же модели на +106 стадия R&D при ещё включённом C2 (ревью V2-1, «спуск Run→R&D: стадия R&D, C2 ещё ON»). Против STP-004 / SPEC стр. 527 это надо проверить на G3 фактом на кандидате. Модельное наблюдение дефектом не объявляю.

### KF-5 — критерий проверки (READY-D, known FAIL до E3/E4)

Источник наблюдения — ревью плана v7 §5 (N7-2) и v7.2 V2-3; PLAN v7.2 addendum «KF-5». Модель x7/x7b/x10; на canonical F1 — NV.

**Исходно.** Устойчивый R&D:
- C1 ON, C1_FBK ON, LV норма;
- C2 OFF, C2_FBK OFF, STO активен;
- `out_HV_Discharge_Request` TRUE (вариант: FALSE, если запрос не выдавался);
- крышка закрыта, EOk, нет SafetyFault, M = (0,0), кнопки отпущены ≥ 2000 мс.

**Последовательность.**
1. M = (1,1) импульсом w ∈ {1, 50, 300} мс с t, затем (0,0).
2. C2_FBK следует команде C2 (+1 скан), HV норма.
3. Наблюдение до t+10000.
4. Зелёная 0,5 с в t+10000, наблюдение до t+25000.

**Ожидается в t+10000** — одно из двух устойчивых состояний:
- (а) Run по RUN-CONF-T — если реализация E3/E4 засчитает импульс принятым запуском и защёлкнет его;
- (б) R&D с `out_HV_C2` FALSE, C2_FBK OFF, STO активен и `out_HV_Discharge_Request` TRUE — непринятый или прерванный подъём (Q-RC-12; вопрос 73 «А»: прерванный переход снова выдаёт Discharge).

Какое из (а)/(б) — не нормируется: семантика legacy-импульса — E4, NV. Нормативно только: ни (а), ни (б) → FAIL.
Из (б) зелёная в t+10000 → R&D→Safe по MOD-005; Safe с C1 OFF и C2 OFF.

**Запрещено:**
- скан ≥ t+10000 со стадией R&D и `out_HV_C2` TRUE (STP-004, SPEC стр. 527);
- R&D с C2 ON и `out_HV_Discharge_Request` FALSE вне идущего перехода;
- после зелёной к t+25000 нет Safe с C2 OFF;
- выход из застревания только через Emergency.

Моменты внутри перехода и время до (а)/(б) не нормируются. 10 с — горизонт теста; нормы моментов появятся с исправлением E3/E4.

Пометки:
- Эти FAIL не скрываются и не выдаются за PASS. Тесты на них — с ожиданием по требованию; на E2 результат FAIL (known).
- Kill по этим guard'ам на E2 не ожидается.
- Новых решений этот перечень не вводит.
- Интерфейс PLC (коды, сигналы) — на пересмотре E4 (AGENTS.md). Перечень не предрешает новую схему команд.
